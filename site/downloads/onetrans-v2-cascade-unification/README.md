# OneTrans-V2: Unifying Retrieval, Pre-rank, and Fine-rank with One Transformer in Industrial Recommender

OneTrans-V2は検索・粗い順位付け・精密な順位付けを残し、ユーザー文脈とTransformerを共有する。著者はオンラインGMV/user +9.74%、同じハードウェア予算で3.2倍のQPSを報告する。

## Core Idea — 主張と解釈

著者の主張：段階ごとのトークンと候補特徴を保ちつつ、ユーザー履歴を一度符号化する。DCGRは複数の検索目的を決定接頭辞で表し、業務上の重みを生成時に加える。

Labの解釈：本ライブラリでは「段階を保つ統合」に位置づける。Sona/OneRec型の段階廃止、UNIQUEの早期融合、VARGの粗い順位付けの迂回とは、統合する境界が異なる。この分類はLabの整理であり、これらとの同条件の優劣は示していない。

## Overview — 概要

OneTrans-V2は検索・粗い順位付け・精密な順位付けを残し、ユーザー文脈とTransformerを共有する。著者はオンラインGMV/user +9.74%、同じハードウェア予算で3.2倍のQPSを報告する。

## Problem — 問題設定

段階別モデルは同じユーザー履歴を繰り返し符号化し、学習信号も分断する。一方、全段階に最も重い候補特徴を使えば費用が膨らむ。共有する文脈と段階固有の処理を分ける必要がある。

## Why It Might Work — 解釈

解釈：同一要求の履歴計算を共有すると重複を減らせる。精密な順位付けから粗い順位付けへ知識を蒸留すれば、候補を早期に落とす判断も合わせやすい。ただし3.2倍のQPSには配信側の共同設計が含まれ、キャッシュ単独の寄与ではない。

## モデル / 手法

## 共有文脈の上に段階固有のトークンを置く

Figure 2では履歴から共有文脈Hを作り、検索・粗い順位付け・精密な順位付けの候補トークンがそれを参照する。候補特徴と計算量は段階ごとに残る。疎なMoEで容量を増やし、μP系のパラメータ化で学習の拡大を安定させる。

DCGR（Figure 3）は、注文・探索・広告などの決定と注文金額の区分を接頭辞zに置き、その条件下で3段のsemantic IDを生成する。式(4)の候補得点は、log P(z|H) + βφ(z) + Σℓ log P(SIDℓ|H,z,SID<ℓ)。φは業務目的に応じた加点、βはその強さである。

β = 0ならモデル確率だけで並べる。βを増やしても特定の商品を必ず選ぶ制約にはならず、接頭辞の確率と商品コードの条件付き確率がともに残る。人工図では3段のコード確率を一つの積へまとめ、全3候補を比較する。枝刈りを伴うbeam searchの再現ではない。

SNT（Figure 4）は履歴を学習サンプルの中心に置き、複数の露出へ符号化を再利用する。各露出が未来の行動を参照しない因果的なmaskが必要になる。配信での共有と学習での再利用を分けて読む。


## Executable Understanding — 最小実験

`uv run papers/onetrans-v2-cascade-unification/run.py`。標準ライブラリだけで実行でき、同じフォルダーのresults.jsonを更新する。

rank()でβを0・0.5・1・2に変え、同じ候補の決定確率・商品確率を固定したまま順位を計算する。文脈計算100、段階処理10+20+30という人工の費用も、3回符号化する場合と1回共有する場合で比較する。

## Results — 人工例の結果

β=0ではA、β=1ではB、β=2ではCが首位になる。人工の計算費用は360から160へ減るが、これは2.25倍という仮定上の比であり、実測3.2倍の説明や再現ではない。

## What We Verified — 確認範囲

CONFIRMED：β=0で確率順へ戻ることと、加点による候補順位の変化。MechanismはPARTIAL。

## What We Did NOT Verify — 未検証

Performance / Scaling / Production applicabilityはNOT TESTED。Transformer、MoE、SNT、学習されたsemantic ID、段階間蒸留、GPUキャッシュ、オンラインA/Bは実行していない。
