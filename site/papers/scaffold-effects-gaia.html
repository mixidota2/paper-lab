概要

エージェント評価では、モデルの推論と scaffold の引き出し方が混ざる。本論文は後者を操作変数にした。GAIA は複数手順、Web、ファイル読解を含むため、単発の回答より制御フローの差が出やすい。

問題設定

Model A を scaffold X、Model B を scaffold Y で測ると、点差はモデル差とも scaffold 差とも言えない。論文の中心は「評価単位を model 単体に置くと交絡する」という問題設定である。さらに ReAct と他の二つはツール面が完全一致していないため、この論文自身の比較にも残る交絡がある（§3.3、§6）。

核心

論文に書かれていること

著者は GAIA validation の Level 1・2 で、ReAct、Planner-Actor-Rater（PAR）、planner-then-executor を 5 モデルに交差させた。問題と条件を固定し、各問を 3 回実行した（§3.3–3.5）。最大の scaffold gap は robust slice の Opus Level 2 で 28 ポイントだった（§4.1）。

Level 2 では、構造化した scaffold は ReAct より少ないツール呼び出しで、途中の失敗から多く回復したと報告する。ただし PAR の ReAct 優位は Anthropic 系では支持され、provider 横断では一様でなかった（§4.2–4.3）。

読書メモ

「このモデルは何点か」より、「どの scaffold とツール面で何点か」と書く方が正確だ。agent 数が一般に有利だと結論づける論文ではない。役割分担、再試行の位置、ツール実装を含む評価装置が測定値を動かす、という警告として読む。

なぜ効きそうか

読書メモ — 著者による因果の立証ではありません。

読書メモ（推論）。PAR は rater が失敗を検出して actor の次手を狭める。planner-then-executor は失敗しても残りの計画を参照できる。どちらも無目的な再試行を減らせる仮説である。論文はこの因果機構を同定しておらず、回復率は記述的な行動指標として報告している。

根拠

設計は 3 scaffold × 5 model × 139 問 × 3 attempt、計画上 6,255 runs である（Level 1 は 53 問、Level 2 は 86 問、§3.5）。実行完了は 5,907 runs で、15/30 cell は部分的だった（§3.6）。主指標は公式 GAIA scorer の正誤。clustered bootstrap 95% CI と scaffold × model の混合効果ロジスティック回帰を使う（§3.5、§4.1）。

強みは事前登録、条件固定、失敗・コスト・ツール量のログである。弱みは公開 validation、provider serialization bug、未完了 cell、ReAct の異なるツール面、reasoning mode を無効にした逸脱である。したがって 28 ポイントを一般的な「scaffold 効果」とは読めない。

実行可能な理解

uv run papers/scaffold-effects-gaia/run.py は、同じ 90 個の合成多段タスクに途中エラーを注入する。reactive loop、PAR 風の planner–actor–rater、planner-then-executor を比較する。結果は results.json に保存する。ここでの agent は確率的な規則であり、LLM でも GAIA でもない。

検証できたこと

合成タスクでは、構造化した制御が注入済みエラー後の回復率を上げ、平均ツール呼び出しを減らす設定を再現した。これは「回復のための状態・評価点を置く」という機構の例示であり、メカニズムは PARTIAL とする。

検証していないこと

GAIA、5 モデル、bootstrap CI、混合効果モデル、28 ポイント、provider 差、費用は再実行していない。実サービスでの信頼性、費用対効果、最適な agent 数も未検証である。反証には、ツール面を完全一致させた held-out task 上の再現と、失敗検出・修復介入を個別に外す ablation が要る。

実装

run.py は固定 seed の小さな状態機械である。途中エラーの位置、回復確率、修復に必要な呼び出しを明示している。実装は説明用で、本番 agent framework の代替ではない。
