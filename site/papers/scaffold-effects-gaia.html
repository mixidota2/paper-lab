概要

公開されているエージェント能力スコアは、「モデルが何ができるか」と「scaffold が何を引き出せるか」を 混ぜてしまう。この論文は、その elicitation gap の大きさを、タスクと条件を固定したまま測る。

事前登録どおり、ReAct / Planner-Actor-Rater (PAR) / planner-then-executor の3つを、 Claude Opus・Sonnet・Haiku、Gemini、GPT の5モデルで GAIA validation L1/L2 にかける。 同一モデル内で scaffold を変えるだけで、robust slice では Opus L2 で最大約28ポイント動く。 「能力が上がれば scaffold 感度は下がる」という直感（H2）は、少なくとも難しいレベルでは 方向が合わない。評価単位はモデル単体ではなく harness–model の組だ、という読みが主眼。

このラボの玩具実験は GAIA 精度を再現しない。中盤のツール失敗を注入した合成タスクで、 3つのループ方針の行動数と復帰率だけを見る。

問題設定

チームAが「自分の最良 scaffold」でモデルAを測り、チームBが別 scaffold でモデルBを測ると、 差分のどれだけがモデル由来か分からない。METR の時間地平線論文なども elicitation を下界として 扱うが、共通ベンチ上で現在のフロンティア並びを横断した制御比較は足りていなかった。

現場の意思決定（どのモデルを買うか、どのハーネスを固定するか）は、単一セルの数字を モデル属性だと思い込むと誤る。ここで欲しいのは、scaffold を操作変数にしたときの 精度ギャップの大きさ、能力ティアとの関係、失敗時の振る舞い、コストである。

核心

著者の主張

事前登録した仮説の骨子は次のとおり。H1: 少なくとも1モデルで best/worst scaffold 差が 10pp以上（L1）。H2: より強いフロンティアモデルほど scaffold ギャップは小さい。 H3: triframe 系 multi-agent（実装は PAR）は L2 では ReAct を上回り L1 ではそうでない。 H4: planner-then-executor はファイル読みタスクで有利。

結果として H1 は支持。H2 は交互作用はあるが「能力↑→感度↓」の方向は棄却（robust では Opus L2 が最大ギャップ）。H3 は Anthropic 系 L2 で条件つき支持、他社フロンティアでは弱い。 H4 は棄却。構造化 scaffold はツール呼び出しが少なく、L2 では中盤エラーからの復帰が高い。 Gemini × planner-then-executor は両レベルで最安寄り、かつ L2 で最も正確、というセルもある。

Research Bot の解釈

著者の数字そのものより、実務への含意は「能力リーダーボードを単一 scaffold の点推定として 読むな」に近い。マルチエージェントが常に得、という話でもなく、家族（プロバイダ）や タスク難易度で条件が変わる。調達や評価設計では、代替 scaffold を1本でも回して 見出し数字が脆いかを見るのが安い保険になる。

このラボでは復帰と行動数の玩具だけを動かした。28pp ギャップ、H検定、コスト順位、 ツール面の交絡は未検証。

なぜ効きそうか

推論 — 著者の主張ではない

構造化ループが効きそうな理由のひとつは、失敗の扱い方にある。ReAct は探索が多く、 同じ失敗アクションを繰り返しやすい。一方 PAR は rater がやり直しを促し、 planner-then-executor は明示プランの上に失敗が載るので、ステップ単位の破綻が残りにくい—— というストーリーはあり得る。ただし論文自身もメカニズムは特定していない。

「強いモデルほど scaffold 不要」が崩れる方向は、難しいタスクでは余力が大きいほど 悪いループが能力を unused のまま残す、という読みとも整合する（天井効果の解釈もある）。

根拠

論文側の主証拠は事前登録つき 3×5×L1/L2、ブートストラップ CI、混合効果ロジスティックの scaffold×model 交互作用。robust slice（SDK バグ旗の除外）で Anthropic L2 のギャップが 広がる点も明示されている。限界として、S1 のツール面が S2/S3 と違う交絡、 Anthropic SDK のシリアライズ欠陥、validation 汚染リスクが書かれている。

ラボの results.json は合成タスクの行動数・復帰率のみ。GAIA 精度や仮説検定の再現ではない。

実行可能な理解

run.py は難易度つき合成タスクに中盤ツール失敗を注入し、三方針（react / planner_actor_rater / planner_then_executor）を同じシードで回す。見る指標は mean_actions と recovery_given_mid_fail。論文の「構造化は行動少・復帰高」という 行動シグネチャの方向だけを、極小スケールで確かめる。

結果

Synthetic toy only. Does not reproduce GAIA accuracy, model families, or the paper's 28pp scaffold gap. Mechanism-oriented: action count and mid-trajectory recovery under three loop policies.

検証できたこと

合成設定では、PAR と planner-then-executor が ReAct より平均行動数が少なく、 中盤失敗が起きた試行での復帰率が高い、という方向が再現した（Mechanism: PARTIAL）。 成功率がそのまま GAIA に対応するとは言っていない。

検証していないこと

  • GAIA L1/L2 の精度ギャップ（最大28pp）や事前登録 H1–H4 の統計的結論
  • モデル家族による multi-agent 優位の条件つき性
  • Gemini s3 のコスト対精度パレート
  • ツール面交絡・SDK バグ・validation 汚染の影響
  • 性能・スケーリング・本番適用性はいずれも NOT TESTED
