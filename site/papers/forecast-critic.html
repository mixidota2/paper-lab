概要

forecast が出た後にも、極端な flatness や既知販促を無視した spike miss を見つける仕事がある。point error が後日まで分からない状況で、critic は先行アラートになり得る。

問題設定

MAPE は実績が出るまで使えず、平均誤差が低くても危険な一件を隠す。言語や画像の販促情報を予測器に入れず、review にだけ使う設計もあり得る。

核心

論文に書かれていること

Forecast Critic は LLM に forecast monitoring をさせ、temporal misalignment、trend inconsistency、spike error を検出できるかを実験する。Abstract は最良 model F1 0.88、human F1 0.97、promo context を含む spike 判定 F1 0.84、M5 の unreasonable forecast は sCRPS が少なくとも 10% 高いと報告する。

読書メモ

これは forecast を良くする手法ではなく、どの予測を人間や別モデルに回すかを決める monitoring layer と読む。critic 自身の false positive cost と feedback loop の劣化が実務上の中心になる。

なぜ効きそうか

読書メモ — 著者による因果の立証ではありません。

読書メモ（推論）。系列形状と context を言語的な期待に照らせば、統計的にあり得るが運用上おかしい予測を拾える。ただし critic がもっともらしい説明を作るだけの risk がある。

根拠

Abstract の synthetic/real-world experiments は promise を示すが、LLM version、prompt、cost、distribution shift に感度がある。F1 をそのまま自社の alert precision とみなせない。

実行可能な理解

uv run papers/forecast-critic/run.py は bias と under-dispersion を flag する規則 critic と raw MAPE ranking を比較する。LLM は呼ばない。

結果

LLM judge の代替ではなく規則ベースの批評器。言語・画像コンテキストや論文の F1 は検証しない。

検証できたこと

メカニズムは PARTIAL。誤差ランキングとは異なる failure taxonomy を持つ critic が review target を増やし得る。

検証していないこと

LLM reasoning、image/context 入力、F1、M5 sCRPS、human comparison、deployment cost は未検証である。

実装

CPU-only の透明な rule set を使い、LLM の代理であることを明記した。
