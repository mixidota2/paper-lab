generative-rec-vs-retrieval
01

概要

Pinterest の UniPinRec は、候補生成と順位付けを一つのモデル系へ寄せつつ、ANN を残した。ファネルを一気に置き換える話ではない。L0 と L1 をつなぎ、L2 の fine ranker は残す。段階的に入れられる設計になっている。

統合の柱は三つある。行動をトークンとして挟まず特徴側へ置く Masked Action Modeling（MAM）、候補生成と順位付けを一緒に学ばせる blended training、候補生成で読んだ履歴の KV-cache を順位付けで使い回すことだ。

論文の数値は重い。Hit@3 は14.8%改善した。本番では BMI saves が0.95%、push opens が0.91%伸び、レイテンシは11.1%下がり、QPS は63.6%上がった。本ラボは、これらの数値を再現せず、計算を二度払わない意味だけを模型で追う。

02

問題設定

候補生成も順位付けもユーザー履歴を読むなら、同じ履歴を別々のモデルが二度エンコードする。長い履歴ほど、その重複は無視しにくい。

行動種別をアイテムと交互に並べる設計も、文脈を長くする。候補生成と順位付けで入力の形が違えば、モデルを共有しても学習と配信のつながりが弱い。

そこで必要になるのは、既存の ANN や段階的なカスケードを壊さずに、履歴表現の重複を減らす統合である。

03

核心

論文が主張すること

UniPinRec は、行動を追加トークンにせず特徴次元に載せる MAM を使い、インターリーブを避けた。blended training と joint loss で候補生成と順位付けの学習を寄せ、配信では retrieval が計算した履歴の KV-cache を ranking が再利用する。

論文は production ranker と比べ、オフライン Hit@3 が14.8%改善し、retrieval recall は維持されたと報告する。オンラインでは BMI saves が0.95%、push opens が0.91%改善した。別配信と比べた end-to-end レイテンシは11.1%低下し、QPS は63.6%上昇した。L2 fine ranker は置き換えていない。

このラボの読み

ここで効いている中心は、モデルを一つにしたことだけではない。履歴を読む仕事を一度にし、長さを増やさず、生成した状態を次段へ渡す。モデル、入力、学習、サービングを同時に設計したところに実務的な重みがある。

生成的なシーケンスモデルを使いながら ANN を残す選択も示唆的だ。Meta の two-tower 論文とは表現形式が違うが、候補生成の配信経路を急に捨てない点では同じ方向を向いている。

04

なぜ効きそうか

ここからはラボの解釈です。著者の因果主張ではありません。

【ラボの解釈】履歴への attention が重ければ、順位付けのたびに履歴を読み直すより、候補だけを足すほうが軽い。KV-cache は、すでに読んだ履歴の鍵と値を次の段で使える形に残す。

MAM は、行動情報を捨てずに系列を膨らませないための選択に見える。インターリーブが長さをほぼ倍にすると、attention の量は長さ以上に増えうる。ただし、実測のレイテンシやQPSはハードウェア、カーネル、通信にも左右される。

05

根拠

論文の根拠は、オフラインの Hit@3 と Recall、KV-cache 再利用を含むサービング比較、本番の BMI と通知の A/B テストである。数値はそれぞれ、Hit@3 +14.8%、BMI saves +0.95%、push opens +0.91%、レイテンシ -11.1%、QPS +63.6% と報告された。

L2 を残している点は、この方式の適用範囲を読むうえで重要だ。ラボの results.json は、相対的な attention 量と系列長を計算しただけで、本番の速さもオンライン指標も測っていない。

06

実行可能な理解

run.py には二組の比較がある。第一は Baseline の別配信で、履歴を候補生成と順位付けが二度読む。Proposed は KV-cache を再利用し、履歴の prefill を一度で済ませる。

第二は MAM とインターリーブの系列長比較だ。履歴992、候補656を固定し、概算の attention 量を出す。単位は相対値であり、ミリ秒やGPU使用率ではない。

08

検証できたこと

合成計算では、KV-cache を使う経路の総コストが別配信より小さくなり、インターリーブは MAM より系列を長くした。方向を確認する模型として、メカニズムは PARTIAL と記録する。

この模型は、Pinterest の環境、Triton、GPU間通信、実際の候補分布を持たない。そのため速度の倍率を本番の11.1%や63.6%と対応させない。

10

実装

run.py は相対 FLOP と系列長を計算する標準ライブラリの小さなプログラムである。履歴992、候補656、12層、幅64は計算を見やすくするための模型の設定で、論文の環境を表す値ではない。

uv run python papers/unipinrec/run.py で results.json を再生成する。Baseline と Proposed の差がどこから出るかを追うための実装で、推薦器として利用するものではない。
