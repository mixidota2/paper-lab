問いモデル / 手法完了度が同じでも過程の採点で差が出る6構成の総合点：同じタスクとモデル群で比較根拠小実験限界

概要

モデルの回答を外部の操作へつなぐ仕組みも評価対象にする。最終成果物、途中の行動、費用を分けて見るためのベンチマーク。

問題設定

正しい手順を説明できても、ファイルを保存しなければ仕事は完了しない。ツールの形式に合わせる、状態を保つ、失敗から戻るといった実行の仕事を担うのがハーネスだ。

この研究は各ハーネスの内部を同一化しない。問題、初期環境、予算、採点をそろえ、固有のプロンプトや状態管理を残して比較する。測っているのは構成全体の差で、単一部品の因果効果ではない。

核心

著者の主張 · 論文に書かれていること

著者は106件のオフライン作業を用意し、実行の記録と成果物を採点する。完了だけでなくツール利用の適切さ、一貫性、回復などを併せて評価し、モデルとハーネスの組合せを報告単位にするべきだと主張する。

一次資料：§3.4 / §4.1 / 表2 / §4.4

解釈・批評 · 読書メモ

調達や改善の判断には、総合点に加えて「何が壊れたか」が役立つ。ただし総合点が高い構成の部品をまねても、その部品が改善原因だったとは限らない。タスク別の失敗記録から、修正すべき箇所を絞り込む使い方がよい。

モデル / 手法

Harness-Benchは 106タスク × 6ハーネス × 8モデル の比較設計。OpenClaw、NanoBot、Hermes、ZeroClaw、NullClaw、Moltisを、同じ初期ファイル・予算・時間制限・評価器で動かす。モデル群はClaude Opus 4.6、Sonnet 4.6、Gemini 3.1 Pro Preview、Qwen3.6 Plus、GLM-5.1、Kimi K2.5、GPT-5.4、DeepSeek V4 Flash（付録B）。各ハーネス固有のプロンプトや復旧方法は保持するため、個々の機能の因果効果を測る設計ではない。

成果物はタスク固有の検査器またはrubricで採点し、実行履歴の評価には固定の claude-sonnet-4.6 を使う。完了度、許可違反の有無、実行過程の品質を掛け合わせるのが特徴だ。Codex（本文ではGPT-5.4）は106件を別枠で評価し、8モデル平均のハーネスと混ぜない。

最終点だけでは、未完了だったのか過程の評価が低かったのか分からない。下の式を分解してから報告値を見る。

なぜ効きそうか

解釈・推論

形式の検査や保存確認を外側へ持たせると、モデルが正しい内容を作った後の取りこぼしを防げると考えられる。根拠の不足は形式検査では修復できない。小実験では、この2種類の失敗を分ける。

根拠

§4.1・表2の設定可能な6ハーネスは106タスクと8モデルで平均され、NanoBotの総合点76.2とOpenClawの52.4の間に23.8ポイント差がある。これは完了率の差ではない。Codexは固定モデルを伴う参考値として別枠。§3.4の過程評価にはLLM判定も含まれるため、その採点の癖も検討対象になる。

一次資料：§3.4 / §4.1 / 表2 / §4.4

実行可能な理解

60件の人工成果物に形式不備・根拠不足・未保存を割り当てる。形式と保存を順に修復し、全条件を満たした件数を再計算する。根拠不足は自動的に合格へ変えない。

実行：uv run papers/harness-bench/run.py。合成データの作り方と比較条件はコード内に記載し、図の全条件の結果を results.json へ保存する。

検証できたこと

メカニズム：PARTIAL（部分的）。確認したのは、このLabで明記した仮定の下での計算と条件による変化。原論文の機構全体を確認した意味ではない。

60件の人工成果物に形式不備・根拠不足・未保存を割り当てる。形式と保存を順に修復し、全条件を満たした件数を再計算する。根拠不足は自動的に合格へ変えない。

検証していないこと

総合点の重み、過程判定の一致率、タスク別の分散を見る必要がある。ネットワークを使わない模擬環境から、実サービスの認証・通信・状態変化へどこまで一般化するかは未確定。

実装

標準ライブラリだけで実行できる。入口は各Labの run.py、計算本体は papers/_toy_common.py にある。関数は論文IDごとに独立し、ブラウザー用の全条件と初期条件の表を同時に出力する。

意図して省いたもの：106タスク、実LLM、各ハーネス、過程のLLM採点。
