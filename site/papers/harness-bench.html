概要

agent は tool、workspace、permission、context、recovery を通して仕事をする。この system layer を harness と呼び、モデルを固定しても結果が動く点を評価対象にする。

問題設定

final answer が正しく見えても、ファイル形式、validator、tool feedback、workspace state を外せば実務成果物として失敗する。complete agent を比較するだけでは、どの層が差を作ったか読めない。

核心

論文に書かれていること

Harness-Bench は共有 task environment、budget、protocol の下で、native harness behavior を保った構成を比較する。106 の offline sandbox task と 5,194 trajectory で、completion、process quality、efficiency、failure を記録し、能力は model–harness configuration で報告すべきだと主張する。

読書メモ

これは harness の因果効果を完全に分離する実験ではない。それでも procurement や評価の単位を『モデル名』から『実行契約を含む構成』へ戻すための有用な診断枠組みである。

なぜ効きそうか

読書メモ — 著者による因果の立証ではありません。

読書メモ（推論）。回復回数や契約違反を trace と共に残せば、能力不足と orchestration の不備を切り分けやすい。ただし、harness ごとに native な設計が異なるため、公平な budget 設計が結論を左右する。

根拠

Abstract は task を manual review し、artifact、trace、usage、validator output を保存したと述べる。そこで見える差は benchmark 設計内の観測であり、実サービス全般へ直接外挿はできない。

実行可能な理解

uv run papers/harness-bench/run.py は 60 個の scripted task で、固定規則と回復規則の format/contract failure を数える。LLM API は呼ばない。

検証できたこと

メカニズムは PARTIAL。最終 completion と contract failure を別メトリクスにすると、同じ task set の比較でも結論が変わる。

検証していないこと

106 task、6 harness、8 model、execution-alignment taxonomy の割合、token efficiency、現場の安全性は未検証である。

実装

scripted agent の失敗位置を固定し、recovery rule だけを替える。再現性のため seed は使わない。
