このLabを読む

問いモデル / 手法基準を固定して、探索と知識を評価する根拠小実験限界

概要

PILOTはExperiment Manager・Search Planner・Memory Curatorを、決定的な安全・統計・権限の境界で囲む。Taobaoの前後比較でbest-bucket IPVはROAM +1.00%に対し+1.40%、探索条件の達成率は53.3%から93.3%。設計は具体的だが、Manager×Plannerの2×2比較は未実施なのでWatchとする。

問題設定

指標が悪くなったらparameterを変えるだけでは、何も変えないbucketと、頻繁に変えすぎて証拠が残らないbucketが生じる。PILOTは「どの候補か」だけでなく、「いつ観察を閉じるか」「何を独立確認するか」「どの経験を次へ持ち越すか」を扱う。

DREAMのrequest向け制御、CORALの設定更新、AgentXのcode開発と並べると、PILOTの責務は実験lifecycleにある。ROAMもagentなので、ここからagent一般が人より優れるという結論は出ない。

核心

著者の主張 · 論文に書かれていること

著者は、Managerによる能動的な実験運営、Plannerによるsegment別探索、Curatorによる経験蓄積が、反応的なROAMより探索の進捗を増やすと主張する。

解釈・批評 · 読書メモ

決定的なサービスが判断可能な選択肢を先に限定する設計に注目したい。within-taskの有意性とcross-taskの記憶の確信度を分ける設計は再利用しやすい。一方、比較実験はその設計の個別寄与まで裏づけていない。

モデル / 手法

3つの役割と、変更できない境界

Experiment Managerはtaskの受付、観察、異常対応、終了後の振り返りを進める。Search PlannerはManagerに呼ばれたときだけ候補を提案し、Memory Curatorは終了したtaskから経験を抽出する。Curatorは非同期で失敗を隔離するため、記憶の保存が失敗しても当該実験の統計的結論は変わらない。採用LLMの具体的なcheckpointやparameter数は確認範囲で明記されておらず、DREAMのQwen3をPILOTへ当てはめない。

task仕様Tは目的、指標、予算、観察期間、登録済みfeatureとstrategy、権限を含む。incomplete → awaiting → ready → frozenと固め、runtimeのplaybookも固定する。安全・統計policy > task仕様 > playbook > approvedな方法論 > 暫定hint > agentの推論という優先順を守る。学習した記憶が上位規則を書き換えることはない（§3.1）。

実行可能なcommandを列挙するManager Guard、状態を唯一書き込むState Committer、変更不能なcertificateを出すStatistics Engineが、LLMの選択を囲む。Contract Builderは観測前に判断基準を固定し、Action EnumeratorとCandidate Validatorは探索可能なactionと提案の適合性を管理する（表2）。判断と強制を同じLLMへ任せないのが設計の中心である。

観察期間を、都合のよいliftで切らない

Managerは固定した観察計画に沿ってmetricsを収集し、freshness、成熟度、sample size、割付の異常を調べる。closeするかの判断時点ではliftの向きを隠し、「もう少しで有意だから待つ」「良い日だけ切り出す」を許さない。noiseらしい異常はdiagnostic-onlyにして窓を延長、反復やhard bound違反はpauseして人へ戻す（§3.2）。

roundはcontinue、reject、promoteで処理する。rejectならChampionは変わらず、promoteなら勝ったChallengerを次の基準にする。目標達成後も段階的なscale-upと独立Dconfirmでの確認があり、search期間のデータだけではproduction deliveryを確定しない。deploy、traffic拡大、仕様変更などには人の承認が必要と本文に明記される。「実験cycle中の人の介入なし」というabstractの結果記述を、無制限の権限と読まない。

PolicyTree：同じ8次元の設定を、誰に適用するかも探す

各leafにstrategy bundleを持つ決定木で、登録済みの処置前featureだけを使ってユーザーを分岐する。全ユーザーは必ず1つのleafへ着地し、missing値の扱いも事前に定義する。木の深さ、leaf数、最小母集団比率、利用feature数、round数とtraffic予算には上限がある（§4.1）。

固定baseline T₀は実験を通して動かさない。Champion Tは現在の確認済み基準、Challengerはそこへatomic actionを1つだけ加えた木。actionはsplit、prune、hashExpand、collapse、updateStrategyの5種類。Plannerは許可集合A(T)の外の操作を作れない。Δtotalは固定baselineとの差、Δstepは現在のChampionとの差なので、基準の混同を避ける。

ROAMもLLM agentであり、非agent baselineではない。ROAMはpage0 / pagingそれぞれのCTR・IPV・CVR・GMVの4次元、計8次元の値を全体へ一律適用する。PILOTは同じ基本parameter空間をsegment別に適用するPolicyTree、checkpoint、最低調整quota、事前登録した仮説と判断基準を加える。制御方法と探索空間の両方が変わっている。

Memory Curator：1回の有意な結果を、再利用可能な知識に飛躍させない

Strategy Evidenceはfrom/to bundleとpopulation scope、Methodology Experienceはoperationとscenario条件をkeyとして記録する。taskごとのbranchへ書き、終了後にmain memoryへ照合してmergeする（§5）。task内で強いcertificateが得られても、新しい記憶はdraftから始まる。

同じscopeで独立taskによる一致が1つ増えるとsupportedへ、規定のcross-task閾値を満たし重大な未解決反証がなければapprovedへ進む。supportedはhintとして使え、approvedはstrategy recallや候補優先度などの助言に自律利用できる。同じtaskの複製は独立証拠にならない。反証は保存し、必要なら元のclaimをsupersededと記録する。新しい反対claimもdraftから始める。inconclusiveは否定的な証拠とは別の結果である。

なぜ効きそうか

解釈・推論

【解釈】観測前に判断基準を固定し、同じtaskの反復を記憶の独立証拠に数えなければ、都合のよい結果だけを学ぶ循環を抑えられる。PolicyTreeは全体一律調整では相殺されるsegment差を利用できるが、細分化しすぎると統計powerを失う。leaf比率や探索予算の制約が必要になる。

根拠

最良bucketの比較は、agentの因果効果を分離しない

Taobaoの5 bucketでROAMを7日、PILOTを最初の5日報告した前後比較。best IPVは+1.00%から+1.40%、Core IPVは+0.90%から+1.60%。共通基準からのliftであり、「PILOTがROAMよりIPVを40%増やした」とは言えない。baseline比の改善幅が0.40 percentage points増えた比較である。

表7のPILOT day 5ではbucket 23がIPV +1.40%、Core IPV +1.60%、取引数+0.95%、取引金額+1.50%。取引数の最大+0.96%はbucket 25。本文の総括はこれら最大値をまとめて記すため、全指標が同じbucketで最大になったとは読まない。bucket 21の取引数−0.13%も消さない。

Search Efficiencyの分母は、5 bucket × 3条件

「目標超過」「再設定1回以下で安定読取」「探索に純進捗」の各binary条件を足す。ROAMは1+4+3=8、PILOTは4+5+5=14で、8/15=53.3%から14/15=93.3%、40 percentage points増（表9）。計算速度や提案1件あたりの成功率ではない。また表7のday 5断面でIPVが1%を超えるのは3 bucketで、表9の4/5は期間内の目標超過の評価と区別する。

§6.3は比較がbefore/afterで非ランダムと明記する。Managerだけ、Plannerだけ、両方、どちらもなしを比べる2×2（表8）は計画であり未実施。per-action観測modelの校正と比較可能なscoringが実施条件。したがって現時点でManager・Planner・Curator個別の増分を数値化できない。traffic構成、時期、探索空間の変更、best-bucket選択の影響が残る。

実行可能な理解

同じlaunch / promote / deliverイベントに対して、権限・data health・独立確認の有無を変える。baselineの「依頼があればそのまま進む」処理と比べると、guardのある状態機械は承認のないlaunchや確認前deliveryを通さない。certificateは手作りであり、統計engineを再実装していない。

記憶では同じtask Aを10回記録する条件と、A・B・Cの独立証拠を比較する。approvedへの閾値3はLabの仮定で、論文の固定値ではない。処置前segmentによる10人の分岐と最小leaf比率も確認し、表9の算術を別途再計算する。

検証できたこと

Mechanism: PARTIAL。人工条件の計算と境界条件を確認した。results.jsonのCONFIRMEDは小さな計算命題にだけ適用する。原論文の学習済みモデルや産業環境を再現した意味ではない。

検証していないこと

LLMの候補品質、逐次検定、多重比較補正、sample ratio mismatch検出、実trafficの承認workflow、PolicyTreeの5 action全実装、memoryの自動反証統合は未検証。人工guardが動くことからIPV改善や自律実験の安全性は導けない。

Performance / Scaling / Production applicability: NOT TESTED。
