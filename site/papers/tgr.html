概要

推薦 cascade は retrieval、pre-ranking、ranking、reranking の計算量を分ける。TGR はこの境界を残しつつ、生成的な表現を各段へ持ち込む産業報告である。

問題設定

SID の階層 token を単純に生成すると、item の境界をまたぐ token 列や、意味が近いが別 item へ流れる drift が起こる。ranking 側にも、候補ごとの多目的 score を低遅延で返す制約が残る。

核心

論文に書かれていること

著者は CCFormer による generative-paradigm ranking、BARGE/HiGR による生成 retrieval・slate、offline reason token を組み合わせた TGR を示す。BARGE は item-boundary loss と semantic drift を ICA、HPR、DPD で扱うと説明する。Abstract は CCFormer の二面完全展開、BARGE の +0.60% CTR、+1.70% reading time を報告する。

読書メモ

全面的な end-to-end 置換より、遅延と GPU 予算をそろえて部品ごとに置く運用原則に価値がある。SID を decode できても、既存 retrieval を安全に捨てられるとは限らない。

なぜ効きそうか

読書メモ — 著者による因果の立証ではありません。

読書メモ（推論）。候補 channel と ranker を分ければ、生成 decode の失敗を既存 channel で吸収しながら、良い領域だけを rollout できる。失敗率、coverage、tail latency を同時に測らなければ、CTR だけで安全性は分からない。

根拠

Abstract は BARGE の offline Hit@5 +10.2–16.9%、CCFormer の最大 +3.57% CTR と +1.71% advertising revenue を記す。これらは Tencent 内 A/B の著者報告で、外部が同じ traffic と candidate pool で再現した数値ではない。

実行可能な理解

uv run papers/tgr/run.py は、800 件を score する ranker と 12 token を decode する slate の演算単位を並べる。item ID、attention、実測 latency は実装しない。

検証できたこと

メカニズムは PARTIAL。小実験では score-per-item と token decode の計算単位が違うこと、channel と funnel replacement を区別すべきことを確認した。

検証していないこと

ICA/HPR/DPD、CCFormer、HiGR、reason token、Hit@5、online A/B、億規模 serving は未検証である。反証には matched latency/candidate pool での SID invalid rate と channel ablation が要る。

実装

標準ライブラリだけで動く決定的な counter である。生成モデルの性能比較に見せないため、結果 JSON に境界を明記した。
