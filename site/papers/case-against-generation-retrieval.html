このLabを読む

問いモデル / 手法学習時の教師と配信時の2塔を分ける教師の順位情報を生徒へ渡す根拠小実験限界

概要

言語モデルをユーザーと商品の表現作りに使い、検索はベクトル索引に任せる。重い教師の判断を、軽い検索経路へ移す設計。

問題設定

数百万件の商品から候補を選ぶ段階では、候補ごとに言語モデルを動かす費用を払えない。商品IDを順番に生成する方式には、途中の枝選択や実在商品との対応付けという別の課題もある。

Two-Towerは、ユーザーと商品を別々にベクトルへ変換して近いものを探す。商品側を事前計算できるため、利用者が来るたびに全商品を言語モデルへ入力せずに済む。

核心

著者の主張 · 論文に書かれていること

ユーザーと商品を同時に読むCross-Encoderを教師にし、その候補間の好みをTwo-Towerへ学習させる。教師は関連性のYes/No判定と商品テキストの予測で訓練する。生徒は共有エンコーダーと文末位置の表現を使い、ユーザー側には潜在表現による追加推論も入れる。推論時の商品ベクトルは事前計算のまま保つ。

一次資料：§4 / §5 / §6 / §7.2

解釈・批評 · 読書メモ

この研究が示す選択肢は、豊かな意味理解と索引検索を組み合わせること。生成推薦全体への決着とは読まない。教師が高性能でも、その順位を生徒が完全には保持できず、索引更新の遅れも残る。

モデル / 手法

公開データでのbackboneは Qwen3-0.6B。教師のCross-Encoder（CE）はユーザーと商品を同時に読み、yesとnoのlogit差を関連度とする。ユーザー条件付きの商品文の次トークン予測も補助学習に使う。

生徒は同じLLMの重みをユーザー側と商品側で共有するTwo-Tower（TT）。末尾のEOS状態からベクトルを取り出し、内積で検索する。教師と生徒が同じ候補集合に付けた確率分布をKL divergenceで近づける。Coconut式の潜在推論はユーザー側だけに1段加え、商品のベクトルは事前計算できる状態を保つ。

生成一般の否定と読むのは広すぎる。公開比較では教師と生徒の成績が異なり、比較対象OneRec-ThinkはQwen3-8Bを使う。計算量・候補集合・学習条件も合わせて評価したい。

一次資料：方法と実験条件

なぜ効きそうか

解釈・推論

教師はユーザーと商品を直接照合できるので、単純な内積では見えにくい関連性を教えられる。生徒へ移せた分だけ検索品質が上がると考えられるが、圧縮には限界がある。狭い候補集合上の蒸留と、全商品からの候補生成を同じ評価にしないことが大切。

根拠

§7.2.1では、生徒が本番DLRMの正規化エントロピー（NE）と同程度に達するのに使った学習データは0.5%と報告する。NEは小さいほどよい予測損失で、クリック率の改善幅ではない。§7.2.2の古いモデルへの耐性は主に教師CEの結果であり、生徒TTの結果へ読み替えない。公開データの比較は§6、運用経路は§5。

一次資料：§4 / §5 / §6 / §7.2

実行可能な理解

16候補を4つの枝に分け、全候補の最高点と、枝の平均点で絞ってから選ぶ最高点を比べる。枝幅を増やすと取り逃しと探索量がどう変わるかを計算する。

実行：uv run papers/case-against-generation-retrieval/run.py。合成データの作り方と比較条件はコード内に記載し、図の全条件の結果を results.json へ保存する。

検証できたこと

メカニズム：PARTIAL（部分的）。確認したのは、このLabで明記した仮定の下での計算と条件による変化。原論文の機構全体を確認した意味ではない。

16候補を4つの枝に分け、全候補の最高点と、枝の平均点で絞ってから選ぶ最高点を比べる。枝幅を増やすと取り逃しと探索量がどう変わるかを計算する。

検証していないこと

同じ商品集合、更新頻度、応答時間上限で生成検索と比較したい。公開ベンチマークの教師の成績と、生徒を本番で動かす結果は分けて見る。事前学習の費用は0.5%という学習データ比に含まれるとは限らない。

実装

標準ライブラリだけで実行できる。入口は各Labの run.py、計算本体は papers/_toy_common.py にある。関数は論文IDごとに独立し、ブラウザー用の全条件と初期条件の表を同時に出力する。

意図して省いたもの：言語モデル、学習、蒸留、近似近傍索引、実測の応答時間。
