問いモデル / 手法商品情報と、情報から判断する規則を分ける観測と方策の入力を式で追う誤った棄権と誤った一致を別々に読む同じtoken予算でどこまで差が残るか根拠小実験限界

概要

IGPOは、商品があるかどうかを固定の指示文へ覚え込ませず、検索時の在庫情報から判断する規則を蓄える。Huaweiの商用AI検索で14日間のA/Bを行い、CTRは相対+3.17%、監査したbad caseは38.9%減と報告した。施策全体の効果である。在庫情報と規則の寄与は、このA/Bでは分離していない。

問題設定

「写真を印刷できるケーキ」が見つからない理由は、商品がない、検索経路が見落とす、候補にはあるが選択段で落とす、の三つに分かれる。検索失敗をすぐに「在庫なし」と学習すると、次の在庫更新でも誤った判断を繰り返す。inventoryは検索対象の集合を指す。実店舗の棚在庫数は推定しない。

核心

著者の主張 · 論文に書かれていること

著者の主張：inventory portraitに現在の検索probeとカテゴリ別scene profileをまとめ、検索段と選択段それぞれへPolicy Guidelinesを注入する。モデル重みとretrieverは固定し、offlineの探索で裏づけられた規則更新だけをreplay検証後に採用する。

解釈・批評 · 読書メモ

解釈：検索に失敗した要求を、単なる不正解ログとして扱わない点が重要になる。見落とした経路を回収できた場合だけ成功と失敗を対比し、有限探索でも未解決なら商品不在の規則を作らない。

モデル / 手法

在庫を調べてから、段ごとの規則を選ぶ

Fig. 1には二つの時間軸がある。検索時に在庫を観測する上段と、offlineで規則を更新する下段だ。上段ではembedding検索のtop-k候補から、scoreの最大・平均・標準偏差、カテゴリ内の件数、属性の有無と充足率を求め、カテゴリごとの不足や最近の変更を蓄えたscene profileと合わせてinventory portraitを作る。

規則も段ごとに選ぶ。カテゴリと処理段の索引で候補を絞り、queryとのembedding類似度で上位を取り出す。Retrieval Plannerは検索経路を決め、Selectionは得られた候補を最終結果に絞る。

規則に「商品aが存在する」と書くと、商品を削除した途端に古い知識になる。そこで「指定属性が乏しい場合は別の埋まっている属性を検索する」という条件付きの判断を蓄える。商品そのものは記憶しない。

offlineでは固定の在庫snapshotで各要求を5回実行する。判定役はDeepSeek-V3 671Bだ。成功・失敗・不確実の三つに分け、失敗や不確実な要求では最大10回の追加探索を行う。同じ要求について成功と失敗の両方が得られた場合にだけ、その差を使って規則候補を作る。未解決なら提案しない。不確実な結果も負例に使わない。

候補を採用する前には、JSON構造、対象要求の改善、背景要求への影響、固定の検証集合を順に調べる。個別に通った候補も、既に採用した規則と組み合わせるたびにreplayし、干渉が起きれば除く。未知の要求への保証はない。

なぜ効きそうか

解釈・推論

解釈：変わりにくい判断規則と、その時点の商品情報を分けると、商品追加や属性名の変更をモデル再学習なしに扱いやすい。ただしprobeは有限の検索である。見つからなかった事実から、カタログ全体に存在しないとは証明できない。著者の未解決93件の監査でも13件は検索の見落としだった。

根拠

一次資料 Table 1 / §4.1–4.4。最終テストは3,000要求で、規則の検証時から4週間後の在庫を用いた。標準構成の単一実行ではFNIが30.6→4.8%、FMが60.8→15.2%。FNIは誤った棄権率。対応商品がある要求を分母にする。FMは誤った一致率で、対応商品がない要求を分母にする。両者の分母は異なる。

同じDeepSeek-V3と18M token予算の比較では、F1@8はGEPA-style 0.787±0.004、IGPO 0.792±0.005で、差は実行間変動の範囲にある。120Mでは0.791±0.006対0.817±0.004。各3回の平均と標本標準偏差であり、単一実行の大きな差だけで手法の優位性を説明しない。

Table 4のA/Bは利用者単位の50/50割付。対照100,400人、施策99,800人で、CTR相対+3.17%の95% CIは[1.9%, 4.5%]。両群500件ずつの独立監査でbad-case相対減少38.9% [25.2%, 50.1%]。在庫なし要求にはCTRを報告せず、誤一致を減らせたかを測る。

応答は遅くなる。追加遅延はp50 49.4 ms、p95 185.8 ms。追加prompt長は平均247.3 token、p95 568.2 token。training-freeは無計算という意味ではなく、offlineの探索・judge・規則候補の生成と検証を必要とする。

検証できたこと

Mechanism PARTIAL。現在の属性を読み直す固定規則が、人工の属性移動と商品削除を扱うことを確認した。CONFIRMEDは背景要求の回帰を棄却する検査と、probeの見落としが残る反例に限る。

検証していないこと

Performance / Scaling / Production applicability NOT TESTED。DeepSeek-V3やQwen3-8Bを実行せず、embedding検索、規則の自動生成、LLM judge、商用A/B、実遅延は再現していない。実カタログの精度は不明。この4要求からは推定できない。

実装

portrait()は観測した商品の属性充足率を数え、search()は手書きの固定規則で属性を選ぶ。evaluate()が別管理の正解集合でFNIとFMを計算する。replay_gate()は対象の改善と背景の非悪化を要求する説明用の関数で、Appendix Bの全閾値や反復rolloutを省略した。追加依存はない。乱数や外部APIも使わない。
