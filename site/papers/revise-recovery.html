問いモデル / 手法根拠小実験限界

概要

REVISE は変更した値と実際の依存関係を照合し、無効になった枝だけを再計算する。再利用には妥当性の証拠が必要で、依存情報が足りなければ suffix や全体再実行へ戻る。

問題設定

変更より後の仕事を全部捨てると、独立な枝まで失う

たとえば旅行案で予算だけが変わったとき、ホテルの選択と総額はやり直す必要がある。一方、予算を読んでいない街の説明は残せるかもしれない。実行順で最初の衝突から後ろを捨てる suffix 方式は、その説明も巻き込む。

ただし、街の説明を出す経路自体が予算で切り替わっていれば依存がある。値の読み取りだけでなく、どの分岐を通ったかという control 依存も追う必要がある。これは推論精度を上げる手法ではなく、指示変更後の状態を正しくそろえる runtime の研究である。

核心

著者の主張 · 論文に書かれていること

著者は進行中の agent workflow を対象に、変更の影響を data/control 依存へ伝播し、完了済み・実行中・未着手の作業を処理し分ける。評価した実行は最新版の oracle と一致し、局所変更では restart や suffix より呼び出しを減らした。

解釈・批評 · 読書メモ

「変更に関係なさそう」という会話上の判断では再利用を許せない。ある枝が読んだフィールドをすべて記録できても、その枝を選んだ分岐条件や外部ツールへ渡した値を取りこぼしていれば、変更後もそのまま結果を公開してよいという証拠にはならない。省ける仕事が減っても、証拠が弱いときに広くやり直す性質が必要だ。

モデル / 手法

変更したパスと、実際に読んだパスを照合する

workflow を DAG G=(V,E) とし、artifact ごとに版番号を持つ。読み取り selector (a,p,c) は artifact、内部のパス、data/control の区別を記録する。revision e=(a,v,v+1,op,Δ) は変更されたパス集合 Δ を運ぶ。古い版への revision は受け入れない。

構造化された状態を read-only proxy で包み、フィールド参照では leaf path、列挙では集合の #members を記録する。親子のパスは重なりとして扱い、要素の追加・削除はその集合の membership 読み取りと照合する。直接の読者から現在有効な子孫へ影響を伝播する。

Direct = {n : Δ intersects (Rdata(n) ∪ Rcontrol(n))}
Affected = Direct ∪ active descendants(Direct)
reuse(x) ⇒ valid(x) ∧ effectSafe(x)            原典 Eq. (1)

最初の2式は Lab の整理である。原典 §3.2 の記述を集合で表した。依存が不明な読者は保守的な集合に入れ、再計算範囲を広げる。

完了・実行中・未着手では、取り消す操作が違う

無効な実行中の呼び出しは cancel、未着手なら avoid、必要な処理を新しい版で recompute する。有効性を示せる実行中の枝は continue、完了済みは reuse。許可は暫定である。

公開する直前に、最終的な読み取り履歴を検査する

変更が来た時点ではまだ読んでいなかった値を、後から読む場合がある。revision 時点だけの判定ではこの late read を見落とす。実行は immutable snapshot を使い、次の証明書を蓄積する。

Cx = (id, vstart, Rdata, Rcontrol, P, mode)      原典 Eq. (2)

P は親 attempt の識別子、mode は complete/coarse/unknown。commit では開始後の全変更と最終的な read set を照合し、親が現在の committed attempt か確かめる。revision と commit は同じ lock で直列化する。外部への作用は検査が通るまで staged のまま保持する。不可逆な作用や証拠の欠落は明示的な処理または停止を必要とする。一次資料：§3。

なぜ効きそうか

解釈・推論

同じ依存情報を使う suffix と比べれば、selective は影響を受けない途中の枝を残せる。変更が局所的で、分岐が独立し、依存記録が細かいほど差が出る。直列の処理や全体に影響する変更では、正しく動いても節約できない。

根拠

oracle 一致は、最新版への回復を測る

Table 1 の15939実行は最新版／全体再実行の oracle と一致し、古い output・effect は0と報告する。内訳には15000の GPU serving 実行と300の敵対的な順序の実行が含まれる。これは in-process の validity と effect safety の評価で、分散合意や crash recovery の保証ではない。

呼び出し削減とレイテンシーは別に読む

Qwen3-14B と SGLang を用いた10ノードの LangGraph アプリでは次の結果になる。数値は Table 5 の著者報告であり、本 Lab の toy とは無関係。

回復方法 model calls completion tokens E2E p50
full restart 10.0 80.0 719 ms
earliest-conflict suffix 7.8 62.4 711 ms
REVISE 4.4 35.2 669 ms

共有 cache を消していないため、著者は calls と生成 token を主指標、model-wall を副次指標にする。LLMCompiler の local 条件では calls が6.00→5.19→3.56。global/untracked 条件では全方式6.00に戻る（Table 7）。情報が欠けたら全体をやり直す。安全な再利用を証明できない場合の動作である。

SWE-chat の観察は実行中に修正できる時間窓を示すが、完全な依存記録がなく安全な再利用量までは示せない。手動監査30件も出現率を推定する標本ではない。負荷実験の goodput 改善は逼迫時に現れ、通常負荷へ一律に外挿できない。一次資料：§2、§4、Appendix A。

実行可能な理解

uv run papers/revise-recovery/run.py

6ノードの DAG を A,B,C,D,E,F の順に並べる。A→C は予算、B→D は都市、E は文体を読む独立な枝で、F が結合する。予算を変更すると A,C,F が無効になる。全体再実行、最初の衝突以降の suffix、依存に沿う selective で再計算集合と最新版の値を比較する。

全フィールドの変更と依存情報 unknown も走らせる。別の certificate 検査で late read、古い親、情報欠落、安全でない effect を拒否し、有効な sibling を通す。ライフサイクル操作は計画を出すだけで、実際の並行 cancel は行わない。

検証できたこと

Mechanism PARTIAL。固定 DAG での影響伝播、非連続な枝の保持、unknown 時の全体再計算、5種類の commit 条件を確認した。確認はこの合成例に限る。

検証していないこと

LLM の非決定性、動的な分岐、proxy による依存取得、membership の更新、実 cancel、revision/commit の race、外部サービスの副作用、crash recovery は NOT TESTED。toy の snapshot は純粋な値であり、実運用の証明書や lock を代替しない。原典の匿名 artifact package の公開先は確認できず、実験の独立再実行はしていない。

実装

affected() が data 依存と子孫をたどり、execute() がキャッシュを使って選択的に再計算する。commit_valid() は検査条件を純粋関数で表す。一般の REVISE runtime の実装ではなく、原典 §3 の境界を説明するための標準ライブラリだけのモデルである。
