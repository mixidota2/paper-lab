候補生成と順位付けは、どの表現まで共有できるか

Baidu/BeihangのUNIQUEはflatな意味codeと候補ごとのtarget attentionを共有モデルへ統合する。Mobile Baiduの1週間A/Bでwatch duration +0.96%、distribution volume +1.08%。P99 89 msはretrieval serviceの条件付き実測。

このLabを読む

問いモデル / 手法codeを探す教師とitemを選ぶ教師が合流する候補同士の混入をattentionで止める階層の住所から、1回の割当へflat化を戻すとrecallが下がる根拠小実験限界

概要

Mobile Baiduのhomepage、discovery page、short videoが対象。意味codeを予測して候補を展開した後、user–item内積による粗ranking、候補targetを入れる精rankingが続く。統合されるのは表現と学習・配信部品であり、カタログ全件を一度に精rankingする方式でも、下流の推薦処理をすべて削除した方式でもない。

問題設定

RQ-VAE型の階層codeは最初の粗い割当が後段の残差に影響し、人気itemへcode利用が偏る。さらに独立したretrieverとrankerでは、最終判断の教師が候補生成の表現へ届きにくい。flat化だけで目的のずれが消えるわけではないため、codeを学ぶ時点のfeedbackと、ranking教師を共有表現へ返す経路も設計する。

核心

著者の主張 · 論文に書かれていること

行動feedbackを含むEQNでflat codeを学び、UIGNの利用者prefixとTDNのitem/code targetをearly fusionする。code予測と複数のranking教師を同じ表現へ流し、階層量子化の誤差伝播とretrieval/ranking間の情報損失を抑える。

解釈・批評 · 読書メモ

Sonaのcascade置換、VARGのpre-rank迂回、LIGE-GRの追加listwiseとは導入単位が違う。UNIQUEはretrieval段に内側の粗・精rankingを持つ共有モデル。GenPageやOGRの列・page最適化とも区別したい。UniRecとの共通点は統合だが、何を共有し何を出力するかを比較する必要がある。

モデル / 手法

EQNは意味だけでcodeを作らない

End-to-End Quantization Networkはitem ID、category、publisher、titleなどと行動feedbackを使う。DSSM形式のtask別user towerと共有item towerを内積で学習し、正規化したitem vectorをflat codeへ割り当てる。codeはEMAで更新し、未使用codeは維持する。Eq. 11の使用率補正はcode利用の偏りを抑える追加策である。

UIGNとTDNはtargetを早い段階で交差させる

User Interest Generation Networkのprefixはprofile、短期・中期・interest履歴を連結する。Target-Code-Aware Discriminative Networkではcode targetとitem targetがprefixを参照する。code logitはuser–codeの交差表現をMLPへ入れて得る。単独user embeddingとcode embeddingの類似度だけではない。

公開benchmarkのTransformerは3層、4 head、hidden 512、dropoutなし。item/user embedding 256、code embedding 64、codebook 1,024。最大501 tokenはprofile 1、短期100、中期200、interest 200。productionの16,384 codeと混同しない。lossはbinary feedbackの重み付きBCE、durationのMSE、codeのcross entropy、DSSM教師、量子化正則化を合わせる。

共有forwardと実際の配信順序は別に読む

学習の共有計算graphはcodeとitemの教師をつなぐ。配信はcode予測→index展開→内積による粗ranking→TDNによる精rankingという順序を持つ。N=100 codeから数十万候補を取り、粗rankingでtop 10k、codeごとの精rankingでM=30を後続処理へ返す。N=200は約2倍の費用に対して多様性の追加利得が小さく、M=10はrecallを損なうという記述がある。

item embeddingは毎時同期、新規itemは初回impressionから5分以内にtraining streamへ入り1時間以内に量子化。昼15秒・夜30秒のcacheでhit率37%・60%。codeの鮮度、モデルversion、cache条件まで含めて89 msを読む。

なぜ効きそうか

解釈・推論

flat codeは階層間の依存を除き、候補codeそのものと利用者履歴を交差させるため、単独user vectorとの内積だけより細かな候補選択が可能になる。target同士を見せないmaskは、候補をまとめて計算しながら他候補の混入を避ける。ただしcode数分のscore計算、candidate fan-out、code/item更新の同期が必要になる。均衡化は意味的な最近傍を変えうるので、分散が下がったことだけで推薦の質を結論しない。

検証できたこと

Mechanism PARTIAL。Eq. 11のτ=0が通常の最近傍へ戻ること、正の頻度倍率による割当変化、target-to-prefixの他候補からの独立性を人工値で確認した。これらの局所条件はCONFIRMED。モデル全体のearly fusionの効果は未検証。

検証していないこと

Performance / Scaling / Production applicability NOT TESTED。DSSMの学習、EMA codebookの収束、RQ-VAEとの公平比較、GPU MFU、A/Bは実行していない。全codeのscore費用や、同じcodeへ属するitem数の偏りがtail latencyへ与える影響も未測定。

実装

assign()は正規化済みitemとcodeの距離へ相対使用率のτ乗を掛ける。attention()は学習projectionを恒等写像にした単頭attention。教師なしの4 codeだけなので、productionのflat化による分散低下は再現対象外。
