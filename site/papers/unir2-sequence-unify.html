このLabを読む

問いモデル / 手法根拠小実験限界

概要

UniR²はユーザー文脈、SID軌跡、item featuresを一つのdecoder系列へ置く。Kuaishouの2週間・5% A/BではOneLive recallと本番pre-rankを同時に置換した。全カスケードの撤去とは区別し、可視範囲・勾配・KV再利用の境界を読む。

問題設定

生成recallはSIDの条件付き分布を学び、ランキングはクリック・長時間視聴・ギフトなどの識別を学ぶ。候補IDだけでは文脈が落ちる。別ランカーでは長い履歴を再計算する。一方、全特徴を生成側へ見せると、未生成のSIDや候補属性が正解を漏らす。単に系列を連結するだけでは解決しない。

核心

著者の主張 · 論文に書かれていること

著者は、SIDを生成した過程を層ごとの特徴融合へ渡すことで、候補IDだけを引き渡す際の情報損失を減らすと主張する。DQ-PCAがタスク別の参照範囲を作り、ranking側のLoRAが生成backboneを保護しながら特徴融合を調整する（§4–5）。

解釈・批評 · 読書メモ

注目したいのは更新の境界だ。共有する表現と更新するパラメータを別々に設計している。ただし疎なembeddingは両タスクで共有されるため、すべての干渉が消えるとは読めない。OneRankerのKV受け渡し＋DCと、同一系列内でSID軌跡を読む方式は異なる。Gryphon-v2の全カスケード置換とも適用範囲が違う。

モデル / 手法

ユーザー文脈、生成軌跡、候補属性を順に置く

ユーザー側は動画・ライブなどの履歴とプロフィールを、種類別のprojectionとtype embeddingでtokenへ変換する。候補SIDには3層のRes-Kmeansを使い、codebook sizeは原文どおり8129と記される（§3）。SIDの入力は [BOS, q1, q2, q3]。BOSからq1、q1からq2、q2からq3を予測する。末尾q3は予測用ではない。全軌跡を見た状態をランキングへ渡す。

S = [P_history ; P_profile ; T_gen ; T_rank]

候補側のT_rankにはitem profile、content embedding、ユーザー×候補の交差統計、上流の事前スコアなどを投影して置く。これらをqueryとして層ごとに更新する。原典はオンライン構成に3層・hidden dimension 640を採用する（§6.3.3）。

DQ-PCAは二つのqueryに別の範囲を見せる

生成queryはすべてのユーザー文脈と、その位置までの生成tokenを読む。maskは下三角で、自己位置を含む。位置iの出力から次tokenを予測する。候補特徴は読めない。ランキングqueryが読むのはプロフィール、全SID軌跡、全item-feature tokensである。長い履歴は直接読まない。候補依存の履歴検索結果などは候補側tokenへ含める（式7–10）。

Q_gen = T_gen, K_gen = V_gen = [P, T_gen]（生成部分はcausal）

Q_rank = T_rank, K_rank = V_rank = [P_profile, T_gen, T_rank]（範囲内は双方向）

Wq/Wk/Wv/Woのbase射影を共有し、FFNは生成用とranking用を分ける。プロフィールとSIDの表現を前向き計算で共有することと、同じ損失で全層を更新することは別である。

stop-gradientの先にranking専用の適応経路を残す

生成損失は L_gen = −Σ_i α_i log p(q_i | u, q_<i)、αは前の階層ほど大きい。ランキング入力は z = Concat(u, v, h_lastSID, h_rank) で、元のユーザー・author特徴も残す。MMoE（タスクごとのgateが複数expertを混合するモデル）とタスク別towerで予測し、L_rank = Σ_t ω_t BCE(ŷ_t, y_t) を最小化する（式12–15）。

rankingのQ/K/Vでは X_rank = sg(WX) + B_rank A_rank X とする（式17）。sgはbase経路への逆伝播を止め、低rank行列BとAがranking側の変化を担う。生成経路ではこのLoRAを使わない。ranking側FFNとtowerも学習対象になる。原典は生成用・ranking用のパラメータ集合を分けつつ、疎なembedding集合は共有すると記す（式18）。本Labでは「全パラメータが完全隔離」とは説明しない。

二段階学習はSID表現が安定してから識別を加える

第1段階は生成損失のみ。第2段階はそのcheckpointから始める。同じ系列にranking損失を追加する。rankingには全sample streamを見せ、各タスクの意味に合うsample maskを掛ける。生成側はクリックを残し、露出をrandom samplingして分布学習に使う。先にSIDの意味を安定させるのは、変動する表現をもとにランカーが誤った識別境界を学ぶのを避けるためだと著者は説明する（§5.1）。

一つのサービスでも候補属性の取得は残る

GPUにユーザーprefixと候補別SID軌跡の層別KVを保持する。CPUが候補属性を取得した後、ranking tokensを追加し、cached statesとranking側LoRAを使って候補をまとめて採点する。ranking queryはここでも履歴全体へ戻るわけではない。strategy filterとrankingは候補集合を複製して並行実行し、最後にfilter flagを適用する。待ち時間にrankingを重ねる設計だ（Figure 3）。

OneRankerは生成とrankingのKV共有に加え、DCでranking側の選好を生成へ戻す。Gryphon-v2は全カスケードの置換を主題とする。UniR²で確認すべき問いは、同一系列での表現融合がrecall＋pre-rankの境界をどこまで改善したかである。

なぜ効きそうか

解釈・推論

生成したSIDのhidden stateには、プロフィールと履歴を条件にその候補へ至った情報が残る。ranking側はそれを読み、候補属性と相互作用させる。履歴を省いても役立つという仮説はここにある。LoRAは共有射影からの小さなずれを許すが、低rankの更新で必要な相互作用を表せるかはデータに依存する。attentionの集中を示すFigure 4だけで因果的な説明が確定するわけではない。

根拠

オンラインで置換したのはrecallとpre-rank

以下は§6.4の著者報告。2026年6月に開始した2週間・5% trafficのA/Bで、OneLive-based recall＋production pre-rankingを基準とする。

サービス 指標 相対変化

Kuaishou like rate +2.560%

この節には各指標の信頼区間や検定結果が示されていない。gifting intentionの厳密な計測定義も確認できない。2週間の正の差から長期定着や他ドメインの効果を推定しない。

分離を外すと生成とランキングが逆方向へ動く

Table 1のClick HR@128はOneLive 0.8284、PROMISE 0.8416、UniR² 0.8741。Table 2のCTR AUCは本番HoME系baseline 0.8450から0.8513へ上がる。

Table 3でDQ-PCAとstop-gradientを同時に除くと、生成損失は+30.10%、HR@1は−44.39%、ranking損失は−3.83%。ただし除去は二要素同時だ。個別効果は分からない。LoRA除去ではranking損失が+7.05%。履歴をrankingにも読ませる構成は15.39G FLOPs、標準構成は9.37Gで、精度と計算量の交換を選んでいる。

原典の注意点：Table 3のUniR²行のCTR/GTR AUC（0.8450/0.9541）はTable 2のbaselineと同じで、Table 2のUniR²値と一致しない。条件差の説明を確認できず、両表の絶対値を混ぜない。Figure 6の推論時間−54.29%は著者のパイプライン比較であり、絶対msやP99ではない。一次資料：§6、Tables 1–3、Figure 6。

生成の事前学習点から始め、joint gradientではranking BCEが下がる一方、NTP交差エントロピーが増える。分離条件ではbaseを生成損失だけで更新し、ranking用adapterを動かすためNTPは初期値を保つ。これは固定した矛盾目標での結果で、常に共同学習が悪いという意味ではない。

検証できたこと

Mechanism PARTIAL。生成側の未来・item情報の遮断と、ranking側の履歴除外を規則として確認した。adapterの自由度は同じにした。その条件でranking gradientをbaseから切り、生成側の損失を保てる合成例を実行した。

検証していないこと

Performance / Scaling / Production applicabilityはNOT TESTED。Transformer、実際の低rank Q/K/V、共有embedding、MMoE、sampling masksは実装していない。KV reuseのメモリ量、CPU/GPU並行処理、オンライン指標も未測定。次に調べたいのは、共有embeddingを通る干渉と、履歴の圧縮で失われる短期意図である。

実装

visibility() が許可行列、seesaw() が解析的なCE勾配p−yを実装する。両条件とも同じ初期base=log(4)、adapter=0で始める。scalar adapterはLoRAの更新境界を説明する代用品であり、行列分解の検証には使わない。
