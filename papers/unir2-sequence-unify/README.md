# UniR²：候補を作りながら、絞り込むための点数も計算する

## 論文の概要

Kuaishouの研究チームは、ライブ配信の候補を探す処理と、最終順位付けの前に候補を絞る処理を、一つのTransformerにまとめました。UniR²は利用者の文脈を読み、候補を表すIDの列を生成します。同じモデルはその途中の情報と候補の特徴を使い、候補を絞るための点数を計算します。

著者は2026年6月に、配信の5%を使って従来のOneLiveによる候補検索と予備順位付けを置き換え、2週間比較しました。Kuaishou本体では再生回数が1.177%増え、Kuaishou Liteではギフト総額が2.569%増えました。異なるアプリの指標であり、推薦の全段階を置き換えた結果でもありません。

## 候補を探す処理と順位付けの違い

候補を作るモデルは、利用者に合う候補IDを予測する。順位を付けるモデルは、候補ごとのクリック、長時間の視聴、ギフトなどの確率を予測する。別のモデルへIDだけを渡すと、候補を作る途中で計算した情報は使えず、長い履歴の処理を繰り返すことがある。一方、候補の特徴を初めから両方に見せると、モデルがまだ予測していないIDや、そのIDの手掛かりを先に読めてしまう。そこで著者は、候補を作るときと順位を付けるときで読める範囲を分けた。

## 著者が提案した仕組み

著者は候補IDだけでなく、そのIDを作る各段階の内部表現を順位付けに渡す。著者は、候補生成と順位付けで読める入力を分け、順位付け専用のLoRAで、候補生成の基本部分を更新せずに候補の特徴を組み合わせられると説明している（§4–5）。

予測時にどの情報を共有するかと、学習時にどのパラメータを更新するかは別の設計だ。埋め込みには二つの処理が共有する部分があり、学習の干渉がすべて消えるとは言えない。UniR²では同じ入力列に候補IDの途中経過を置く。OneRankerが計算済みのKVや配信側の判断を別の処理に渡す方法とも、Gryphon-v2が推薦の全段階を置き換える方法とも、対象が異なる。

## 長い履歴をもう一度読む必要があるか

候補IDを作る内部表現には、プロフィールと履歴を読んでどの候補にたどり着いたかという情報が含まれる。順位を付ける処理は、その情報と候補の特徴を組み合わせる。Labでは、候補を作ったときの情報を受け取れることが、順位付けで長い履歴を読み直さずに済む理由の一つだと考えた。順位付け専用のLoRAでどこまで必要な調整ができるかは、データに依存する。図4はモデルが参照した部分の違いを示すが、この図だけで、なぜ精度が変わったかまでは確定しない。

## 論文の実験

### 本番で比べたのは候補検索と予備順位付け

著者は2026年6月に、本番トラフィックの5%を対象に2週間のA/Bテストを始めた。比較したのはOneLiveで候補を探し、既存のモデルで予備順位を決める方式と、その二つをUniR²に置き換える方式である（§6.4）。

| アプリ | 指標 | 従来方式からの相対変化 |
| --- | --- | ---: |
| Kuaishou | 再生回数 | +1.177% |
| Kuaishou | フォロー率 | +0.655% |
| Kuaishou | いいね率 | +2.560% |
| Kuaishou Lite | ギフトを送った利用者数 | +0.717% |
| Kuaishou Lite | ギフトを送る意向（gifting intention） | +1.567% |
| Kuaishou Lite | ギフトの総額 | +2.569% |

§6.4には、指標ごとの信頼区間と検定結果が示されていない。Labではgifting intentionを正確にどう数えたかも確認できていない。2週間の差から、長期に利用する人が増えたか、他のサービスでも同じ効果が出るかは分からない。

### 一緒に外すと、候補生成の損失は増え、順位付けの損失は減った

検索した128候補にクリックされた配信が入る割合（Click HR@128）は、表1でOneLiveが0.8284、PROMISEが0.8416、UniR²が0.8741だった。表2ではクリックの予測順位を測るAUCが、HoMEを使う本番の比較方式で0.8450、UniR²で0.8513だった。

表3で、各処理が読む範囲の分離（DQ-PCA）と勾配の遮断を一緒に外すと、候補生成の損失は30.10%増え、HR@1は44.39%下がった。一方、順位付けの損失は3.83%減った。二つを同時に外した比較なので、どちらがどれだけ影響したかは分からない。順位付け専用のLoRAを外した場合は、順位付けの損失が7.05%増えた。順位付けにも長い履歴を読ませる方式は15.39G FLOPs、標準方式は9.37G FLOPsだった。

表3にあるUniR²のクリックとギフトのAUC（0.8450、0.9541）は、表2にある既存方式と同じ値で、表2のUniR²の欄とは合わない。論文ではこの差の理由を確認できない。Labでは両表の値を直接比べない。図6の推論時間54.29%減は著者がパイプライン全体を比べた結果で、絶対時間やP99を表す値ではない。[一次資料：§6、表1–3、図6](https://arxiv.org/pdf/2607.24439v1)。

## 合成例を実行する

`uv run papers/unir2-sequence-unify/run.py`

最初の合成例では、履歴2個、プロフィール1個、開始記号とSID3個、候補の特徴2個を使う。参照表の行は読む側、列は読まれる側を表す。候補を作る処理が読めない位置の値を10,000に置き換えても、集計結果は変わらない。

学習の例では、次の記号を当てる確率の目標を0.8、順位付けの目標を0.2とし、わざと同じ重みを逆方向に動かす。比較する二つの方式にそれぞれ調整値を1個置き、調整できる自由度をそろえる。学習率0.1で200回更新する。

## 合成例の結果

候補生成だけを学習した点から始め、両方の損失で同じ重みを更新すると、順位付けの損失は減ったが、次の記号を予測する損失は増えた。順位付けの損失が共有する重みを更新しないようにすると、順位付け専用の調整値だけが順位付けを学び、候補生成の損失は初期値を保った。この例では二つの目標を初めから対立させている。共同学習が常に悪いことを示す結果ではない。

## Labで確認したこと

Labは候補生成が未来の記号や候補の特徴を読めないことと、順位付けが長い履歴を直接読まないことを、合成例の参照表で確かめた。学習では調整値の数をそろえ、順位付けの損失が候補生成側の重みを変えないとき、候補生成の損失を保てた（Mechanism PARTIAL）。

## Labで確認していないこと

LabはTransformer、実際の低ランクQ・K・V、共有埋め込み、MMoE、目標ごとのサンプル選択を実装していない。KVを残すためのメモリ量、CPUとGPUの並行処理、本番での指標も測っていない（NOT TESTED）。共有埋め込みを通じてどの程度影響するか、履歴を圧縮すると直近の関心をどれだけ失うかは、この実験では分からない。

## コードが計算する範囲

`visibility()` は参照を許す位置を返す。`seesaw()` は交差エントロピーの勾配p−yを計算する。どちらの学習条件も同じbase=log(4)、adapter=0から始める。調整値を1個にしたのは、どの重みを更新するかを確認するためであり、LoRAの行列の近似を検証するためではない。
