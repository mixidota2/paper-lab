# 商品を外すと、買い替え先の棚に何個必要になるか

## 論文の概要

HübnerとKuhnは、食品小売店が扱う商品と、各商品を棚の正面に何列並べるかを、補充の条件に合わせて決める方法を提案しました。著者らは、商品を外すと、一部の客は残った別の商品を買うと仮定しました。棚割りの候補ごとに、買い替えで増える需要も計算し、次の定期補充までの需要のうち、指定した割合を満たせる個数を、その商品の棚に置けるかを確かめました。

著者らは、実店舗の飲料データを使い、買い替えの割合や、扱っていない商品の需要、商品ごとの粗利には仮の値を置きました。買い替えを最初から計算に入れた棚割りは、買い替えを考えずに棚割りを決めてから調整した方法に比べ、計算上の利益が最大14%高くなりました。この比較では実際に棚を変更しておらず、店舗の利益が14%増えたわけではありません。補充作業への影響も測っていません。

## Labで確かめること

Labでは、補充の間隔を固定し、架空の商品を使って、買い替えによる需要を足すと必要な棚在庫がどう変わるかを比べます。原著の非公開データや近似法を再現していません。

## 4つの入力で違いを見る

- T1：27候補のうち10案が棚幅に収まり、そのうち7案が商品ごとの棚在庫の条件も満たします。全部の条件を守る案の最大利益は24です。買い替えを考えずに選んだ案は、後から需要を足すと利益21ですが、Aの棚在庫が足りません。
- T2：同じ需要で比べると、基準案の利益は10、最適案は16です。どちらも条件を満たします。基準案が37.5%低いという値は、差の6を最適案の16で割ったものです。
- T3：元の需要で条件を守ると利益は最大1です。需要を棚在庫に合わせて減らした別の計算では利益が20になります。前提が違うので、この2つの数字をそのまま比較しません。
- T4：Bだけを棚に置くと、もともとの需要1個にAから移った4個分が加わり、Bの需要は5個です。

## プログラムを動かして記事を開く

リポジトリのルートで次を実行します。Pythonの計算には標準ライブラリだけを使います。

```bash
uv run --locked papers/assortment-replenishment-hard-constraints/run.py
uv run --locked --extra dev pytest tests/test_assortment_replenishment.py -q
uv run --locked python -m paper_lab.build --out /tmp/paper-lab-shelf-preview
uv run --locked python -m http.server 8000 --directory /tmp/paper-lab-shelf-preview
```

記事を開くには `/papers/assortment-replenishment-hard-constraints.html`、実験だけを開くには `/downloads/assortment-replenishment-hard-constraints/interactive.html` に進みます。実験をダウンロードした場合は、`interactive.html`、`model.js`、`interactive.js`、`results.json` を同じフォルダに置き、HTTPサーバーから開きます。

## 小数の可否と、同率の案をどう扱うか

プログラムは画面に丸めて出した値を可否の判定に使いません。同率の利益と棚幅の比較には絶対差 `1e−9`、棚在庫の比較には `1e−9×max(1,q,fD)` の許容差を使います。最大利益が同じ案はすべて保存します。画面は、面数の組を辞書順に並べ、最初の案を代表として表示します。

確認済み（CONFIRMED）は、この小規模な入力での計算の照合を指します。原論文の仕組みについては一部だけを確認しました（PARTIAL）。実店舗の性能、商品の候補を増やした場合の性能、本番への適用は検証していません（NOT TESTED）。著者らのコードは確認できていません（NOT OBSERVED）。

`tests/test_shelf_ui.py` は、ブラウザーを使わず、条件に応じて画面に載せる内容を検査します。画面幅ごとの表示や、実ブラウザーでのダウンロードが動くことは、この検査だけでは確認できません。
