# SCOPE: Supply-Chain Operations through Coupled Policies for End-to-End Coordination

## 概要

品揃えを変えると、必要な在庫や配送の負担も変わります。SCOPEの著者は、品揃え、供給元、補充の間隔、配送経路を別々に決める代わりに、前の判断を次の判断に渡す方法を提案しました。選んだ品揃えの価値から在庫や配送などの費用を差し引く共通の指標で、判断の組み合わせを評価します。

JD.comの物流データを使った18のシナリオでは、工程ごとに判断する比較手法のうち、最も良かった方法よりも、この指標が1.58%高くなりました。これは過去データを使って算出した指標の差です。会社の実現利益が1.58%増えたことを示す結果ではありません。

## 問題設定

品揃えで選ぶ商品が変わると、運ぶ数量や荷物の重さも変わります。供給元を変えると、出発する場所と道路距離が変わります。補充の間隔を延ばすと、配送の回数は減りますが、1回に運ぶ荷量や在庫を持つ負担が増えます。配送経路に同じ計算方法を使っても、前の判断によって解く問題が変わります。

## 四つの判断をつなぐ仕組み

著者は、品揃えから配送経路までの各段階で、先に決めた内容を次の段階へ渡します。各段階は別々の損失で学び、著者は検証用のデータで、計画全体の評価値が高い組み合わせを選びます。

品揃えや補充の間隔が決まると、運ぶ量や配送日も変わります。配送だけを最適化する比較では、その前に選んだ品揃えや間隔は変えられません。著者が計算した計画の評価値から、売上や利益の増加は判断できません。

## 品揃えから配送経路までを決める手順

SCOPEは、拠点と道路距離をTransformerで表し、配車費、走行費、在庫を持つ負担などの条件を別に符号化します。各段階は共通の拠点情報を使うだけでなく、その段階までに決めた内容も入力として受け取ります。ここでいう段階は意思決定の依存関係であり、最初の段階で配送を始め、次の段階まで待つという意味ではありません。

| 段階 | 決めること | 次に渡すこと |
| --- | --- | --- |
| 品揃え A | 拠点ごとに、ちょうどK品目を選びます。 | 選んだ品目で、扱う需要や配送の荷量が変わります。 |
| 供給元 σ | 各配送先に対して、条件を満たす供給元を1つ選びます。 | どこから配送するかを決めます。 |
| 補充間隔 T | あらかじめ決めた補充グループごとに、配送と配送の間の日数を選びます。 | 同じグループの配送日と、1回で運ぶ荷量が決まります。 |
| 配送経路 R | 配送日と供給元ごとに要求をまとめ、経路を求めます。 | 実際の道路距離と、車両の重量・容積の上限を使います。 |

式(1)は1日分の荷量を品揃えから計算し、それに補充間隔を掛けて、1回分の荷量を見積もります。式(2)は、品揃えの価値から、選ばなかった商品への需要にかかる罰則、配送費用、在庫を持つ負担を引きます。選ばなかった商品への需要は代理指標で、在庫を置いた商品の欠品で失った売上を測った値ではありません。

### 各段階を学ばせてから、組み合わせを選ぶ

式(3)は、前の判断を固定し、残りの判断を最適に選んだときに得られる最良の評価値を定義します。SCOPEはこの最良値を直接求めません。品揃えでは品目を一つずつ入れ替え、需要をカバーする割合と品揃えの価値が基準を満たす場合に限り、後段まで実行したときの評価値を比べます。供給元の学習に使う初期の正解は、条件を満たす中で最も近い拠点であり、後段も含めて最良の供給元を求めたものではありません。

補充間隔の学習では、ある計画条件のもとで、すべての補充グループに同じ間隔を与え、間隔の候補ごとに計画を評価し直します。最も良かった共通の間隔を初期の正解に使います。グループ別に間隔を変えたときの正解は作りません。学習後に計画を作るときは、グループごとに間隔を選べます。

配送経路を求めるモデルは、事前にOR-Toolsで作った経路を手本にします。計画を作るときはOR-Toolsを呼びません。複数の開始点から、車両容量を守れる候補を作り、その中で費用が最も低い経路を使います。すべての経路の中で最適とは限りません。

著者は各段階を別々の損失で学習させ、検証データで計画を最後まで作って、全体の評価値が最も高い学習済みの組み合わせを選びます。検証の評価値を各段階へ勾配として戻すわけではありません。

## 先の判断が配送を変える理由

配送経路だけを改善する場合、すでに決まった品揃えや補充間隔は変えられません。SCOPEの学習では、たとえば品揃えを一つ変えると、配送まで含む計画がどう変わるかを比べます。著者は、このような比較を初期の学習に使い、各段階で得た候補の組み合わせを全体の評価値で選びます。

式(3)は、先に決めた内容を固定したときの最良の計画を定義します。著者の実装は、その最良値を直接求めず、各段階の近似と検証データで候補を選びます。すべての段階に全体の評価値の勾配を戻したり、全体で最適な計画を保証したりする方法ではありません。

## 論文の評価結果

一次資料は[原論文v1の表1・2と§4](https://arxiv.org/html/2607.28488v1)です。評価値U_refは、品揃えの価値から配送や在庫などの費用を差し引き、参照値で調整した日次の指標です。値が大きい方を良い計画とします。通貨で測った実現利益や、経路の費用だけを表す値ではありません。

| 過去データを使った評価 | 別々に決める最良の比較手法と評価値 | SCOPEの評価値 | 需要をカバーした割合（比較手法とSCOPE） |
| --- | --- | --- | --- |
| Dingdong：配送拠点から店舗へ | TopDemand–OR-Tools：206,276.14 | 206,329.79 | ともに0.948 |
| JD.com：地域倉庫から前方倉庫へ | TopValue–OR-ToolsとTopValue–HGSが同点：288,973.15 | 293,547.12 | ともに0.427 |

Dingdongのデータは18都市の898店舗、865品目で、各90日の18シナリオを評価しました。最良の比較手法との差は53.65で、比率にすると約0.026%です。JD.comのデータは地域倉庫8か所、前方倉庫43か所、1,110品目、91時点の記録で、各91日の18シナリオを評価しました。拠点などの識別情報は伏せられ、業務上の数量は尺度を変えています。表1で報告した差は4,573.96（1.58%）で、表示値どうしを引くと丸めのため4,573.97になります。JDでは需要順に選ぶTopDemandのカバーの割合が0.429で、評価値が最も高い方式が、需要を最も広くカバーしたわけではありません。

表1のBestFixは、1〜7日からデータごとに一つの共通間隔を選ぶ方式です。シナリオごとに最適な間隔を知っている比較相手ではありません。表2でSCOPEの補充を毎日に固定した場合、JDの評価値は279,026.38で、元のSCOPEより14,520.74低くなりました。これは表1で毎日補充する比較手法の最高値283,074.28とは別です。間隔を変えて計画を評価し直す学習だけを外すと288,859.25となり、表の差は4,687.86でした。JDの供給元は学習の対象ですが、表2では供給元の学習だけを外して比較していません。

各段階を最初からまとめて学習した場合、段階を分けて学習したSCOPEとの差はDingdongで32,422.18、JDで74.50でした。また、学習済みのモデルを固定し、価値と費用の換算を変えた35条件ではDingdongで30条件、JDで35条件が首位でした。荷量の換算を変えた7条件では、Dingdongで7条件、JDで5条件でした。どのデータや前提でも同じ改善が出るとは限りません。著者は過去データで計画を比べており、現場で運用を切り替えた試験ではありません。

## 図で確かめること

Labでは、供給元と配送先を一つずつに固定し、需要が多く重い商品Aと、需要が少なく軽い商品Bから一つを選びます。補充間隔は1〜4日です。1回に使う車両の台数は、荷量を容量で割った値を整数へ切り上げて求めます。この人工例では容量を10に固定し、道路距離や配送経路は扱いません。

配車1台あたりの費用を切り替え、需要の多いAを先に選んでから間隔だけを比べる方式と、商品と間隔の全候補を比べる方式を見比べます。どちらも同じ費用と評価式を使います。

## Labの人工例

配車費が0または2のとき、全候補を比べる方式は商品Aを選びました。配車費が10または30のときは商品Bを選びました。配車費が10の場合、Aを先に選ぶと最良の間隔は4日で、1日あたりの評価値は11.1です。商品と間隔を同時に比べると、Bを2日おきに配送する計画が13.3で選ばれました。BはAより需要が少ない一方、運ぶ荷量が小さくなります。

全候補を比べる方式には、Aを先に選ぶ方式の候補もすべて含まれます。そのため、この人工例では、全探索の評価値がAを先に選ぶ方式を下回りません。著者の学習済みモデルがどれだけ良い計画を作るかは、この比較から分かりません。

## 確認したこと

CONFIRMED（確認済み）：Labは、車両の容量を超えると必要な台数が増えることと、配車費によって評価が最も高い商品が変わることを人工例で確認しました。

PARTIAL（一部確認）：確認したのは、荷量と費用を固定した式で計算し、2商品と4つの間隔の候補をすべて比べるところまでです。SCOPEの学習は再現していません。

## 確認していないこと

NOT TESTED（未検証）：LabはSCOPEを学習させず、複数供給元、道路距離を使った複数拠点の配送、在庫の推移、実店舗の品揃え変更を試していません。規模を広げたときの性能や、U_refが現場の利益や欠品の費用を正しく表すかも確認していません。

## 手元で同じ結果を出す

リポジトリの直下で次を実行すると、Pythonの標準ライブラリだけで `results.json` を作り直せます。

```bash
uv run papers/scope-coupled-supply-chain-policies/run.py
```

`utility()` は式(1)・(2)を簡略化し、荷量、配車費、在庫を持つ費用と、選ばなかった商品への需要を評価します。`experiment()` は商品と間隔の候補をすべて比べます。これは式(3)・(4)を読むための人工例で、ニューラルモデルや経路計算を実装したわけではありません。
