# Pinterestは、買い物向けの候補を探す価値をどう測ったか

## 論文の概要

Pinterestの研究チームは、推薦の候補を集める段階で、買い物向けの商品を探す処理を呼ぶかどうかをリクエストごとに決めました。一部のリクエストでは、その処理を呼ぶかどうかを無作為に割り付けました。著者はこの記録に異なるしきい値を当てはめ、どれを本番で試すかを決めました。本番の主方式が使うのは、呼ぶ場合の予測値だけです。呼ぶ場合と呼ばない場合の予測値の差を、そのまま判断に使ったわけではありません。

本番実験のうち、呼び出しが約40%減った群では、サイト全体のSuccess Curation件数が0.26%、ピンの詳細画面での保存件数（Repins）が1.10%増えました。購入に近い行動の指標には統計的に明確な差が出ていません。呼び出しを最大85%減らしたのは別の群で、これらの改善率が同じ条件で得られたわけではありません。

## 候補を探す段階で決める

ピンの詳細画面では、Pinterestは複数の方法で候補を集め、最後に表示順を決める。買い物向けの候補を毎回集めると、商品への反応が増える一方で、ピンの保存などが減る場合がある。後段のモデルがその候補を表示しないと判断しても、候補を集める計算はすでに済んでいる。

無作為に割り付けたのは、買い物向けの候補を配信できるリクエストの一部である。Pinterestのすべてのリクエストを無条件に無作為化したわけではない。

## 著者の提案と、このLabの読み方

著者は、買い物向け候補を呼ぶかどうかを無作為に分けた記録から、結果の予測と、呼び出しによる追加効果の推定を同時に学習した。著者は同じ記録でしきい値ごとの結果を見積もった。本番では、候補生成を最大85%減らした群でも、買い物につながる後段の指標に統計的に明確な差は出なかったと報告している。

この研究が変えたのは、候補の中から商品を何位に置くかではなく、その前に買い物向けの候補を探しに行くかどうかだ。Labでは、学習した追加効果が正しいかと、実際に使う予測値としきい値で利用者の行動がどう変わるかを分けて考える。

## 呼ばなかった記録を残す理由

同じようなリクエストで候補を呼んだ結果と呼ばなかった結果が記録にあれば、通常の配信ログでは観測しにくい「呼ばなかった場合」の結果を判断材料に加えられる。これはLabによる仕組みの解釈だ。

本番の主方式は二つの結果予測の差を取らず、呼んだ場合の予測だけで判断する。この方式なら二つの予測誤差が差に重なるのを避けられるが、呼ばなくても購入につながるリクエストを高く評価することもある。追加効果を学習したからといって、本番の方式まで最適になるわけではない。

## 論文の実験

### 同じしきい値で、事前の試算と本番を比べる

著者は基準モデルのSV方式を使い、過去の無作為ログで試算した結果と本番の結果を比べた（表4）。δ=0.0102では、候補生成を呼び出す割合が本番で64.4%、事前の試算で64.6%減った。論文のTP Imp（表示回数の指標）は本番で11.3%、事前の試算で10.1%減った。この表は、追加効果を補正して学ぶ方法だけの効果を測っていない。

### 約40%削減した群と、最大85%削減した群は別

表5の本番実験では、候補生成の呼び出しが約40%減った群で、サイト全体のSuccess Curation件数が0.26%、ピン詳細画面の保存件数（Repins）が1.10%増えた。買い物につながる後段の指標には、統計的に明確な差が出ていない。呼び出しを最大85%減らした群は別であり、表5の増加率が同じ群で得られたとは言えない。

著者は他の候補を遠隔で検索する処理と並行して採点し、リクエスト全体の応答時間は悪化しなかったと報告している（§4）。Labでは負荷ごとの応答時間を確かめるためのログを得ていない。

## 合成データで補正式を試す

```sh
uv run papers/pinterest-causal-retrieval-shopping/run.py
```

Labは3種類のリクエストに対し、呼ぶ群と呼ばない群を各100件ずつ用意した。合計は600件で、各群の結果が起きる割合をあらかじめ決めた。モデルが μ₁=0.3、μ₀=0.2 と誤って予測したとき、正しい割付確率0.5と誤った0.8で、補正後の値がどう変わるかを比べる。

もう一つの実験では、本番と同じく呼んだ場合の結果確率をしきい値と比べる。しきい値が選ぶ行動と、記録に残る割付が一致した行だけを集める。結果の合計を一致した件数で割る。均等割当のこの例で、その割付とは別に、全リクエストについてあらかじめ決めた確率から求めた平均と比べる。

## 合成例の結果

結果予測が間違っていても、正しい割付確率0.5で補正すると、3種類すべてで、あらかじめ決めた追加効果と一致した。割付確率を0.8と誤って指定すると、表の右端のように一致しなくなった。

| リクエストの種類 | 真の追加効果 | 正しい割付確率で補正 | 誤った割付確率で補正 |
| --- | ---: | ---: | ---: |
| low | 0.02 | 0.02 | 0.275 |
| medium | 0.20 | 0.20 | 0.1625 |
| organic | 0.05 | 0.05 | −0.9625 |

しきい値δ=0.3では、3分の2のリクエストで候補を呼ぶ。記録から計算した報酬率も、あらかじめ決めた確率から求めた報酬率も0.426667だった。この例はサンプルのばらつきがないように結果を用意している。少数の実データでも同じ精度が得られるとは言えない。

## Labで確認したこと

Labは切り詰めのない補正式と、均等に割り付けた記録を使う試算を確認した（Mechanism PARTIAL）。正しい割付確率で期待値と合うこと、行動が一致した記録の平均が真の平均と合うこと、割付確率を間違えるとずれが出ることの3件は確認できた（CONFIRMED）。深層モデルの学習と、補正項を切り詰める効果は対象外である。

## Labで確認していないこと

LabはPinterestの記録を使った学習、実データでのSVとDPの比較、最大85%の呼び出し削減、表5の本番結果を再現していない。性能、規模を広げたときの挙動、本番適用は検証していない（NOT TESTED）。合成例で平均が合っても、利用者の行動が変わった場合や、別の利用者に影響する場合に同じ結果が得られるとは限らない。

## コードが計算する範囲

`dr()` は論文の式7に当たる補正値を、切り詰めずに計算する。`evaluate()` は、行動が一致した記録を集めて平均する。記録がn件、しきい値の候補がk個なら、計算はしきい値ごとに全件を読むのでO(nk)かかる。論文のAlgorithm 1のように、記録を並べ替えてから結果を累積する方法は実装していない。
