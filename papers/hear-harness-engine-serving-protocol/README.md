# Can Agent Harnesses and Inference Engines Hear Each Other? The HEAR Protocol for Agentic LLM Serving

## 概要

著者は、エージェントの手順を管理する側と、モデルの推論を実行する側が情報を交換するための取り決めを提案しました。HEARでは、手順を管理する側が、同じ入力部分を後で使う予定を伝えます。推論を実行する側は、その部分の途中計算を保存しているかを知らせます。この情報を使うと、途中計算を再利用しやすい要求を先に処理しつつ、ほかの要求が待ちすぎないようにできます。

SCBenchの記録を再生した実験では、待ち時間を抑える設定で、到着順に処理した場合より全要求が終わるまでの時間が481秒から299秒に短くなりました。最初の出力までの待ち時間は中央値で63.1秒から28.3秒、95パーセンタイルで74.2秒から51.1秒になりました。別の実験では負荷によって有利な設定が変わりました。これらは配信の効率を測った値で、回答が正しくなることを示す結果ではありません。

## なぜ情報を交換するのか

手順を管理する側は次に必要な入力を知っていますが、その途中計算がGPUに残っているかは分かりません。推論を実行する側はキャッシュや待ち行列を確認できますが、ツールを待っているエージェントがいつ戻るかは分かりません。このままでは、再利用する直前にキャッシュを捨てたり、再計算が不要な要求を後回しにしたりします。

一方、再利用の予測をすべて「キャッシュを保持せよ」という要求として扱うと、混雑時にも資源を空けられなくなります。何が分かっているかと、何をする必要があるかを別に伝えます。

## 著者の提案とLabの解釈

HEARは、手順を管理する側と推論を実行する側の間で、何を知らせ、何を要求し、どの結果を返すかを定義します。要求、文脈の版、推論を担当する実体を結び付けます。著者は同じ取り決めを、キャッシュを使う要求の順序と、役割ごとの実行方法の選択に使いました（§3–4）。

[関連するハーネス費用のLab](harness-buys-tokens-not-pass-rate.html)では、作業を管理する側が推論の入力を増やす例を扱います。HEARでは、逆に再計算を減らす情報を推論側に渡します。Parrot、KVFlow、PBKV、Pythiaにも両者の情報を使う仕組みがあり、HEARの焦点は特定の実行順ではなく、予定、要求、状態、結果の意味をそろえることです。

## 何を伝えるかと、どう処理するか

### 手順を管理する側が伝える情報

エージェントの手順を管理するハーネスは、要求の役割、準備状況、依存関係、文脈をいつまで使うかを知らせます。「次のツールが終わったら同じ文脈を使いそうだ」という情報は予測です。推論エンジンにキャッシュを保持するよう求めたわけではありません。保持や解放、準備、実行方法、待ち時間に関する要件は、別の種類のメッセージで伝えます（表1）。

### 推論エンジンが返す状態と結果

推論エンジンは途中計算を保存するKVキャッシュの所在、待ち行列、資源の混雑、対応する操作を報告します。いまキャッシュがあるという報告は、次に使うまで予約したという意味ではありません。操作を受理した通知も完了した通知とは異なります。エンジンは完了、拒否、未対応、失敗を区別し、実際に使った構成、再利用できた量、費用などの結果を返します。

希望なら可能な範囲で応じます。要件を満たせないときは拒否するか、明示的に許された代替を使います（表2）。要求、文脈の版、処理を担当するエンジンの実体を結び付けて管理するため、別の版や別のエンジンの報告を取り違えずに扱えます。HEARはこの意味の取り決めで、通信で使うデータ形式や特定の実行順を定めるものではありません。

### 次に処理する要求と、保存しておく文脈

式1の `dᵢ = π(hᵢ,sⱼ)` は、ハーネスが伝えた情報と、推論側から得た最新の関連情報を使って処理を決める式です。エンジンの報告時点はハーネスが判断する時点より前の場合があります。

論文のキャッシュ優先方式は、入力の先頭から50%以上が保存済みの要求を再利用しやすい要求（hot）とし、再利用できる保存単位が多いものを先に処理します。Guard-Wは、W秒待った要求が次の実行を選ぶ段階で追い越されないようにします。到着から最初のトークンまでや処理完了までをW秒以内に収める締切ではありません。

MooncakeのSession-Awareは次の実行順ではなく、何をキャッシュに残すかを決めます。会話が続く見込みをp、処理していない時間をidleとし、`r = p exp(−idle/400)` で保持の優先順位を求めます。これは著者が試した方策で、HEARの必須要件ではありません。

### 主担当と読み取り担当の実行構成

著者は主担当のvLLM・OmniKVと、読み取り担当のvLLM・H2O・SnapKVを組み合わせた6構成を開発段階で比較しました。品質と安定性の条件を満たすものの中から、タスク全体を完了するまでの時間が短い構成を選び、正式評価前に固定しました。BrowseComp-PlusではvLLMとH2O、DeepResearchBenchではOmniKVとH2Oです（式4–5、表5）。

## キャッシュの再利用と待ち時間の関係

保存済みのKVキャッシュを使えば、入力を処理する計算を減らせます。ただし、再利用しやすい要求を毎回先に処理すると、再利用できない要求は待ち続けます。推論側が知らせる保存状況と、手順を管理する側が指定する待機の要件を分けて扱うと、両方を見て実行順を決められます。

実行方法を選ぶ際も、役割と出力の長さによって合う構成が変わります。GLM-4.7-Flashの主担当が1要求で出すトークンは、BrowseComp-Plusで約400、DeepResearchBenchで約4,400でした。一つの役割だけ実行方法を替えた表6の値は、タスク全体の短縮率ではありません。

## 論文で確かめたこと

[一次資料：原論文v1の表3–6と付録A–B](https://arxiv.org/html/2610.06597v1)。著者はSCBenchとMooncakeの記録をQwen3-8Bで再生し、同じ要求に対して実行方法を比べました。TTFTは要求が届いてから最初のトークンが出るまでの時間です。P95は、短い方から95%の要求が収まる時間の目安です。

### SCBenchのキャッシュ再利用と待機

| 設定 | TTFTの中央値／P95／最大（秒） | 全会話の完了（秒） | KV再利用率 |
| --- | --- | ---: | ---: |
| 到着順（FCFS） | 63.1／74.2／79.0 | 481 | 19.2% |
| キャッシュ優先 | 4.6／75.8／93.9 | 224 | 87.6% |
| キャッシュ優先＋Guard-40 | 28.3／51.1／65.0 | 299 | 66.1% |
| キャッシュ優先＋Guard-60 | 4.5／64.0／80.4 | 230 | 84.7% |

表3の到着順とGuard-40を比べると、全会話の完了時間の比は481÷299で約1.61倍です。中央値の比は約2.23倍、P95の比は約1.45倍です。キャッシュ優先だけの再利用率87.6%、中央値63.1秒から4.6秒、完了481秒から224秒への短縮もSCBenchの結果で、Mooncakeの値ではありません。キャッシュだけを優先した場合、最大TTFTは79.0秒から93.9秒に延びました。

### Mooncakeで再生する負荷を変えた結果

表4の50%、75%、100%は、対象期間に始まった会話のうち再生に含める割合です。GPUの使用率ではありません。50%では会話の継続見込みを使う方式（Session-Aware）だけで、再利用率が到着順の19.5%から31.9%になりました。75%ではSession-Awareとキャッシュ優先、待機保護を合わせると、1分間の処理ターン数は到着順の116.4から121.0になりました。

100%では三つを合わせた方式が108.9ターンで、到着順の122.7ターンを下回りました。TTFTの中央値は到着順163.9秒、三つを合わせると161.7秒、キャッシュ優先だけでは86.8秒でした。キャッシュ優先だけの処理数は128.3ターンです。表4の会話単位の時間は、複数のやり取りの応答待ちを合計した値です。

### 調査タスクの役割別構成

LangGraphとGLM-4.7-Flashを使い、主担当と読み取り担当を別のH100で実行しました。両方をvLLMにした基準と比べ、BrowseComp-Plusの208問ではvLLMとH2Oで5.69時間から4.62時間（約1.23倍の速さ）になり、Judgeの正答率は46.15%から46.63%でした。DeepResearchBenchの100件ではOmniKVとH2Oで5.93時間から2.42時間（約2.45倍の速さ）になり、RACEは40.6%から41.1%でした。開発時に構成を探索した費用はこの時間に含みません。選んだタスクで品質の悪化を観測しなかった結果で、同等性を確認したわけではありません。

## Labの合成例

Labでは一度に一つだけ処理し、始めた要求に割り込みません。保存できる文脈は一つで、開始時にはAが入っています。時刻0にBとCが来て、Aは時刻0から30まで2秒ごとに16件届きます。キャッシュがあれば入力の処理は1秒、なければ6秒で、最初のトークンが出てから完了までは1秒と仮定します。実機の時間ではありません。

同じ18件を到着順、キャッシュ優先、キャッシュ優先に待機保護を加えた方式で処理します。待機保護では、次の処理を選ぶ時点で最も古い要求が8秒以上待っていれば、その要求を選びます。要求を選ぶ順序の規則であり、最初のトークンまでの締切ではありません。

上の通信図は、メッセージの受理と完了を別々に進められます。下の時間軸では要求を選ぶと、処理前のキャッシュ、最初のトークンが出た時刻、待機保護の適用を確認できます。時間軸はPythonで計算した値です。

## 合成例で変わった値

合成例のTTFTは、到着順で平均18.83秒・最大20秒、キャッシュ優先で平均5.50秒・最大45秒、待機保護付きで平均15.50秒・最大21秒でした。全要求が終わるまでの時間は順に51秒、46秒、51秒です。待機保護は、キャッシュ優先で生じた長い待ちを減らしましたが、全要求の完了は到着順の51秒と同じでした。キャッシュを再利用した要求は順に15件、16件、15件です。

## Labで確かめたこと

合成例では、同じ到着列の要求をそれぞれ一度だけ処理し、到着前に始めていないことを確かめました。キャッシュ優先では平均TTFTが短くても最大値が延び、待機保護を加えると古い要求の待ちが短くなる例です。確認したのは、再利用と待機保護の一部です（Mechanism PARTIAL）。

## 確認していないこと

実際のLLM、GPU、KV圧縮、通信の実装、4つのベンチマーク、本番運用は試していません。キャッシュの部分一致、複数GPU、非同期の状態更新、Session-Awareも再現していません。古い状態通知や障害時に正しく処理できるかは未検証です。著者が示す匿名のコード公開先は内容を確認できず、コードを実行していません。

## 配布コードの実行方法

配布した `run.py` を保存したフォルダで `python run.py` を実行します。標準ライブラリだけで動き、外部サービスへ接続せず、同じフォルダに `results.json` を保存します。リポジトリから実行する場合は次のコマンドを使います。

```bash
uv run --no-project papers/hear-harness-engine-serving-protocol/run.py
uv run paper-lab build
```
