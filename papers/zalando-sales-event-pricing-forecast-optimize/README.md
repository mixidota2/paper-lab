# セール価格の予測と実現利益を分けて読む

## Overview

Zalandoの研究チームは割引率ごとにセール中の販売数を予測し、その予測から商品ごとの割引率を選びました。割引率を決める計算には、セール中に売って得る利益だけでなく、在庫を残して後で売る場合に見込める利益も入れています。

研究チームは2023〜2024年に12市場でA/Bテストを23件行いました。商品をグループ単位で無作為に割り付け、システムが決めた割引と、従来どおり担当者が補正した割引を比較しました。23件を統合すると、利益への貢献額（PCII）は6.00%増えました（95%区間は0.79〜11.03%増）。一方、純売上（NMV）と返品後の販売数（SIAR）は区間が0をまたぎました。売上が対照と同等だったとまでは言えない結果です。

## Problem

Zalandoは通常期に、毎週Transformerで週ごとの需要を予測していた。従来のセールでは、担当者が既存システムの割引案を補正していた。セールは平均6.2日続き、セール日数は年間の約35%を占める。通常期と同じように毎週しか更新しないと、セール中の需要の変動に対応しにくい。割引で販売数を伸ばしても、今売った商品はあとで売れないため、残した在庫から見込める利益も変わる。

研究チームが選ぶのは商品ごとの価格であり、顧客ごとに価格を変える実験ではない。販売数は在庫を超えない。純売上を出すときは、返品に相当する分と付加価値税（VAT）を売上金額から除く。

## Core Idea

研究チームは市場と予測日ごとにLightGBMを使い、割引率を候補ごとに変えて日別の需要を予測した。モデルには、割引が大きいほど予測需要が減らない制約を入れた。価格を選ぶときは、日別の需要を足して在庫を上限とする販売数を求める。著者は、その販売数で見込める長期利益（LTP）に、純売上（NMV）に重みを掛けた額を足し、合計が最大になる割引率を商品ごとに選ぶ。

Labでは、需要の予測と、その予測から価格を選ぶ処理を分ける点を、Ferreiraら（2016、Rue La La）やCaro–Gallien（2012、Zara）の延長と捉えている。既存のZalandoの価格最適化（Liら2022、Streeckら2024）とは、商品どうしを結ぶ制約を外した点が違う。このため、商品を一つずつ採点して価格の候補を短時間で出せる。日次の運用と実地試験、どの誤差を測ってモデルを選んだかを同じ事例で追えることが、この論文の利点だ。

## Method

割引率を一つ決め、日別の予測需要をセール期間で足す。その合計が在庫Mより多いとき、売れる数はMまでとする。残る在庫の利益まで含め、商品ごとに次の順で計算する。

| 式 | 計算 | 意味 |
|---|---|---|
| (3) | s(d)=min(M, Σₜ Sᵗ(d)) | 予測需要と在庫のうち、小さい方を販売数にする |
| (4) | NMV(d)=(1−R)(1−d)Ps(d)/(1+VAT) | 返品率Rに相当する売上と、税を除いて純売上を求める |
| (5) | p(d)=NMV(d)−Cs(d) | 純売上から費用を引く |
| (7) | LTP(d)=p(d)+[M−s(d)(1−R)]γ | 残る在庫から見込める利益を足す |

γは残る在庫1単位から見込める将来利益で、著者は既存の週次システムから求める。

式(1)は各商品で argmax_d[LTP(d)+α NMV(d)]。候補ごとの点数を比べる計算なので、ある商品の割引が別の商品の需要を変える効果は含まない。式(2)の −NMV′(d)/LTP′(d)=1/α は、値を連続的に変えられ、目的関数を微分できる場合の限界条件だ。対話図では決められた割引率だけを使うので、選択は段階的に変わる。α=0で長期利益が同じ候補が並ぶ場合、純売上で同点を解消しなければ、同じ長期利益で純売上がさらに高い別の候補が残ることがある。このため、強いPareto効率性までは保証されない。

## Why It Might Work

著者がLightGBMを選んだ理由は、予測精度、学習時間、学習の安定性だ。Table 2で報告した学習時間はGBTが7時間、TSMixerが18時間、MLPが24時間だった。割引を大きくしても需要が減らない制約を置くと、逆向きの予測を避けられる。価格を選ぶ段階では商品別に採点できるため、著者は数時間かかっていた最適化を数分に短縮した。

αを変えた案を並べると、担当者は売上を増やす案と、残る在庫の利益を優先する案を比べられる。ただし、γを一定に置く設計では、将来の値付けを変えたときの利益までは更新しない。需要予測の誤差も残る。

過去に売れにくい商品ほど担当者が大きく割り引いていた場合、割引率と販売数を見ただけでは、商品がもとから売れにくかったのか、値下げで何個売れるようになったのかを分けにくい。過去に実施した価格で誤差が小さくても、試していない割引率で需要を正しく予測できるとは限らない。

## Evidence

一次資料である[原論文v1](https://arxiv.org/pdf/2606.13741v1)のTable 4には、11波で延べ6,204,627 articlesが記載されている。同じ商品が複数波に含まれ得るため、620万を重複のないSKU数とは扱わない。著者は事前の利益とNMVを揃えるよう、商品をまとまり単位で無作為に割り付けた。試験ごとに前後差を対照と比べる差の差で推定し、ベイズ階層モデルで試験を統合した。対照群は、人による判断と既存アルゴリズムを組み合わせた運用だった。

Table 5ではPCIIが+6.00% [0.79, 11.03]、NMVが+2.23% [−0.83, 5.33]、SIARが+0.56% [−3.10, 4.26]。ドイツ単独ではSIAR +16.7%、NMV +17.9%、PCII +16.7%だった。ドイツの結果を他市場にそのまま当てはめない。ある商品の値下げで代わりに売れる商品の数が変わるなら、無作為化をしても影響は残る。他の商品への介入が自分の結果を変えないというSUTVAの条件には懸念がある。

Table 2は212日分の予測を比較している。業務向けのDemand ErrorとGMV ErrorではGBTが最小、商品を均等に扱うRMSEとMAPEではMLPが最小だった。著者によると、LightGBMは速く安定して学習でき、ニューラルネットワークより設定を広く探索できた（§3）。Table 2の順位には、モデル構造だけでなく、試せた設定の違いも含まれる。

Demand Errorは、数量の誤差に値引き前の価格を反映する。式(9)では市場と日ごとに、商品の数量の二乗誤差を価格で重み付けして合計する。その値を、同じ価格で重み付けした実績数量の二乗和で割り、平方根を取る。低価格で少量の商品を多く改善したモデルと、売上の大きい商品の誤差を減らしたモデルでは、評価が変わり得る。

Table 3は実地試験ではなく、著者のシミュレーションだ。真の需要を知る比較条件（oracle）に対し、MSEで学習したモデルのPCIIは予測115.02%、実現93.07%だった。Tweedieでは予測94.21%、実現91.57%だった。予測値と実現値の差はTweedieの方が小さいが、実現PCIIはMSEの方が高い。

## Executable Understanding

対話図でαを上げ、純売上を重視すると、架空の3商品で選ばれる割引率がどう変わるか、在庫の上限に達するかを確認できる。LabはFig. 4をもとに、式(1)、(3)〜(7)で点を計算した。Zalandoの商品データは使っていない。図に出るのは加重和で選んだ候補で、離散候補のPareto境界をすべて列挙したものではない。

別の最小実験では、400商品×56日の価格弾力性を一定とした需要を作った。需要水準、弾力性、曜日効果、割引率を同じ入力とし、MSEとTweedieでLightGBMを別々に学習する。それぞれが選んだ割引率を、ノイズを含まない期待需要の表で評価する。seedは11、22、33。既知の弾力性をモデルに渡しているため、実データから価格の因果効果を推定できるかは検証していない。

## Results

Labでは、選んだ割引率から予測した利益と、その割引率を真の期待需要で評価し直した利益を別々に示す。比較の分母は、真の期待需要を知るoracleが同じγで割引率を選んだときの短期利益だ。Labの短期利益はZalandoのPCII会計定義を完全には再現していない。oracleが最大化するのは長期利益なので、短期利益で比べた値は100%を超える場合もある。

図はresults.jsonから3つのseedの結果を表示する。論文のTable 3に載る115.02%などを再現するようには調整していない。損失関数の選び方で実現利益が上がるかと、利益を正確に見積もれるかは別の問いだ。この小規模実験からTweedieが常に優れるとは言えない。

売上計画の承認に使うなら、実現利益の高さだけでは採用を決めにくい。次の3点も確認したい。

- 割引を選ぶ時点で見込んだ利益を、実現利益がどの程度下回るか。
- 在庫が十分な商品と、在庫が販売数の上限になる商品とで、誤差が違うか。
- 純売上の重みαを変えても、同じ傾向が残るか。

## What We Verified

CONFIRMED：Labは3つのseedで、割引を大きくしても需要予測が減らないこと、販売数が在庫を超えないこと、αを上げても選択した案のNMVが下がらないことをassertで確認した。式(3)〜(7)で利益を計算し、予測した利益と評価し直した利益を分けた。

PARTIAL：再現したのは、価格を決める計算の一部だ。市場と予測日ごとのモデルを分けず、週次モデルでγを求める処理も、過去の価格決定による交絡も含めていない。

## What We Did NOT Verify

NOT TESTED：Labでは、23件の実地試験、6%の利益改善、数百万商品の処理時間、本番での価格の因果効果を検証していない。非公開データも公式本番コードも使っていない。返品率と費用は固定し、需要の不確実性、ある商品の価格が別商品の販売に及ぼす効果、将来の在庫補充は扱わない。

## Implementation

リポジトリ直下で、次のコマンドを実行する。

```bash
UV_CACHE_DIR=/tmp/uv-zalando uv run --no-project papers/zalando-sales-event-pricing-forecast-optimize/run.py
```

必要なのはLightGBM 4.6.0とNumPy 2.2.6。run.pyはresults.jsonを書き出す。解説の編集元はlab.yamlとREADME.md、一次資料との対応はmapping.mdで、HTMLはこれらから生成する。次に検証するなら、過去の値付けをもとに価格を選ぶデータと、価格を無作為に割り付けるデータを比べる。商品の売れやすさと選ばれた価格の関係によって、最適化後の利益差がどれほど変わるかを調べたい。
