# 商品を探す段階と、結果を選ぶ段階

## 検索時に使う商品情報

IGPOは、検索要求に近い商品を埋め込みで探し、類似度がしきい値を超えた上位k件を取り出します。この予備検索をprobeと呼びます。IGPOは類似度の最大値・平均・標準偏差を求め、カテゴリごとに候補数、属性欄の種類、値が入っている割合を集計します。次に、過去に確認した検索範囲の不足や商品情報の変更をまとめたカテゴリ別の記録（scene profile）を加えます。著者はこの要約をinventory portraitと呼びます。これは予備検索で見えた情報であり、カタログ全体を調べた結果ではありません。

IGPOは、見つかったカテゴリと処理段に対応する規則を取り出し、検索要求との類似度が高い順に各段で最大3件を選びます。候補を探す段階では、検索をどの属性や経路から行うかを決めます。候補から結果を選ぶ段階では、得られた候補が要求に合うかを判断します。観測した候補に一致の根拠がないと判断すれば、商品を返しません。カタログに商品が存在しないと断定するわけではありません。

規則は特定の商品IDの存在を記憶しません。たとえば「タグ欄に値がほとんどなければ、値が入っている説明欄も検索する」と書けば、同じ規則を商品が入れ替わった後も使えます。モデルの重みと候補を探す仕組みは変えません。

## 過去の検索を再実行して規則を更新する

著者はある時点の商品カタログを固定し、同じ要求で5回検索します。判定役のDeepSeek-V3 671Bは、各試行を成功・失敗・不確実に分けます。失敗や不確実な結果が出た要求では、見落とした経路を最大10回の追加探索で探します。ただし、不確実な結果を失敗の証拠にはしません。同じ要求で成功と失敗が比較できたときにだけ規則の変更案を作ります。追加の探索でも分からなければ、その要求からは変更案を作りません。

著者は変更案のJSONの構造を確認し、元の規則と変更案で同じ検索を試し直します。直したい要求で結果が改善するか、以前は成功していた別の要求や固定の検証集合で、悪化が許容範囲に収まるかを確認します。個別に通過した案も、他の案と一つずつ組み合わせ、そのたびに検査します。組み合わせると条件を満たさない案は採用しません。この検査に通っても、未知の要求で結果が悪化しないとは限りません。

Labは、手で作ったケーキの商品情報と固定した規則だけでこの区別を説明します。埋め込み検索や言語モデルで規則を作る処理は実行していません。
