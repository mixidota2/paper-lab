# IGPO：商品カタログを検索時に調べる方法

## 概要

Huaweiの著者は、取り扱う商品が頻繁に変わるAI検索を改善しました。IGPOは検索のたびに商品候補を調べ、その情報を探し方や選び方の規則と一緒にモデルへ渡します。著者は過去の検索を試し直し、探し方を変えると商品が見つかる場合と、検索で確認できた商品情報からは該当候補が見つからない場合を分けて規則を整えました。モデルの重みは更新しません。

利用者を無作為に分けた14日間のA/Bテストで、著者はクリック率が相対で3.17%増え、監査した1,000件の検索では問題のある結果が38.9%減ったと報告しました。検索時に商品カタログを調べる処理と判断の規則を同時に加えたため、どちらがどれだけ改善に寄与したかはこの試験から分かりません。

## 見つからない場合の切り分け

「写真を印刷できるケーキ」が結果に出ないとき、商品カタログに該当商品がない場合もあれば、候補を探す段階で見落とした場合もあります。候補には入っていても、最後に別の商品を選んだり、何も返さなかったりすることもあります。商品カタログと、そこから取り出した候補と、最終結果を区別しないと、探し方の失敗を商品不在として覚えてしまいます。

原論文のinventoryは、検索対象の商品情報を指します。実店舗の棚や倉庫に何個残っているかは、この方法では調べません。

## 商品情報と判断規則

著者は、予備検索で見つかった候補やその類似度をカテゴリ別の記録と合わせ、候補を探す段階と選ぶ段階に別々の規則を渡します。モデルの重みや検索基盤は固定し、同じ検索を再実行して確かめた変更案だけを採用します。

検索結果に商品がないだけでは、商品カタログにもないとは言えません。著者は、同じ要求で見落とした検索経路を見つけられたときに成功と失敗を比べ、未解決の要求から商品不在を前提にした規則は作りません。

## 検索時の処理と事前の規則更新

## 検索時に使う商品情報

IGPOは、検索要求に近い商品を埋め込みで探し、類似度がしきい値を超えた上位k件を取り出します。この予備検索をprobeと呼びます。IGPOは類似度の最大値・平均・標準偏差を求め、カテゴリごとに候補数、属性欄の種類、値が入っている割合を集計します。次に、過去に確認した検索範囲の不足や商品情報の変更をまとめたカテゴリ別の記録（scene profile）を加えます。著者はこの要約をinventory portraitと呼びます。これは予備検索で見えた情報であり、カタログ全体を調べた結果ではありません。

IGPOは、見つかったカテゴリと処理段に対応する規則を取り出し、検索要求との類似度が高い順に各段で最大3件を選びます。候補を探す段階では、検索をどの属性や経路から行うかを決めます。候補から結果を選ぶ段階では、得られた候補が要求に合うかを判断します。観測した候補に一致の根拠がないと判断すれば、商品を返しません。カタログに商品が存在しないと断定するわけではありません。

規則は特定の商品IDの存在を記憶しません。たとえば「タグ欄に値がほとんどなければ、値が入っている説明欄も検索する」と書けば、同じ規則を商品が入れ替わった後も使えます。モデルの重みと候補を探す仕組みは変えません。

### 過去の検索を再実行して規則を更新する

著者はある時点の商品カタログを固定し、同じ要求で5回検索します。判定役のDeepSeek-V3 671Bは、各試行を成功・失敗・不確実に分けます。失敗や不確実な結果が出た要求では、見落とした経路を最大10回の追加探索で探します。ただし、不確実な結果を失敗の証拠にはしません。同じ要求で成功と失敗が比較できたときにだけ規則の変更案を作ります。追加の探索でも分からなければ、その要求からは変更案を作りません。

著者は変更案のJSONの構造を確認し、元の規則と変更案で同じ検索を試し直します。直したい要求で結果が改善するか、以前は成功していた別の要求や固定の検証集合で、悪化が許容範囲に収まるかを確認します。個別に通過した案も、他の案と一つずつ組み合わせ、そのたびに検査します。組み合わせると条件を満たさない案は採用しません。この検査に通っても、未知の要求で結果が悪化しないとは限りません。

Labは、手で作ったケーキの商品情報と固定した規則だけでこの区別を説明します。埋め込み検索や言語モデルで規則を作る処理は実行していません。

## 見落としを区別する理由

カタログの商品情報は変わりますが、どの属性を見て判断するかという規則は使い回せます。IGPOは商品情報を検索のたびに読み直し、商品を追加・削除したり属性名を変えたりしても、モデルを学習し直さずに対応することを目指します。ただし、限られた候補しか調べないため、見つからなかったことをカタログ全体に存在しない証拠にはできません。

著者は、該当商品があると分かっていたのに最初は見つけられなかった124件のうち、112件でオフラインでの3回の探索で検索経路を見つけました。別に、追加探索をしても未解決だった93件の要求とカタログの組を監査すると、13件は検索の見落としでした。分母が違う二つの集計であり、監査で見落としを確認できなかった残りを、すべて商品不在とは断定できません。

## 論文の評価結果

一次資料は[原論文v1の§4.1〜4.4、Table 1〜4](https://arxiv.org/pdf/2609.04813v1)です。最終テストでは、規則を検証した時点から4週間後の商品カタログを使い、3,000件の要求を評価しました。各方式の標準構成を1回ずつ実行した比較では、FNIが30.6%から4.8%に、FMが60.8%から15.2%に下がりました。

FNIは、カタログに該当商品がある要求のうち、システムが商品を一致として返さなかった割合です。FMは、カタログに該当商品がない要求のうち、商品を返して一致したと判断した割合です。該当商品があるのに別の商品を一致として返した誤りは、どちらにも数えません。たとえばウェディングケーキがあるのに写真入りケーキだけを返した場合、どちらの誤りにも数えません。正解の商品を返したかを調べる一致率やF1とは役割が異なります。著者が正解とした商品は、評価した方式の候補と本番の検索ログを専門家が確認した範囲に限られ、全カタログを網羅したものではありません。該当商品がない場合も、一致しないと明示して代替案を返すことは、誤一致に数えません。

関連する商品情報が更新された643件では、該当商品がある500件でFNIが8.2%、ない143件でFMが23.1%でした。影響がなかった要求では、それぞれ1,750件で3.8%、607件で13.3%でした。改名に該当する区分では、該当商品がない要求が0件のため、FMは算出できません。FMが0%という意味ではありません。

同じDeepSeek-V3を使い、規則の更新に使えるトークン数をそろえた比較では、1,800万トークンでF1@8がGEPA-styleの0.787±0.004に対し、IGPOは0.792±0.005でした。F1の差は小さく、この比較だけでは優位性を判断できません。同じ予算でのFMは、GEPA-styleの46.0%に対してIGPOは34.7%でした。1億2,000万トークンでは0.791±0.006に対し、0.817±0.004でした。値はそれぞれ3回の実行の平均と標本標準偏差です。

14日間の商用A/Bテストでは、利用者を50対50に無作為に割り付けました。対照群は100,400人、施策群は99,800人でした。クリック率は全体で相対3.17%上がりました（95%信頼区間：1.9〜4.5%）。各群から500件を抽出し、どちらの群か伏せて検索結果と当時のカタログを監査すると、問題のある結果は相対で38.9%減りました（95%信頼区間：25.2〜50.1%）。

該当商品がなかった要求に絞ると、問題のある結果は対照群45/128件、施策群14/125件で、割合は相対で68.1%下がりました。この区分では、商品を返さないことが正解になり得るため、クリック率は報告されていません。ほかの区分には改善幅の信頼区間が0をまたぐものもあります。A/Bでは予備検索と再実行で確認した規則を同時に導入したので、全体の差を二つに分けることはできません。

著者が報告した追加遅延は中央値49.4ミリ秒、95パーセンタイル185.8ミリ秒でした。入力は平均247.3トークン、95パーセンタイル568.2トークン増えました。モデルの重みを更新しなくても、規則の更新には検索の再実行、結果の判定、変更案の作成と検査が必要です。

## 図の操作

図では、手で用意した3種類のケーキと4件の検索要求を使います。タグ欄の情報を説明欄に移す、商品aを削除する、予備検索で商品cを見落とす、という条件を切り替えます。どの条件でもタグだけを調べる方式と、そのとき値が入っている属性欄を調べる方式を比べます。規則は変更しません。

正解にあたる商品は、検索の後で採点するときだけ参照します。最初の3条件では検索が全商品を参照し、最後の条件では商品cがカタログに残っていても検索からは見えないようにします。

## Labの人工例

正答数は、元の属性では2件から4件、属性を別の欄に移すと0件から4件、商品aを削除すると1件から4件になりました。商品cを予備検索が見落とす場合は2件から3件でした。該当商品がある3件のうち1件に何も返せず、FNIは33.3%でした。該当商品がカタログにないことと、検索から見えないことは異なります。

Labは別に、変更したい要求で結果が改善しても、以前は正しかった別の要求で悪化する変更案を試しました。この例では、過去の要求を再実行する簡略な検査で案を退けました。いずれも人工例であり、商用環境の性能は確認していません。

## 確認したこと

CONFIRMED（確認済み）：Labの固定した規則は、手で用意した条件の属性移動と商品削除に対応しました。商品cを見落とすと正解を返せず、別の要求を悪化させる規則案は簡略な検査を通りませんでした。

PARTIAL（一部確認）：Labで確認したのは、商品情報が変わったときの一部の判断と、予備検索の見落としの例です。IGPO全体は再現していません。

## 確認していないこと

NOT TESTED（未検証）：LabはDeepSeek-V3やQwen3-8Bを実行していません。埋め込み検索、規則の自動作成、言語モデルによる結果判定、商用環境でのA/Bテスト、応答時間も検証していません。この4件の検索から、実カタログでの正確さや、規模を広げたときの性能は判断できません。

## 結果の再生成

リポジトリの直下で次を実行すると、Pythonの標準ライブラリだけで `results.json` を作り直せます。

```bash
uv run papers/igpo-huawei-inventory-grounded-search/run.py
```

`portrait()` は、検索から見える商品のうち、各属性欄に値が入っている割合を計算します。`search()` は手書きの規則で調べる欄を選び、文字列が一致する商品を返します。`evaluate()` は検索とは別に正解を参照し、FNIとFMを計算します。`replay_gate()` は対象の要求が改善し、別の要求が悪化しなければ変更案を通します。原論文の付録Bにあるすべてのしきい値や、条件を変えた反復試行は含めていません。乱数や外部APIも使いません。
