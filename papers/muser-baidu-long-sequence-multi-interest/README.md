# MuSeRは古い行動をまとめて残し、直近は1件ずつ使う

Baiduなどの研究チームは、利用者一人あたり最大10万件の行動履歴を、推薦のたびに読み直さずに使う方法を提案しました。MuSeRは古い履歴ほど粗くまとめて事前に計算し、配信時は直近の行動と組み合わせます。履歴全体を一つのベクトルに平均する代わりに、複数の観点から履歴を読み、異なる関心に合う候補を探します。比較した設定の中では、履歴を6通りに読む構成が最もよい結果を出しました。ただし、それぞれが人の言葉で説明できる関心を表すとは限りません。

Baiduアプリのホーム画面では、順位付けなどの後段を変えずに候補を探す処理だけを入れ替え、数週間にわたって比較しました。著者によれば、1日の利用者数が0.26%、セッション時間の合計が0.89%増えました。一方、ログを使った別の比較では、履歴を圧縮すると正解を上位500件に含む割合（Recall@500）は、圧縮しない場合の0.2351から0.2232に下がりました。これは本番での改善率ではなく、計算を減らすときに候補をどれだけ取りこぼすかの比較です。

## 昔の履歴をどこまで残せるか

Labは古い行動を細かく残す代わりに足し合わせると、入力個数と、保存できる情報がどう変わるかを人工例で比べる。論文の推薦モデルを学習させた実験ではない。

## 教材の計算を実行する

リポジトリの最上位から実行すると、スクリプトと同じフォルダーの `results.json` を更新する。

```bash
uv run papers/muser-baidu-long-sequence-multi-interest/run.py
```

コードはPythonの標準ライブラリだけを使う。コードと結果だけを取得した場合は、そのフォルダーで `uv run run.py` を実行する。

## 各ファイルで確認できること

`lab.yaml` は記事と図の定義、[方法](method.md)は履歴の圧縮と関心の取り出し方、`run.py` と `results.json` は人工実験と結果を収める。[対応表](mapping.md)には、原論文の箇所と、Labで試していない処理を記した。`uv run paper-lab build` で公開ページを作る。

Labは、合計が保たれてもグループ内の順序が消えることや、全位置を比べる場合の組数を人工例で確かめた（Mechanism: PARTIAL）。実運用の性能、規模を増やした場合の挙動、本番適用は検証していない（NOT TESTED）。CONFIRMEDは個別の計算についての判定で、著者の本番結果を再現したわけではない。
