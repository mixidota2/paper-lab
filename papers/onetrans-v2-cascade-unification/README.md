# OneTrans-V2の3段階と、履歴の計算を使い回す方法

検索で候補を集め、粗い順位付けで候補を減らし、最後に詳しい情報で順番を決めます。OneTrans-V2は、この3段階で同じTransformerを使います。ただし、商品候補に関わる計算まで全段階で同じにするわけではありません。

## 概要

OneTrans-V2は、推薦候補を探す段階、粗く順位を付ける段階、精密に順位を付ける段階を残しながら、3段階を同じTransformerで学習します。候補によらない利用者の情報は一度計算して共有します。一方、候補の特徴や学習の目的は段階ごとに異なります。

著者は利用者を無作為に分け、新しいモデルと配信の仕組みで3段階すべてを置き換えた場合を、段階ごとに別のモデルを使う従来方式と比べました。利用者当たりの流通取引額（GMV）は9.74%増えました。新しい仕組み全体の比較なので、計算の共有だけでどれだけ増えたかは分かりません。

## 著者が比べたもの

| 何を測ったか | 著者の結果 | 比較した条件 |
| --- | --- | --- |
| 検索の1位に正解がある割合（HR@1） | OneTrans-GRの0.0545に対し、小型のV2Sは0.0660、大型のV2Lは0.0923 | 過去データを使った検索の評価（表2） |
| 1要求で行う演算の量 | 3モデルを使う従来方式の合計は275 GFLOPs、V2Sは239、V2Lは662 | 表2の演算量。毎秒処理できる要求の数とは別 |
| 利用者当たりの流通取引額（GMV）と活動日数 | GMVは9.74%増、活動日数は0.25%増 | 利用者を無作為に半分ずつ分け、V2Lと配信の仕組みで3段階全部を置き換えた比較（§6.3） |
| 毎秒処理を終えた要求の数（QPS） | 3.2倍 | 同じハードウェア予算で、3段階すべての処理が済んだ要求を数える（§6.3） |

§7.9で著者は、段階ごとの配信を先に最適化し、さらに履歴計算を3段階で共有したときに、全体の処理件数が1.53倍になったと報告しています。3.2倍は、履歴の共有だけを切り出した数字ではありません。同じ節にある4.4倍は、学習時に同じ利用者への複数の表示で履歴計算を共有した結果です。

検索のDCGRだけを評価した別の試験では、従来方式の主な検索経路に比べてGMVが48.0%増えました。商品を見せた回数は69.3%増え、1,000回当たりのGMVは13.0%減りました。検索経路だけの比較なので、推薦全体の利用者当たりGMVが9.74%増えた試験とは分けて読みます。

## 教材を動かす

このフォルダーで `uv run --no-project python run.py` を実行すると、Pythonの標準ライブラリだけで計算し、同じフォルダーの `results.json` に保存します。

教材では、同じ3候補を使います。βが0なら確率で最も有力なAが先頭になり、βを1にするとB、2にするとCが先頭になります。候補は途中で捨てず、3件すべての得点を計算します。

履歴の計算量を100、後続3段階を10、20、30と仮定すると、履歴を3回計算する場合は360、共有した場合は160です。この比は教材の仮定から出た値です。著者が本番の配信で測った3.2倍を再現していません。

## 資料の読み方

`method.md` では3段階の仕事と目的ごとに候補を生成する式、学習時の履歴の共有を説明します。`mapping.md` では、論文のどこを教材で扱ったかを確認できます。`lab.yaml` は記事と図、`run.py` は教材の計算、`results.json` は計算結果です。

学習時のSNTは、各表示より後の行動を読み込まないようにします。表示より後の行動を隠しても、施策の効果を推定することにはなりません。

この教材は、著者のモデル学習、GPUを使った配信、実際の利用者に対する評価を行っていません。
