# PushDualGenは動画のコードを先に出し、文面は必要なときに作る

Qwen3-0.6Bは動画を表すコードを先に生成し、必要なら通知文を続けて出す。本番の推薦では上位20件のコードを既存の利用者の表現と組み合わせて動画を探す。

優先度：Watch。Labは2026年9月21日に一次資料を確認した。

## 実行

リポジトリの最上位で最初のコマンドを実行すると人工実験の結果を更新する。次のコマンドでLabのページを作る。

```sh
uv run papers/pushdualgen-kuaishou/run.py
uv run paper-lab build
```

## 概要

KuaishouのPushDualGenは、利用者の行動履歴などから、まず通知に向く動画の特徴を表すコード（SID）を生成します。そのコードに続けて、必要に応じて文面も生成する仕組みです。本番では上位のコードを既存の利用者特徴と組み合わせ、その情報を使って似た特徴を持つ動画を検索します。通知やアプリのおすすめ欄を、生成モデルだけで作る仕組みではありません。

著者は14日間、サービスのトラフィックの計15%を二群に等分し、従来の通知推薦と比べました。通知をクリックした後の指標では、一定条件を満たす再生の割合が64.46%から69.94%へ上がり、低評価の割合は0.053%から0.033%へ下がりました。対照群に対する相対変化はそれぞれ8.50%増、37.70%減です。比較したのは推薦方式全体で、文面生成だけの効果ではありません。

## 課題

通知がクリックされても、利用者が動画を見続けるとは限らない。長い行動履歴を文章で入力し、動画候補を決める前に説明まで生成すると、候補を探すのに必要な処理が増える。一方、通知のクリック履歴だけでは、アプリ内の閲覧やコメントなどの好みは捉えきれない。著者は、生成した動画のコードを単独で使わず、既存の利用者の特徴に加えた。

## 中核アイデア

著者は、動画を短いコードで表し、利用者の履歴をもとに先にコードを生成する方式を提案した。その後で必要な場合だけ文面を生成する。推薦の処理は、コードの情報を既存の利用者の特徴に加え、近い動画を検索する。

別の研究との違いは、候補を探すための利用者表現を変える点だ。LIGE-GRが変えるのは、集めた候補から一覧を並べる処理だ。

## 仕組みが働く理由

モデルが動画のコードを先に確定するなら、文面を出す必要がないときにそこで止められる。学習では文面の損失も使い、コードを言葉と結び付ける手掛かりにできる。ただし、生成した文面を読んでも、モデルがその動画を選んだ理由を証明できるわけではない。既存の利用者の表現と組み合わせることで、通知のクリック履歴以外の行動も残せる。

## 著者が報告した比較結果

一次資料：[原論文の§4、表1–2](https://arxiv.org/html/2608.07989v1)。

著者はサービスのトラフィックの計15%を二群に等分し、約1億5,000万人を含む14日間の比較を行った。試験前の指標で差を調整するCUPEDを使い、表1の4指標でp<0.05と報告した。

| 指標 | 従来方式 | PushDualGen | 相対差 |
| --- | ---: | ---: | ---: |
| 通知のクリック回数（Click PV） | 82.04M | 82.39M | +0.43% |
| 日次の利用指標（DAU） | 414.89M | 415.08M | +0.05% |
| クリック後の有効再生率 | 64.46% | 69.94% | +8.50% |
| クリック後の低評価率 | 0.053% | 0.033% | −37.70% |

有効再生率は5.48パーセントポイント上がった。低評価率の37.70%減は、対照群の低評価率を基準にした相対差だ。不満をすべて測った値ではない。また、表のDAUと、試験に割り当てた約1億5,000万人の集計範囲の関係は本文だけでは確認できないため、人数の差に換算しない。

表2のPass@20は、独立に生成した20件のコードに正解が含まれる割合を示す。完全構成は0.422、コードと言葉を結び付ける事前の適応を外した条件は0.366、動画を個別の部品に分けて量子化する方式を外した条件は0.401だった。これらはオフラインでコードの予測を比べた結果だ。本番で文面の生成だけを省いたときの効果は報告していない。

## 人工実験

Labは人工の行動履歴から、頻度が最も高い動画のコードを選び、その後に文面を出すか切り替える。別の人工例では3本の動画を用意し、既存の利用者の特徴だけを使う場合と、コードの特徴を加える場合で、内積の順位を比較する。モデルの学習や通知文の品質を測った例ではない。

## 結果

この欄はLabの人工実験の結果だ。著者のA/Bテストとは、使ったデータも測った指標も異なる。

## 確認した範囲

**仕組みの検証：一部のみ（Mechanism: PARTIAL）**。Labは2種類の履歴で、同じ方法で先にコードを確定すると、文面を出しても省いてもコードが変わらないことを確かめた。固定したベクトルの例では、コードの表現を足すと動画の順位が変わった。出力の回数は文字単位で数えたもので、実行時間は測っていない。

## 確認していない範囲

**実運用での性能・規模を増やした場合の挙動・本番適用：未検証（NOT TESTED）**。LabはOmniの圧縮学習、各ベクトルのK-means、Qwen3の適応と微調整、近似検索の再現率、文面の忠実性、通知の頻度制御、A/Bテストを再現していない。

原論文の§6は、文面からコードを生成する逆方向の使い方も調べる。これは文面を生成する前にコードを出す、§3.2の推薦用の順序とは別だ。

## 実装

`decode()` はログの頻度でコードを決めた後に文面を選ぶ。`rank(beta)` は式7の組み合わせを使い、全候補の内積を計算する。近似探索用のインデックスは使っていない。

実験コードはPythonの標準ライブラリだけを用いる。値を固定しているため乱数は使わない。結果はコードと同じフォルダーに保存する。
