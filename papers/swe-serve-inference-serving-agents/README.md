# SWE-Serve: Benchmarking Agentic Engineering For Production Inference Serving

SGLangの53課題で、局所的に動く変更がサーバー全体でも動くかを測る。E2E対象19課題では、同じパッチの採点からE2Eを外すと成功率が45.9%から69.4%へ上がった。

## Overview

SGLangの53課題で、局所的に動く変更がサーバー全体でも動くかを測る。E2E対象19課題では、同じパッチの採点からE2Eを外すと成功率が45.9%から69.4%へ上がった。

## Problem

モデル対応、デコード、キャッシュ、分散実行、APIの変更は複数の境界をまたぐ。個別関数が正しくても、設定の伝播や状態の共有を誤ればユーザーのリクエストは失敗する。

## Core Idea

著者の主張：著者は、推論配信の実装を機能・回帰・E2E・性能制約で評価するSWE-Serveを提案した。E2E検査を外したときの差は23.4ポイントと報告している。

Labの解釈：変更した関数のテストに加え、公開APIからモデル実行まで到達するテストが必要だと読める。53課題の合格は運用準備全体や保守性の保証ではない。

各課題を指定コミットのコンテナで実行し、未変更のno-opが落ち、参照実装のoracleが通ることを確かめる。隠された機能テストと回帰テストに、対象課題ではE2Eと性能条件を加える。外部の解答を取得できないclosed-book環境で評価する。

## Why It Might Work

【解釈】同じパッチのまま採点項目だけを外すと、モデル生成の変動と検査の違いを分離できる。ただしテストを減らせば一般に合格率は上がる。論文は12課題で同数・同種の非E2Eテスト除去とも比較し、E2E除去による新規合格が2.0倍と報告した。

最初に確かめたいのは、手元の単体テストが通る変更について、公開APIから渡した設定がモデル実行へ届くか、以前の要求の状態が次の要求へ漏れないか、複数要求を同時に処理しても仕様を保てるかを、それぞれ独立したテストで説明できるかという点だ。

## Executable Understanding

小さな配信サービスの4種類のパッチを固定し、直接関数の検査、公開API経路、連続リクエストの状態検査を実行する。検査を1群ずつ追加して同じパッチの合格数を比べる。実際のSGLang、HTTPサーバー、LLMは使わない。

入力はalpha、次にbetaだ。期待値は各入力そのものになる。まずlocal-onlyを見る。decodeを直接呼ぶとalphaが返る。局所検査は通る。しかしrequestは空文字を返す。APIへの配線漏れだ。state-leakはどうか。初回は通る。2回目はalpha betaになる。前の要求が混ざった。completeだけが3群を通過する。

この実験で問うのは、同じコード変更について、関数を直接呼ぶ検査、利用者から到達する入口を通る検査、別の要求を続けて処理する検査を順に足したとき、どの不具合が初めて見えるかという検査範囲の違いである。

## Results

4パッチ中、局所検査は3件、API経路を加えると2件、状態検査まで加えると1件が合格した。局所検査だけで通る2件は、APIへの配線漏れと状態の混入を残していた。

## What We Verified

CONFIRMED：同じパッチでもAPI経路と状態検査を加えると局所テストの見逃しを検出した。PARTIAL：検証境界の考え方のみを再現した。

## What We Did NOT Verify

NOT TESTED：53課題、H100でのモデル配信、性能ゲート、11モデルの成功率、ハーネス比較。合成4件から論文の23.4ポイントを再現したとは主張しない。
