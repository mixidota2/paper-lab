### 履歴を読む計算を候補生成と順位付けで共有する

Gryphon-v2の共有エンコーダーは、利用者の行動履歴Hᵤを読み、状態列Eᵤを作る。著者の構成は双方向エンコーダー7層、生成デコーダー2層、順位付け部（Ranking Module）1層、隠れ幅1024、全体で0.5Bパラメーター。配信モデルは最大2,048件の行動を読み、教師は最大8,000件を読む。教師は学習時だけ使うので、配信時に教師用の履歴を計算することはない。

デコーダーはカタログ内にあるSIDだけを生成するため、途中までのIDをまとめた木（trie）を参照する。配信時はビーム探索で1,024個のSIDを出し、それぞれを対応する曲へ展開する。同じSIDに複数の曲が対応する場合は、その曲を一つのグループとして扱う。上限の1,200曲を超えたら、生成確率の低いSIDから、そのグループごと除く。曲数の上限が1,200だからといって、常に1,200曲が残るわけではない。

```text
pθ(σ|u) = ∏ᵦ pθ(sᵦ | s<ᵦ, Eᵤ)
Iᵤ = ∪σ∈retained beam { i : Φ(i)=σ }
eᵢ = Encodeitem(item ID, SID prefix n-grams)
ranking heads = RankingModule(Eᵤ, eᵢ)
```

順位付け部は各曲のIDと、SIDの先頭を構成する部分列をmulti-hash embeddingで表す。その曲をQueryにして共有履歴を参照し、タスクごとの点数を出す。最終順位は教師と同じ固定の組み合わせで決める。組み合わせの具体的な重みは、確認した本文にはない。生成確率は候補の採否に、順位付け部の点数は残った曲の並びに使う。候補から外れた曲を順位付け部が戻すことはできない。[一次資料：§3・§5.1](https://arxiv.org/html/2608.06213)

### 学習では2種類の候補を同じ教師で採点する

Gᵤは、学習の各ステップで現在のデコーダーが生成した候補。Mᵤは、同じ要求のログに表示された曲。両方を同じ教師が採点し、配信モデルの順位付け部は、その点数を予測する。表示ログの反応を、順位付け部に直接正解として渡す方法ではない。r̂ᵗは配信モデル、rT,ᵗは教師の点数、Tは順位付けタスクの集合を表す。

```text
Lroll = (1/|T|) Σₜ (1/|Gᵤ|) Σᵢ∈Gᵤ |r̂ᵗᵤᵢ − rT,ᵗᵤᵢ|
Limpr = (1/|T|) Σₜ (1/|Mᵤ|) Σᵢ∈Mᵤ |r̂ᵗᵤᵢ − rT,ᵗᵤᵢ|
L = LNTP + Lroll + Limpr
```

この式は、候補源ごとに平均絶対誤差を計算し、二つの平均を係数1で足す。著者が報告した「重複を除いた候補の90%超を生成候補が占める」は、どの候補を学習に使ったかの数字だ。損失の比率が90対10という意味ではない。

たとえば生成候補が10曲、表示ログの候補が2曲で、共通する曲が1つあれば、全部で11曲になる。1タスクの式では、生成候補だけにある1曲の絶対誤差に掛かる係数は1/10、表示ログだけにある曲は1/2。両方にある曲は二つの平均に入るため1/10＋1/2になる。これは式の意味を示す例で、論文の本番ログにこの構成があったことを示すものではない。

LNTPは、ログの正例のSIDをトークンごとに予測する損失だ。NTPはデコーダーと共有エンコーダーを、蒸留は順位付け部と共有エンコーダーを更新する。ビーム探索を通じて勾配を流したり、方策勾配でデコーダーを更新したりする方法ではない。[一次資料：§3.6〜3.7・付録A](https://arxiv.org/html/2608.06213)
