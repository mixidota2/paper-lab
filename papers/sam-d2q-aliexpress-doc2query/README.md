# SAM-D2Q: Aligning Multimodal Doc2Query with Search Demand and Conversion for E-commerce

AliExpressの研究チームは、商品名にない言葉で検索しても、意図に合う商品を候補に入れる方法を提案しました。SAM-D2Qは、商品画像と商品名を読んで、その商品を探すときに使われそうな言葉を生成します。検索を受ける前にその言葉を既存の検索索引へ加えるため、検索のたびに生成モデルを動かす方式ではありません。

本番トラフィックの4%を使った21日間のA/Bテストで、著者は従来方式より決済件数が2.27%、成約率が0.53%増えたと報告しました。この二つはサービスの95%水準の確認を通過しています。取引総額の3.38%増は、増減の方向を示す値で、有意差を確認した結果ではありません。また、論文に書かれた実験の時期は、学習用の重みを決めたログの収集時期より前で、本文だけではこの時系列を確定できません。

## 商品名にない語を補う

短い商品名には、色、袖の長さ、柄などが書かれていないことがある。商品名だけから追加する語を考えると、画像と合わない語を足したり、画像にある特徴を見落としたりする。商品に合う語でも、利用者がほとんど検索しない語なら、検索から購入につながる効果は限られる。

## 商品名と画像から検索語を作る

著者はQwen3-VL-8Bに商品名と画像を入力して検索語を生成する。最初に検索語と商品の対応を学び、次に商品名の視覚属性を隠して画像から補う練習をする。最後に検索語と商品の関連性、検索需要と購入の見込み、視覚属性を報酬として学習する。

Labの見方では、SAM-D2Qは既存の検索で商品にたどり着ける語を増やす。商品コード（SID）を生成して直接検索する方式へ置き換えるのではなく、全語一致の検索、利用者の検索語を書き換える処理、ほかの候補取得経路と併用する。

## 語を加えると候補が変わる理由

すべての検索語を含む商品だけを候補にする場合、商品名にある語を繰り返したり並べ替えたりしても候補は増えない。画像で裏付けられる新しい語なら、その語で検索した利用者に商品が届く。一方で、商品と合わない人気語を索引に入れると誤取得も増える。そのため、著者は商業価値だけでなく商品の関連性でも検索語を評価する。

導入を判断するときは、検索語の商業価値を近似した学習報酬、固定した評価モデルで測る関連商品の数、無作為に割り付けた本番テストでの決済件数を分けて確認したい。前の段階の指標が上がっても、次の段階で同じだけ改善するとは限らない。索引が増えた分の費用も比較に含める。

## 論文が報告した評価

### オフラインでは上位3,000候補に入る関連商品を比べた

著者は880万商品と3万件の検索語を使い、商品名だけ、テキスト版のDoc2Query、SAM-D2Qの完全構成を比較した。表1の上位3,000件では、固定した関連性モデルが関連ありと判定した商品数の平均は、順に454.5件、558.0件、594.1件だった。関連性モデルの判定は、人がテスト対象の商品をすべて評価した結果ではない。表2のQuery-Valueも学習報酬に近い評価値であり、独立して測った事業成果とは分けて読む。

### 本番では既存の検索に索引を追加した

著者の報告では、対照群にもCPVによる属性の追加、カテゴリ辞書、同義語、検索語を書き換える処理、ほかの候補取得経路があった。処置群では、その構成を残したままSAM-D2Qで作った索引を足した。本番トラフィックの4%を使った21日間のテストで、決済件数は+2.27%、成約率は+0.53%、取引総額は+3.38%、クリック率は+0.25%だった。決済件数と成約率はサービスの95%水準の確認を通過した。他の指標は方向を示す値として報告され、信頼区間の幅は示されていない。

索引サイズは約35%増え、候補取得のP99の所要時間は0.2%増えた。検索時に生成モデルは動かないが、索引を作り、保存する負担は残る。検索結果が0件だった検索PVの割合は2.07%から1.72%に下がった。差は0.35ポイント、元の値に対して約17%減だ。

### 論文に記載された日付

A/Bテストの日付は2025年6月8〜28日、商業価値の重みを求めるためのログの収集時期は2025年8〜11月と書かれている。テスト時に使った重みの版や、二つの記述の関係は本文だけでは確かめられない。

## Labの小実験

Labは3商品の単語集合を用意し、タイトルだけ、手で用意した候補を全部足す場合、商品に合う候補だけを足す場合を比べた。コードは商品を1件ずつ調べ、検索語のすべての単語がその商品の集合に含まれるときだけ返す。全語一致の結果を示す実験で、転置索引そのものや、検索速度を再現する実験ではない。追加する語と、商品に合うかどうかは人が決めた。

商品aの名前は「summer shirt」で、検索「red shirt」のredが足りない。「red short sleeve shirt」を索引に載せる語の例として加えると、商品aが候補に入る。商品aに「leather bag」まで加えると、バッグの検索にもシャツが出る。商品に合わない追加候補だけを除くと、その誤取得は消え、関連するバッグの商品cは残る。

全語一致は、まとまった語句の一致とは異なる。仮に「red leather bag」で検索すると、別々の追加候補の単語を合わせて全語がそろうため、すべての候補を追加した場合は商品aが返る。個々の追加候補には「red」「leather」「bag」をすべて含むものはない。この追加例は、個々の検索語句を保存して一致を調べる実装ではないことを示す。

3種類の検索語で、商品名だけでは関連商品を取得できなかった。候補を無条件で足すと関連商品を3件取得し、誤取得が1件生じた。商品に合う候補だけを足すと関連3件は残り、誤取得は0件になった。商品ごとに追加された語の数を合計すると、無条件の場合は7件、候補を確認した場合は5件だった。

Labは、検索方法を同じにしても、各商品に加える語によって候補が変わることを確かめた。人工データでは商品に合わない語を除くと、関連商品を減らさずに誤取得が減った。確認したのは全語一致での語の追加の効果に限る。

Labは画像の理解、CPVで作ったデータによる学習の効果、GRPO、学習用の関連性モデル、880万商品の規模、本番での取引総額を再現していない。候補と判定を人が決めた例から、学習済みモデルの性能や索引の速度は分からない。

## 実行

リポジトリのルートで `UV_CACHE_DIR=/tmp/uv-cache uv run papers/sam-d2q-aliexpress-doc2query/run.py` を実行する。Python標準ライブラリだけを使い、商品に付けた単語で検索した結果を `results.json` に保存する。
