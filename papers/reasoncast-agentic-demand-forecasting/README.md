# ReasonCast: Agentic Demand Forecasting with Selective Semantic Reasoning

## 概要

ReasonCastは、祝日やセールの情報を需要予測に反映するかどうかを、その都度決める方法です。Chronos-2 smallで出した予測をそのまま使うか、手元のイベント情報で補正するか、検索や時系列を調べるツールも使って補正するかを選びます。予測の土台となるChronos-2 smallの重みは変えません。

公開データM5のイベント前後では、誤差の指標WMAPEが多変量データで追加学習したChronos-2 smallの33.10%に対し、ReasonCastは32.63%でした。一方、著者が調べた平常日の販売データでは、常に補正するとWMAPEが7.91%から9.59%に悪化しました。補正するかを選ぶ方法では補正を見送り、元の7.91%を保ちました。どちらも過去のデータに対する予測の比較で、在庫や発注の改善は測っていません。

## 何を変える方法か

Qwen3-32Bは、元の予測とイベントの情報から、補正しないか、手元の情報で補正するか、追加の情報を調べて補正するかを選ぶ。Chronos-2 smallが数値を予測する。補正する場合は、イベントに合わせて売上の推移と水準を調整する。

Labが注目したのは、補正を選ばなければ元の予測を必ず残す点だ。販促の予定と欠品の記録を使って導入を判断するなら、売上と買いたかった数量を分け、同じ情報で予測した場合の誤差と、発注した場合の費用を別々に比べる必要がある。

## 予測の課題

売上の履歴だけでは、今年の祝日や大型セールで売上がどう変わるかを読み取りにくい。逆に平常日では、関係のない出来事を加えることで予測の誤差が大きくなる場合がある。著者は、イベントを使うかどうかと、使うときにどれだけ予測を変えるかを分けて決めた。

独自データは、最も細かい商品カテゴリごとの日次売上15,696系列である。一つの商品を一店舗で売った数ではない。著者は予測を出す時点までに分かっていた情報で、その後7日間を予測した。

## 著者の評価

著者は独自データで、2025年8月末までを学習、9〜10月をモデル選択、11月から2026年5月までを評価に使った。評価は各7日間の15区間で、祝日10、大型セール3、平常期2を含む。公開データM5では、10店舗を合計した3,049商品系列で、イベント前後の7日間を14区間調べた。

WMAPEは、観測ごとの予測誤差を絶対値にして足し、実績の絶対値の合計で割った値だ。以下の差はパーセントポイントであり、誤差の相対変化率ではない。

| 評価した区間 | 比較対象 | ReasonCast | 誤差の差 |
| --- | --- | --- | --- |
| 祝日の影響が大きいカテゴリ | 売上の履歴で追加学習したChronos-2 small（Uni-FT）：42.39% | 39.10% | −3.29ポイント |
| 大型セールの影響が大きいカテゴリ | 追加情報も使って学習したChronos-2 small（Multi-FT）：22.14% | 20.89% | −1.25ポイント |
| M5のイベント前後 | 追加情報も使って学習したChronos-2 small（Multi-FT）：33.10% | 32.63% | −0.47ポイント |
| 独自データの平常期 | 追加学習なしのChronos-2 small：7.91% | 7.91%（補正なし） | 0ポイント |

平常期で補正を強制すると、誤差は7.91%から9.59%へ1.68ポイント悪化した。別の試験でイベント説明の内容を逆にすると、15区間のうち13区間で悪化した。著者が評価したのは与えられた販売データに対する予測で、在庫や欠品を減らせたかは測っていない。[一次資料：初版 §5.2、表2・3、§5.8](https://arxiv.org/html/2608.15291v1)

## Qwen3-32Bが補正の方法を選び、Chronos-2が売上を予測する

ReasonCastは、Chronos-2 smallで売上の履歴から最初の予測を出します。Qwen3-32Bは、その予測、予測の不確かさ、祝日やセールの記録を読んで、補正が必要かを判断します。Skipなら数値は変えません。Basicなら手元の情報を使います。Toolなら検索や時系列の統計も調べます。祝日と大型セールでは、著者の設計上Skipを選べません。

補正に使う情報には、どのイベントが関係するか、需要が増えるか減るか、変化がいつ始まりどのように続くか、振れ幅、ピークなどが含まれます。著者はまず、Claude Opus 4.6が作った例で、決められた形式で答えるようQwen3-32Bを学習させました。次に、催しの影響を表す項目を採点して強化学習しました。そのモデルで作り直したデータを使って、イベント情報と数値の予測をつなぐ処理を学習します。最後に予測器の重みを固定し、予測誤差がどれだけ変わったかを採点に使って、経路の選び方とイベントの説明を学習しました。[一次資料：初版 図1、§4.2・4.7、付録B](https://arxiv.org/html/2608.15291v1)

## 日ごとの形と全体の水準を、別の処理で調整する

予測器の内部表現 `H` を、イベントを参照する成分 `Hᴱ = HP` と、それ以外の成分 `Hᴺ = H(I−P)` に分けます。著者はQR分解で得た直交基底 `Q` を使い、直交射影 `P = QQᵀ` を作ります。式6の二つの成分を足すと元の `H` に戻ります。イベントに対応する成分だけがテキストを参照し、式8ではその結果を `H̃ = Hᴺ + Hᴱ + mαgΔH` として予測器の内部へ加えます。注意機構の出力を投影し直すわけではなく、影響が同じ部分空間にとどまるという意味ではありません。

式11では、予測器が数値を出したあと、指数で計算した倍率を掛けます（`ŷ = ŷ_lat ⊙ exp(mβgρ)`）。これで大きな水準の変化を扱います。二つの補正は、テキストを使うかを示す `m` と、個別の予測ごとに補正の強さを決める `g` を参照します。Skipでは `m=0` なので、加算は0、倍率は1です。式12では元の予測をそのまま得られます。[一次資料：初版 §4.3〜4.6](https://arxiv.org/html/2608.15291v1)

## 今回の7日比較と原論文の境界

Labの画面では、補正が数字に与える影響だけを確かめます。元の予測を `b`、足す値を `a`、倍率の対数を `l`、補正の強さを `g` とし、日ごとに `(b + g*a) * exp(g*l)` を計算します。論文の[式8](https://arxiv.org/html/2608.15291v1#S4.SS3)はモデルの内部に値を足しますが、教材は出力に直接足します。[式11](https://arxiv.org/html/2608.15291v1#S4.SS5)と式12も、倍率と補正なしの違いを学ぶために簡単にしたものです。

実績 `y` は誤差を測るときだけ使います。Skipを選ぶと、補正の式を通さず元の予測をコピーします。Labでは祝日の例でもSkipを選べますが、論文の方法にはその選択肢がありません。以前の固定例に出てくるBasicとToolにも、モデルや検索を動かす部分はありません。

### 予測をどう採点するか

WMAPEは、日ごとの絶対誤差の総和を、実績の合計で割って100を掛けた値です（論文の式16）。Labで入力できる実績は0以上です。過大予測と過小予測は相殺しません。元の予測から何ポイント変わったかを表示し、差が負なら誤差は小さくなりました。実績が全部ゼロならWMAPEは定義できないため、保存時に `null` とします。実績がゼロでも、絶対誤差の平均（MAE）は実績合計で割らないため表示します。

元の予測が毎日10、実績が毎日20の場合、補正なしでは50%、2倍の補正を強さ1で使うと0%、強さ0.5なら約29.289322%です。実績が毎日10なら、同じ2倍の補正で0%から100%に悪化します。また、3日目に実績が増えた例で補正を4日目にずらすと、誤差は12.5%から25%に増えます。以前の固定例では、実績が動かないときにBasicを使うと0%から20%に増える条件もあります。

### 入力と計算結果の扱い

画面は7日分でない配列、数値として扱えない値や無限大、負の実績、0から1を外れた補正の強さを受け付けません。配列はカンマ・読点・空白で区切れますが、連続する区切りや末尾のカンマでできる空欄は0にせず、入力を求めます。

計算結果の行は独立しています。指数の値が大きすぎて計算できなかった行は「計算不能」とし、その曲線を描きません。他の行は残るため、最大の強さで補正する行が計算できなくても、Skipの元予測は変わりません。どれかの行に負の予測があれば、画面に警告を出します。元の予測も確認の対象で、負の値を0に直しません。

## Labで確かめたこと

Labの計算を別に求めた値と比べ、誤差、半分の強さで使った補正、間違った情報、イベント日のずれを確認した。実績がすべてゼロの場合や、補正後が負になる場合、不正な入力も区別した。Skipでは補正の演算を通さない。確認したのはこの教材の計算で、論文全体の仕組みは一部のみ（PARTIAL）。画面、キー操作、書き出しは、この計算の検査では確認していない。

LabはChronos-2とQwen3-32Bを動かさず、検索、経路を選ぶ学習、直交射影、強化学習も再現していない。欠品で売上が買いたかった数量を下回る場合、販促の費用、品切れを防げる割合も評価していない。モデルの性能、件数を増やしたときの動作、本番での有用性は未検証（NOT TESTED）。

## 自分で同じ計算を試す

このフォルダーで `uv run run.py` を実行すると、Pythonの標準ライブラリだけで同じ `results.json` を生成できます。保存した入力を使うなら `uv run run.py --input comparison.json` を実行します。結果は標準出力に表示されます。Webページでは入力を変えるとその場で再計算し、JSONを保存できます。

リポジトリのルートで `uv run --extra dev pytest tests/test_reference_comparisons.py` を実行すると、定めた入力と誤差の規約を検査できます。Node.js 18以上がある場合は、`uv run --extra dev python tests/check_reference_js.py` でJavaScriptの値を独立した期待値と照合し、PythonとJavaScriptを120条件で比べられます。

上の検査は計算を調べるもので、画面操作は含みません。サンドボックスが使えるChromeで幅360 pxと1,440 pxの画面、キー入力、保存と読み直しを検査する場合は、`CHROME_PATH` と必要に応じて `REFERENCE_SITE` を指定し、`uv run --with playwright tests/reference_browser.py` を実行します。この検査は127.0.0.1に一時的なHTTPサーバーを立て、終わったら閉じます。ファイルを直接ブラウザーで開く検査とは別です。

## 保存ファイルから、計算に使ったコードを確かめる

`implementation` は計算に使うコードの識別情報です。サイトを作るときに、`model.js`、`interactive.js`、`run.py` のSHA-256を計算し、`implementation.json` と `implementation.js` に保存します。これら二つの生成ファイル自身は計算対象ではありません。ブラウザーで書き出したJSONの識別情報と、配布ファイルに対する `sha256sum model.js interactive.js run.py` を比べられます。

Pythonの `pack()` は、実行した `run.py` のハッシュを保存します。生成手順を経ずにJavaScriptモデルだけを直接使った場合は `status: unavailable` になります。ハッシュはコードの内容を見分けるための値で、署名や公開コミットの証明ではありません。コミットしていない変更もハッシュに反映されます。以前のJSONを読み込んでも以前のコードは動かず、再保存時には現在の識別情報、原論文の版、入力、教材の仕様バージョンが入ります。
