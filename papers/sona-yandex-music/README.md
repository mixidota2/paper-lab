# Sona：Yandex Musicは候補検索と曲の順位付けをどうまとめたか

## 論文の概要

Yandex Musicの研究チームは、自動で曲を流すMy Vibeで、候補を探す処理、候補を絞る処理、最後に並べ替える処理を一つのモデルにまとめました。Sonaは、利用者が聴いた曲や曲への反応を手掛かりに候補を作り、同じモデルの中で曲に点数を付けます。採点部は訓練中に別の教師モデルの点数を学びますが、最終構成では曲を選ぶときに教師を動かしません。配信できる曲を制限する既存のルールは維持しました。

スマートスピーカーでMy Vibeを使う人を対象に、著者は利用者を各群15%ずつ無作為に選び、Sonaを従来方式と7日間比べました。Sonaの群では、対照群よりも主指標のActive Usersが4.53%、総再生時間が6.30%増えました。著者は全利用者に展開しておらず、推薦に現れる曲の範囲も従来方式より狭いと報告しています。この試験ではSonaの最終構成をまとめて試したので、個々の変更がどれだけ効いたかは分かりません。

## 研究チームが変えたこと

音楽では、同じ曲を繰り返し聴くことが利用者の望みである場合もある。動画と同じように重複を抑えればよいとは限らない。また、次に再生されそうな曲を当てるだけでは、好みの曲や長く聴いてもらえる曲を上に並べられるとは限らない。著者は、大きい教師モデルをリクエストのたびに動かさず、軽い採点部にその点数を学ばせた。

## 論文の実験

### 音楽を流すスマートスピーカーの本番比較

最終の実験では、著者はスマートスピーカーでMy Vibeを使う利用者を各群15%ずつ無作為に選び、従来方式とSonaを7日間比べた。対照群に比べ、主指標のActive Usersが4.53%、総再生時間が6.30%、いいねが11.42%、リピートの指示が17.99%、論文でDeeply Engaged Usersと呼ぶ利用者の指標が7.37%増えた（表7.12、著者の報告ではいずれもp<0.01）。論文の§7.5には、Active UsersやDeeply Engaged Usersに含める条件の記載はない。ここでいう「利用者数」は実験のActive Usersで、登録者全体や長期の継続率ではない。リピートの指示は、利用者が繰り返し再生を指示した回数で、曲が一覧に重複する割合とは違う。



実験4では、教師を配信時に動かさず、教師から学んだ採点部を使った群のActive Usersが、その実験の対照群より1.41%増えた。実験5と改善幅には3.12ポイントの差がある。ただし、別の実験であり、履歴の長さだけを変えて直接比べた結果ではない。論文の2.35倍も、Sonaの4.53%と過去のArgusの1.93%という改善幅の比であり、利用者数やモデル精度の比ではない。Gryphon-v2の記事では、教師から学んだ採点部を使う構成を説明している。

### 長い履歴と、履歴を圧縮する処理をログで比べる

Teacher Recall@10では、採点部と教師が同じ生成候補に点を付け、双方の上位10曲に共通する曲の数を10で割る。著者はその値をリクエストごとに求めて平均した。上位の曲が同じ順番に並ぶ必要はない。表7.6では、表示された候補だけで採点部を学んだ場合に0.2983、生成候補も使った場合に0.5654だった。

一方、Target-track Recall@1000では、正解曲があるリクエストごとに、上位1,000曲に入った正解曲の割合を求めて平均する。正解曲が1,000曲を超える場合は、分母を1,000にする。この値は表示候補だけで学ぶと0.8663、生成候補も使うと0.8615だった。教師と同じ曲を上位に選ぶことと、ログ上の正解曲を探せることは別だ。

表7.7では、約2,000件の履歴を使い、採点部なしではTeacher Recall@10が0.0381、採点部を4層にすると0.6005だった。約8,000件をすべて同じように処理すると0.6586、古い履歴の計算を減らした構成では0.6474だった。重み付きのペア精度（WPA）は圧縮あり0.6033、なし0.6029で、全指標で同じ順になるわけではない。[一次資料：§7、表7.6〜7.12](https://arxiv.org/html/2608.11015v2)

## 合成例を実行する

```sh
uv run papers/sona-yandex-music/run.py
```

Labは、人が決めた式で候補に点を付ける教師と、その点を学ぶ線形モデルを用意した。表示された候補だけを使う、生成した候補だけを使う、両方から別々に平均を求めて足す、の三つを比べる。学習に使っていない生成候補120件を採点する。

MAEは教師と学習したモデルの点数の差を絶対値にして平均したものだ。ペア精度は、候補を二つずつ選び、教師と学習したモデルが同じ向きに厳密な順位を付けた割合である。同点は一致に含めない。履歴を読む計算については項の数だけを数えた。論文が報告した「約半分の推論費用」を測り直したものではない。

## 合成例の結果

生成候補と表示候補の両方を学ぶと、合成例のペア精度は1.0だった。表示候補だけで学ぶと約0.791だった。一方、点数の誤差（MAE）は、生成候補だけを使った場合より両方を使った場合のほうが大きい。Labでは、表示候補側の一つの特徴が常に0になり、その特徴の係数を学べないようにした。実際の配信ログにも同じ特徴があるという意味ではない。

## Labで確認できること

Labは、教師と学習するモデルを変えずに候補の集め方を変えると、未使用の候補で順位が一致する割合が変わることを確かめた（Mechanism: PARTIAL）。二種類の候補の誤差は、論文§4.2に合わせて別々に平均して足した。乱数の初期値と学習回数は同じにした。

## Labで確認していないこと

LabはTransformer、Qwenでの内容表現、残差量子化、生成と採点で共有する学習、同じIDに割り当てられる実際の曲の数を検証していない。配信中のモデルが中央値45分で更新される処理も再現していない（NOT TESTED）。数カ月の効果、スマートスピーカー以外の推薦、推薦に出る曲の範囲を広げられるかは論文でも未解決である。
