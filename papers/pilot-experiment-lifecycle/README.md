# PILOT：推薦実験の観察・候補選び・成果の記録

## 概要

Taobaoの著者は、推薦設定を試す仕事を三つの役に分けるPILOTを提案しました。提案役は試す設定を考え、進行役は設定を変えるか観察を続けるかを決め、記録役は実験結果を整理します。安全上の制約、統計による判定基準、実行できる操作は、プログラムが管理します。

著者は利用者を五つの実験グループに分け、従来のエージェント方式ROAMとPILOTを別々の時期に試しました。それぞれの方式で最も結果が良かったグループでは、共通の基準に比べて商品詳細ページへの訪問数が、ROAMで1.00%、PILOTで1.40%増えました。著者は別の評価として、目標を上回ったか、測定が安定したか、次に試す設定の探索が前進したかも、五つのグループそれぞれで確かめました。全グループを通じた三条件の達成割合は、ROAMの53.3%からPILOTの93.3%に上がりました。この比較から、進行役と提案役の効果を個別に見積もることはできません。

## 推薦設定をいつ変えるか

指標が悪化するたびに推薦設定を変えると、どの設定で結果が出たか分からなくなります。一方、悪化がなければ設定を変えない方式では、改善の候補を試さずに期間が終わることがあります。PILOTは次の候補だけでなく、観察を終える条件、配信前に別のデータで確認すること、次の実験に残す結果も扱います。

利用者ごとの推薦をその場で制御するDREAM、実行基盤の設定を見直すCORAL、改善コードを作るAgentXとは、管理する範囲が異なります。比較対象のROAMもエージェント方式なので、人とLLMの比較ではありません。

## 提案・運用・記録の役割

### 誰が提案し、誰が実験を動かすか

進行役（Experiment Manager）は実験を受け付け、測定、異常への対応、終了後の振り返りを進めます。提案役（Search Planner）は進行役から依頼されたときに候補を作ります。観察期間や配信量を変えたり、候補を採用したりする権限はありません。記録役（Memory Curator）は終了した実験の結果を整理します。この保存に失敗しても、すでに確定した実験の結論は変わりません。採用したLLMの具体的な版や規模は、確認した本文では明記されていません。

実験を始める前に、目的、指標、予算、観察期間、使える特徴量・戦略、操作権限を決めます。仕様は未記入の項目を確認し、実行できる段階を経て固定します。運用の手順書も固定します。安全・統計の規則、実験の仕様、手順書、承認された過去の方法、暫定の手掛かり、LLMの推論の順に優先します。過去の結果から学んだ記憶が上位の規則を書き換えることはありません。

進行役が使える操作をManager Guardが列挙します。状態を書き換えるのはState Committerで、統計的な判定記録を出すのはStatistics Engineです。Contract Builderは観測前に判定の基準を定めます。Action Enumeratorが選んでよい操作を挙げ、Candidate Validatorが候補の適合性を確認します（§3.1、表2）。LLMの提案と、規則を強制する処理を分ける設計です。

### 観察を終える条件と配信の条件

進行役は、データが新しいか、値が確定しているか、サンプルが十分か、利用者の割り当てに異常がないかを調べます。観察を閉じる判断には、効果が上向きか下向きかを見せません。偶然と疑われる異常は診断用に記録して観察を延長し、繰り返す異常や許容範囲を超える異常は停止して人に戻します（§3.2）。

各回では、観察を続ける、候補を退ける、候補を採用して次の比較相手にする、のいずれかを選びます。候補を退けた場合は現在の比較相手が変わりません。勝った候補を採用しても、目標達成後の段階的な配信拡大と、別のデータで行う独立確認を経てから配信を確定します。ある運用期間に人が介入しなかったことは、操作権限や事前の承認がなかったという意味ではありません。

### 誰にどの設定を適用するか

PolicyTreeは、利用者を条件で分け、各分岐の末端に推薦設定の組を割り当てます。利用者は施策の前に分かる登録済みの特徴量で分けます。施策によって変わった行動で事後的に群を分けないためです。特徴量がない場合の扱いも定め、すべての利用者を1つの末端に振り分けます。木の深さ、末端の数、各末端が含む利用者の最低割合、特徴量数、実験回数、配信量に制約があります。

実験を通して変えない固定基準T₀は、全体の効果を測る相手です。Champion T*はその時点で確認済みの木で、次の候補の効果を測る相手です。ChallengerはChampionに登録済みの操作を1種類だけ加えた候補です。操作には分岐の追加・刈り込み、ハッシュによる分割、分岐の統合、推薦設定の更新の5種類があります。Δtotalは固定基準との差、Δstepは現在のChampionとの差です。

ROAMもLLMを使う方式です。初回ページと追加読み込みのそれぞれで、クリック率、商品詳細ページへの訪問、購入への転換、取引金額に対応する4つずつ、計8つの値を全体へ一律に適用します。PILOTは同じ基本設定を利用者の群ごとに変えられる木にし、確認時点、最低限の調整回数、事前に登録する仮説や判定基準も加えました。前後比較では運用と探索範囲の両方が変わっています。

### 一つの実験の結果を、別の実験で確かめる

記録役は、どの設定がどの利用者群で別の設定を上回ったかという記録と、どんな状況でどの実験手順が適したかという記録を分けます。実験が終わるまで個別の記憶に保存し、その後に出典、適用範囲、既存の記録との矛盾を照合します。同じ実験で統計的に強い結果が出ても、新しい主張は下書き（draft）から始まります。

同じ範囲で別の実験が結果を支持すると、裏付けあり（supported）となり、暫定の手掛かりに使えます。規定の件数を満たし、重大な反証が未解決でなければ承認済み（approved）となり、候補の優先づけなどに使えます。同じ実験の記録を複製しても独立した証拠にはなりません。支持と反証は両方残し、対立が解消できるかを定めた手順で調べます。結論が出なかった結果は、反証とは別です。この知識が安全規則より優先されることはありません。

Labは1つの主張への観測を順に保存します。反証が来ると、その時点の状態にとどまります。すでに承認済みなら取り消さず、あとから支持が増えても昇格を再開しません。支持の履歴と独立した支持数は増えます。承認に必要な独立した支持3件は教材の設定で、原論文の固定値ではありません。矛盾する記録の解消や置き換えは実装していません。

## 論文の前後比較

[一次資料（原論文v1）](https://arxiv.org/html/2608.18637v1)の§6では、Taobaoホーム画面「Guess You Like」の5つの実験グループを対象に、ROAMの7日間とPILOTの最初の5日間を報告しました（図8）。商品詳細ページへの訪問数（IPV）の最良グループは、共通の固定基準に対して+1.00%から+1.40%に変わりました。Core IPVは+0.90%から+1.60%、取引金額は+1.13%から+1.50%です。+1.00%と+1.40%の差は0.40ポイントで、全利用者の訪問数が40%増えたという結果ではありません。

表7の5日目では、IPVが最大のグループ23で、IPVは+1.40%、Core IPVは+1.60%、取引数は+0.95%、取引金額は+1.50%でした。取引数の最大+0.96%はグループ25で、グループ21の取引数は−0.13%です。論文の総括は各指標の最大値を並べており、すべてが同じグループの値ではありません。

表9の探索条件の達成率（Search Efficiency）は、5グループそれぞれで、目標を上回った、再設定1回以下で測定が安定した、探索が前進した、の3条件を数えます。ROAMは1+4+3=8件、PILOTは4+5+5=14件です。分母は5×3=15で、53.3%から93.3%へ40ポイント上がりました。計算速度や、提案1件あたりの成功率ではありません。期間中の目標超過はPILOTで4グループでしたが、表7の5日目の値だけでは3グループです。著者はその後も続け、7日間の目標を達成したと報告しました。

この比較は、同じ時期に利用者を無作為に割り付けた比較ではありません。進行方法と設定の探索範囲が同時に変わりました。進行役と提案役をそれぞれ使うかどうかの2×2比較（表8）は計画だけで、実施していません。各操作の測定結果を比較できるように調整することなどが、計画を実施する前提です。今回の結果から、各役だけを追加した効果は分かりません。

## 観察条件と利用者の群を分ける理由

先に判定条件を決めておけば、良く見える日だけを選んで観察を終えることを防げます。同じ実験の記録を別々の証拠として数えないことで、一度の結果を何度も確認したように扱わずに済みます。

利用者群ごとに設定を変えると、全体の平均に隠れた違いを試せます。一方、細かく分けるほど群ごとのデータが減り、効果を見分けにくくなります。論文の設計では各分岐の最低割合や実験の予算を定めています。

## Labで変えられる条件

Labの図は、外から与えたイベントとデータの健全性・承認・独立確認に対して、状態がどう変わるかを表示します。データが健全でなければ停止します。データが健全で状態が `observe` のとき、`promote` を渡すと `confirm` に進みます。この分岐は承認や独立確認を読みません。承認を調べるのは開始（`launch`）と配信（`deliver`）、独立確認を調べるのは配信だけです。配布JSONの「証明済みのpromote」は、あらかじめ付けたケース名です。Labは証明書を発行せず、その内容も検証しません。

もう一つの図は、同じ実験Aの記録を10回保存する場合と、別々の実験A・B・Cが支持する場合を比べます。結論が出なかった結果は反証に数えません。反証が来るとその時点の状態にとどまり、承認済みでも取り消しません。後から支持が来れば履歴と件数には加えますが、昇格は止まったままです。独立した支持3件で承認する条件はLabが決めました。

## 人工例での結果

承認なしでは開始せず、データの異常があると停止します。健全と入力して `promote` を渡した例では確認へ進み、配信には承認と独立確認の両方が必要です。

同じ実験Aからの支持を10回保存しても、独立した支持は1件です。人工の10人を施策の前に定めた特徴量で分けると、3人が個別設定、7人が既定の設定になります。特徴量がない人も既定の設定です。これらの結果は、著者のオンライン指標ではありません。

## 確認したこと

Labは、開始と配信の承認、配信の独立確認、同じ実験を重複して数えないことを人工の入力で確かめました。配布JSONで `CONFIRMED` としたのは、その欄にある個別の条件だけです。

## 確認していないこと

Labは候補をLLMに作らせていません。逐次検定、多重比較の補正、利用者の割り当て比率の異常（SRM）の検出、実際の配信量と承認の管理も実装していません。木に対する5種類の操作全体や、記録同士の対立を解消して置き換える処理は対象外です。人工例から商品詳細ページへの訪問が増えることや、本番運用の安全性は分かりません。

## 手元での再実行

配布の `run.py` を `python run.py` で実行すると、標準ライブラリだけで人工例を計算し、隣に `results.json` を保存します。外部APIやモデルは使いません。操作図は計算済みの結果を表示し、ブラウザで統計量を推定しません。

一次資料と書誌に取得できる公式実装の案内は確認できませんでした。配布コードは公式実装を移植したものではありません。
