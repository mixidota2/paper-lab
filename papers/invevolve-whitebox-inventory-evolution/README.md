# InvEvolve：発注コードの探索と配備の条件

## Overview

InvEvolveは人が読める発注コードを作る方法です。著者は大規模言語モデルにコードを書かせ、シミュレーションで費用を比べながら修正しました。発注ルールを選んだ後は、そのコードが商品ごとの発注量を計算します。

著者は学習に使っていない人工データの30条件を使い、条件ごとに費用が最も低い従来方式と比べました。その方式より費用が低かったのは、InvEvolveでは25件、ルールを選び直す処理を加える前の言語モデルでは13件でした。Dunnhumbyの販売履歴を使った比較でも、InvEvolveは30件中20件で条件ごとの最良の従来方式より費用を抑えました。著者は販売履歴から需要を復元してシミュレーションを行っており、実際の店舗で発注を変えたわけではありません。

## 欠品と需要の変化

この論文は、欠品したときに満たせなかった需要を翌日に持ち越さず、売り逃す在庫管理を扱います。従来の発注ルールは人が計算を追えますが、販促や季節性をどう使うかは人が設計する必要があります。言語モデルに発注コードを書かせても、過去の需要に合わせすぎたり、将来の需要が過去と変わったりする問題は残ります。

## 発注コードの候補と比較相手

著者は、学習した言語モデルで発注コードを提案し、全候補を同じ需要経路で実行して費用を比べます。探索中の最良方策を入れ替えるときは、候補が固定の参照方策と現在の最良方策の両方に対する条件を満たすかを確かめます。配備時は固定の参照方策だけを比較相手にして、改善の信頼下限で候補を絞ります。その中から信頼上限が最も大きい候補を選び、条件を満たす候補がなければ参照方策を使います。

InvEvolveが書き換えるのは発注コードです。期間ごとに方策を探索しますが、運用中の発注量は採用したコードが計算します。発注のたびに言語モデルに数量を尋ねるわけではありません。[SabreAgent](../sabreagent-design-time-inventory/README.md)では、言語モデルが設計時に季節性の事前分布を作り、運用時には固定した数理最適化が発注量を決めます。

## 発注コードの学習、探索、配備

著者はGLM-4.7-FlashをGRPOで学習させます。モデルが書いた発注コードを実行し、最良の従来方式より費用が低ければ報酬を1、それ以外を0とします。学習したモデルは、探索時に発注量そのものではなく、発注量を計算するコードの候補を書きます。

探索では、同じ需要経路で候補ごとの在庫と費用を計算し直します。探索中に最良として扱う方策を入れ替えるには、候補が二つの条件を満たす必要があります。固定の参照方策に対する改善の信頼下限が `ξ` 以上で、現在の最良方策に対する改善の信頼下限が `ε+ξ` 以上であることです。入れ替えに至らなくても、形式上有効で評価済みのコードは、配備候補を選ぶときの比較に残り得ます。

配備時は、固定の参照方策に対する改善の信頼下限が `ξ` 以上の候補を残し、その中から、同じ参照方策に対する信頼上限が最も大きい方策を選びます。通過する候補がなければ、固定の参照方策を使います。探索中の入れ替え条件と、配備時の選び方は異なります。

Labでは、論文が探索で見つけたTilted-CBSとTilted-PICの式を使います。Tilted-CBSは在庫不足が大きいほど発注上限を引き上げ、Tilted-PICは不足に掛ける係数でも発注量を変えます。Labが実行するのは、固定した係数で発注量と費用差を計算するところまでです。言語モデルの学習、候補の生成、探索中の方策の入れ替えは行いません。

## 信頼区間を使った判断

同じ需要経路で候補と比較相手を動かし、比較相手の費用から候補の費用を引いた値を改善量 Z とします。Z が正なら、その経路では候補の方が低費用です。原論文の式7・8は、改善量の平均を中心に、次の半幅で信頼区間を作ります。

```text
rad = B sqrt(2 log(2N/δ) / m)
LCB = mean(Z) − rad; UCB = mean(Z) + rad
```

B は改善量の絶対値の上限、N は比較数の上限、m は候補間で共通に使う需要経路の本数です。δ は期間ごとに許す判定の失敗確率で、比較数の上限 N が大きいほど区間は広がります。ξ はシミュレーションと配備先の需要分布の違いによって、改善量が悪化し得る幅です。探索中の入れ替えには、固定した参照方策に対する信頼下限（LCB）が ξ 以上、現在の最良方策に対するLCBが ε+ξ 以上という二つの条件があります。ε は入れ替えに求める改善幅です。

配備時は、参照方策に対するLCBが ξ 以上の候補だけを残し、同じ参照方策に対する信頼上限（UCB）が最も大きいものを選びます。探索中に昇格しなかった候補でも、形式上有効で評価を済ませていれば比較の対象になり得ます。保証は、同じデータで候補を順次選ぶ状況でも信頼区間が有効であることと、シミュレーションと配備時の改善量の差が ξ に収まることを前提とします。良い方策を見つける側の保証には、探索が候補を十分に調べることも必要です。付録Eの ξ の調整や、付録Fの少ないデータ向けのt分布による計算は、前提がいつでも成立することを示す証明ではありません。

## 在庫不足から発注量を求める式

IP は手元の在庫と入荷予定の合計、S は目標在庫です。Δ は目標に足りない量、q は発注量を表します。CBSは発注量の上限を r に固定します。Tilted-CBSは同じ基準の上限から始め、不足量に α を掛けた分だけ上限を引き上げます。Tilted-PICは不足量に Kp を掛け、丸めてから上限を適用します。

```text
Δ = max(0, S − IP)
CBS:        q = min(Δ, r)
Tilted-CBS: q = min(Δ, r_base + αΔ)
Tilted-PIC: q = max(0, min(round(Kp Δ), r_base + αΔ))
```

図では α と Kp の組み合わせを選び、同じ不足量で各方式が何個発注するかを見比べます。基準の上限が同じなら、α=0 のTilted-CBSはCBSと同じです。不足が整数で Kp=1 なら、Tilted-PICとTilted-CBSも同じ発注量になります。不足に端数があると、丸めで切り上がった発注量が不足量を上回ることがあります。

## 人工需要での計算結果

Labは、0〜10個の整数需要が同じ確率で出る60日分の需要を、乱数の種930で256経路作りました。どの方式にも同じ需要を与え、入荷まで3日、目標在庫24、基準の発注上限4、在庫1個の保管費1、売り逃し1個の費用9としました。係数を固定したときの1日あたりの平均費用は、CBSが12.402、Tilted-CBSが9.501、Tilted-PICが10.037でした。

Tilted-PICでは、不足が0.875個のときに0.65を掛けてから四捨五入すると、発注量が1個になり、在庫と入荷予定の合計は24.125個になります。丸めで増えるのは最大0.5個で、0.65を掛けた時点では不足量より小さいため、この3方式の計算では合計が24.5個を超えません。在庫が残る日と売り逃しが出る日は重ならず、最大需要は10個なので、1日の費用は90以下です。信頼区間の計算では余裕を持たせて B=114 を使います。この上限は3方式の設定に対するもので、図の全設定を対象にしていません。

B=114 で求めた区間の半幅は21.093でした。参照CBSに対する改善の信頼下限は、Tilted-CBSが−18.191、Tilted-PICが−18.728です。平均費用は下がりましたが、不確実性を差し引いた信頼下限で判定すると、ξ=0 でも両案は条件を満たしません。参照CBS自体の改善量は0で、切り替えは行いません。

## Labで確かめたこと

CONFIRMED（確認済み）：基準の上限が同じなら α=0 でCBSとTilted-CBSが一致し、整数の不足と Kp=1 ならTilted-CBSとTilted-PICが一致しました。Labは指定した設定内で費用に上限があることを確認し、同じ需要経路に対する改善量の平均と信頼区間を計算しました。

PARTIAL（一部確認）：Labは発注式と、固定した参照方策に対する判定だけを確かめました。二つの新しい方策は採用条件を満たしませんでした（NOT OBSERVED）。

## Labで確かめていないこと

NOT TESTED（未検証）：LabはGRPOでの学習、発注コードの生成、探索中の最良方策の入れ替えを行っていません。需要分布の差を見込む ξ の推定、少ないデータ向けのt分布による信頼区間、CJデータの需要復元、96条件での係数の再探索も検証していません。人工需要での費用差から、論文の勝率、規模を広げた性能、実運用での安全性は判断できません。

```bash
UV_CACHE_DIR=/tmp/uv-cache uv run --no-project papers/invevolve-whitebox-inventory-evolution/run.py
```

`run.py` は、その日の入荷を受け取り、発注量を決めてから、需要に応じて在庫を減らします。Labの人工結果と論文の集計は、`results.json` の別の項目に保存し、図表はこのファイルから生成します。Labは非負の値を四捨五入します。原論文の実装で端数をどう扱うかは確認していません。
