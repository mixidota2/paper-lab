# ReuseGR：検索語の計算を共有し、履歴は検索ごとに使う

著者は生成検索の処理を、検索語が同じなら事前に共有できる部分と、利用者の現在の行動履歴に合わせる部分に分けました。大きなモデルが商品コード（SID）の先頭を用意し、小さなモデルが検索時に残りを補います。事前準備がなければ、別の小さなモデルがその場で全層を生成します。

準備済みの44,225件の検索語で、上位100件に正解SIDが一つでも入る割合は、従来の小さなモデルの81.99%から85.82%になりました。平均処理時間は117.00msから71.45msです。これは準備済みの条件での比較です。実際の検索で準備済みと未準備が混ざるときの値は、別に扱います。

一次資料：[著者論文第1版](https://arxiv.org/html/2611.04259v1)。著者のHTMLの§3〜5、式3、表1・5、付録A・C・D・Eを読みました。PDFの全画像、公式実装、商用ログは確認していません。

## PythonとJavaScriptの入力は同じ範囲にそろえる

Pythonの `toy(prepared=True, depth=1, query='wide', history='left', budget=4)` とJavaScriptの `ReuseGR.toy(...)` は、同じ種類の値を受け取ります。

- `prepared` は真偽値です。 `depth` は0〜3の整数、`budget` は0〜8の整数です。整数の欄では、真偽値、文字列、配列、null、NaN、Infinity、範囲外の値を拒否します。
- `query` は `wide` または `narrow`、`history` は `left` または `right` です。 `projection(p)` は0〜1の有限な数だけを受け取ります。

両言語の結果はこの入力範囲で照合します。候補の木は16個の葉に固定し、任意の配列を入れる仕組みはありません。空の候補集合で平均を取ることもありません。枝を0本に制限したときに順位表が空になるのは想定どおりです。入力が無効なら例外を返し、NaNをJSONのnullに置き換えて保存しません。出力のJSONにある条件から計算し直せます。準備済みの深さ0と未準備の経路は、候補の値が同じ場合も別に表示します。

## 論文の数値とLabで確かめたことを区別する

Qは準備済みの検索語が占める種類数の割合です。Pは準備済み検索が占めるログ行の割合です。HRは検索語ごとに一つでも正解を拾えたかを集計し、Recallは検索語ごとに正解全体のうち何件取れたかを求めます。端点をPで混ぜた値は推計で、同じ実験で測った値ではありません。

著者は準備済みの経路で、7Bモデルが最も高く評価した粗いコードを使って履歴を絞っています。比較方式と未準備の経路では、ログの検索語と一致する履歴を使います。ほかの処理も一緒に変わっているため、差のすべてを先頭部分の共有の効果とはみなしません。商用ログは非公開で、LLMを使う最近の二塔型モデルとの比較はありません。検索語がないフィードにそのまま適用できるかも未検証です。

Labで確認したのは、入力の範囲、処理経路、候補が残る条件、採点と選択の順序、著者が報告した数値の算術です。著者の学習や推論、速度、規模を大きくした挙動、本番での効果は再現していません。Nodeで画面の要素を模したテストは、本物のブラウザや端末での表示・保存の確認ではありません。

## 保存が始まらないとき

「合成条件と投影をJSON保存」を押すと、ファイルと同じJSONが読み取り専用の欄にも表示されます。ダウンロードが始まらなければ、その欄からコピーできます。画面の案内は、端末が保存を終えたことを確認するものではありません。

条件を変えたとき、値が無効になったとき、初期条件に戻したときは、以前の結果を取り違えないよう欄と案内を消します。入力した条件やJSONは外部へ送りません。画面のテストは、保存に失敗した場合や連続で保存した場合、条件変更とリセットを扱いますが、端末が本当にファイルを書いたかまでは確認しません。
