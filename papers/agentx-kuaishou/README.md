# AgentX：推薦の改善案を発案から本番評価まで進める

## 概要

KuaishouのAgentXは、推薦の改善案を作るところから、本番の比較結果を次の案に生かすところまでを支援します。エージェントが過去の実験から案を出し、審査を通った案の実装と検証を進める仕組みです。本番では主指標だけでなく、悪化を避けたい指標も確認します。人は案の審査や導入判断に関わり、採用しなかった実験の結果も次の検討に残ります。

著者が3ワーカーを3週間運用したところ、374案のうち10件が本番導入の候補になりました。1ワーカー・1週あたりで比べると、同時に進めた実験数は従来の人手の運用の8倍で、アプリ利用時間の累積増加率は約3.7倍でした。一方、案ごとの本番展開率は人手のほうが高く、同じ案を人とエージェントに無作為に割り付けた比較でもありません。

## 発案だけでは実験が増えない理由

推薦の案を増やしても、実装や試運転が滞ったり、実験に使える利用者の割り当てが決まらなかったりすると、本番で試せません。AgentXは案の発案から実装、観測、判定までを複数の案で並行して進めます。変更するのは本番コード、推薦のルールを書くための言語（DSL）、戦略の設定です。会話で利用者に推薦を返す仕組みではありません。

案を何件試せたかと、1案あたりどれだけ本番に進んだかは別の指標です。人があらかじめ選んだ案と、エージェントが出した案を比べるときは、選び方の違いも残ります。

## 論文の手順

### 改善案を発案・実装・評価する

発案では、エージェントが過去の実験、システムの構成、データ分析、外部研究を調べて仮説を立てます。変更できる内容か、既存案と重ならないかを確かめ、人が案を審査します。実装ではリポジトリの規約と依存関係に従って変更を作り、コンパイルと試運転で本番実験を始められるかを確認します。評価では段階的に配信し、必要な日数のA/Bテストを観測します（§4〜6）。

KEEPには、主指標の効果が基準以上であり、統計的に有意で、副作用を監視する指標（guardrail）が許容範囲にあることが必要です。重大な悪化があれば採用せず、中程度の悪化は人が得失を審査します。観察用の指標は監視を続けます。観測が足りない場合や判断が残る場合は、理由を記録し、現時点では採用を決めない保留（EXTEND）にします。著者は指標の得失を経済価値で比べる集計も使います。

評価役は判定とともに、主指標の効果、副作用の状態、統計手法、観測期間、解釈上の注意を記録します。失敗した実験についても、原因、発生した工程、目的、対象の区分、変更箇所を記録し、次の発案で参照できるようにします（§6.3〜6.4）。

### SGPOで実行基盤を変える

評価役が実行記録と採点基準から、どこを直すべきかを文章（g）で示します。修正役はその文章から実行基盤（harness）の変更案を作ります。一度に変更するのは担当エージェント1つの指示、検査規則、出力形式などです。他の役を固定し、変更前hと変更後h′で同じ課題をやり直します。同じ課題ごとの得点差を平均し、差が基準を超え、データ形式、ツールの利用範囲、人の審査条件などを壊さなければ採用します（§7.1、式7〜9）。

`(loss_text, g) = Evaluator(h, traces, rubrics)`

`h′ = Refiner(h, g)`

`admit(h′) ⇔ mean[J(h′, task)−J(h, task)] > ε AND Safe(h′−h)`

SGPO-Iは作業の実行記録から課題と採点基準を作ります。発案担当の5回の例では、尺度をそろえた課題の得点が75.15%から98.00%になりました。同じ回の新旧比較には同じ課題を使いますが、回をまたぐと課題と採点基準が変わり得ます。オンラインの推薦指標が22.85ポイント改善したという結果ではありません。

SGPO-IIは過去に承認されたマージリクエストから要件を取り出します。実装役には元の変更を見せず、評価役だけが参照します。重み付き総合点が4.0以上で、要件どおりに動作するかの採点も4以上なら、その課題は合格です。複数ファイルにまたがる非同期処理の例では総合点が2.60から4.90へ上がりましたが、別の例では3.67から1.80へ下がりました。確認した課題で悪化を見つけても、未検証の課題で悪化しない保証にはなりません。

SGPOは文章で指示や検査規則を変更する手順で、数値勾配でLLMの重みを更新する手法ではありません。§7.2では逆に実行基盤を固定し、結果を見てどのモデル構成を次に探索するかを変えています。

### 本番候補までに残った案の数

3週間の運用では374案のうち106案が審査を通り、そのうち100案が実装されて実験に入り、10件が本番導入の候補（LR）になりました。106/374と100/106では分母が違います。最後の段階は表示した件数で10/100=10%ですが、論文の表5は9.9%と報告しています。全374案を分母とする10/374は約2.67%であり、§8.2の別の探索実験とは混ぜません。

## 論文の運用結果

[一次資料（原論文v2）](https://arxiv.org/html/2606.26859v2)の§8.1では、3ワーカーが3週間で374案を出し、106案が審査を通り、100案が実装されて実験に入りました。10件が本番導入の候補です。内訳はメインフィードが361案から8件、生活サービスが13案から2件です。候補になった件数を、すべての利用者へ展開した件数とはみなしません。

表8の1ワーカー・1週あたりでは、同時実験数がAgentXで12、人手で1.5でした。本番導入の候補は1.1件と0.08件、アプリ利用時間の累積増加率は0.0623%と0.0167%です。約3.7倍はこの増加率どうしの比で、利用時間自体が3.7倍という意味ではありません。一方、1案あたりの展開率はAgentXが2.7%、人手が5.1%でした。同じ案を、同じ条件で人とAgentXに無作為に割り付けた比較ではありません。

メインフィードでは利用者のアプリ利用時間が累積で+0.561%と報告されました。生活サービスの年率換算売上は1億元を超えたと報告されました。対象と指標が異なるため、共通のA/Bの効果として合算しません。年率換算売上は1年間に実際に得た売上でも、利益でもありません。個々の施策の展開範囲の重なりや元データはLabでは独立に確認できません。

§8.2のモデル構成の探索は、3週間の運用とは別の実験です。113本の論文を再現し、214件を実験へ送り、180件が完了しました。公開データ上で簡略化した基準を上回ったのは104件（完了180件の57.8%）、本番A/Bに送ったのは22件、結果が正だったのは5件、本番導入の候補は2件です。57.8%は、配信条件も含めた本番システム全体に勝った割合ではありません。

§8.3の別の個別事例では、視聴後の共有・保存・再視聴などを表す信号（PCV）を順位付けに使いました。最初の案は視聴時間の伸びを確かめきれなかったため、次の案では品質の条件を加え、利用者の活動量に応じて重みを変え、視聴時間を重視する基礎スコアを使いました。この変更のA/Bでは視聴時間+0.071%、著者がreal-showと呼ぶ指標+0.118%でした。メインフィード全体の累積値+0.561%とは別の値です。

## 並行して進めるための条件

確認したリポジトリの規約、実験の設定、試運転の手順、観測する期間を共有すると、次の案で同じ確認をやり直さずに済む場合があります。独立した作業を先に進めれば、別の案の観測が終わるまで実装を待つ必要もありません。

ただし、同時に変更できる設定、使える利用者の規模、人が審査できる件数には限りがあります。表6では、却下された268案のうち64.7%が、設定や実験資源が他の案と重なる分類に入っています。ワーカーを増やしたときに成果まで比例して増えるとは、この3週間の観察では確かめられません。

## Labで比べる入力

Labは、主指標の効果を同じ0.3にした5つの入力で、判定がどう変わるかを示します。副作用の悪化がないとき、中程度のとき、重大なときのほか、観測が短いときや信頼区間の下限が負のときを比べます。効果の基準0.2と観測14日間は教材用の設定で、論文の固定規定ではありません。

次に、手で用意した3課題の変更前後の得点から、実行基盤を更新する条件を確かめます。Labは信頼区間を推定せず、課題を実際に実行して得点を付けることもありません。

## 人工例での判定

条件を満たす入力は採用（KEEP）です。同じ主指標の値でも、重大な副作用があると不採用（DISCARD）、中程度なら人の審査を待つ保留（EXTEND）になります。観測3日の場合や、信頼区間の下限が−0.1の場合も保留です。

3課題の得点差の平均が約0.1333でも、安全性の条件を満たさない変更は採用しません。平均差が負の例も採用しません。ここで使った得点は人工の入力で、著者が報告したSGPOの改善率ではありません。

## 確認したこと

Labは人工の入力で、副作用の悪化や観測日数によって判定が変わることと、得点差と安全性の両方で更新を判定することを確認しました。配布JSONの `checks` にある `CONFIRMED` は、記載した個別の条件だけを指します。

## 確認していないこと

LabはLLMによる発案・実装、統計量の推定、本番での配信、SGPOの改善率を再現していません。ワーカーを増やしたときの効果や、人と同じ条件で比べた成績も検証していません。

## 手元での再実行

配布の `run.py` を `python run.py` で実行すると、標準ライブラリだけで判定を計算し、隣に `results.json` を保存します。乱数や外部APIは使いません。入力と出力は配布ファイルにあります。

論文とarXivの書誌からは取得できる公式実装への案内を見つけられず、公式コードでの再現は行っていません。非公開と断定したわけではありません。

配布の `mapping.md` に節と表の対応を載せています。PDFの版を固定した一次資料から報告値を転記し、教材用の結果と分けています。
