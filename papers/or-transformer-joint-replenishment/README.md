# OR-Transformer: Scaling Real-Time Decision-Making to 1,000 Items

複数の商品をまとめて発注すると固定費がかかるとき、いつ発注し、各商品を何個頼むか

Liuらは、まとめて発注するかと、発注する場合の商品ごとの数量を別々に学習させました。1,024商品を使ったシミュレーションでは、OR-Transformerの平均割引費用は、学習する比較手法で最も低かったPPOより約75%低くなりました。

## 論文の概要

Liuらは、複数の商品をまとめて発注するたびに固定費がかかる場合に、いつ発注し、各商品を何個頼むかを決める方法を提案しました。著者らのOR-Transformerは、全商品の在庫や未着注文を見て、まとめて発注するかと、発注する場合の商品ごとの数量を別々に求めます。学習では、数量を変えたときに、その後の在庫や費用がどう変わるかをシミュレーターの式から計算します。

著者らは、需要や納期を設定したシミュレーションで、1,024商品を50回の判断にわたって評価しました。平均割引費用はOR-Transformerが約35万、学習する比較手法の中で最も費用が低かったPPOが約139万で、提案手法の費用はPPOより約75%低くなりました。この規模で各手法を学習したのは1回で、128回は評価用の試行数です。著者らは実店舗では検証していません。

## 共同発注で節約できる費用と、早く頼むと増える費用

複数の商品をまとめて発注すると、品目の数や注文量にかかわらず1回分の固定費がかかります。一つの商品を補充するとき、他の商品も同時に頼めば、別々に発注する場合より固定費を抑えられます。一方、必要より早く頼むと保管費が増えます。著者らは、在庫が足りずに満たせなかった分は未納として次期へ繰り越す設定を使いました。棚から商品がなくなった時点で売上が失われる設定ではありません。

## 著者らの学習方法と、Labの2期の計算

### 著者らのモデルは、発注するかどうかと、発注する量を別々に出す

Liuらは、倉庫の在庫、未着の発注、納期、保有費用、未納費用などを商品ごとに入力します。どの商品にも共通の情報として、発注の固定費や市場全体の需要の状態も渡します。モデルには一覧の何番目かを示す番号を渡しません。入力で商品AとBの位置を入れ替えると、数量の出力もAとBに対応して入れ替わります。共同で発注する確率と、全体の費用の見積もりは変わりません。

別々の3つのTransformerが、発注の確率、商品ごとの候補数量、将来にかかる費用を出します。共同発注する場合をY=1、発注しない場合をY=0とします。商品iの候補量をQᵢとすると、実際に発注する量はYQᵢです。発注する場合でも、数量は商品ごとの上限を超えません。発注するかどうかを判断する時点では、その期の需要はまだ分かりません。発注した商品は、商品の納期を経て初めて需要に使えます。

### 著者らは、発注の有無と数量で勾配の計算を変えた

Yは0か1なので、著者らはYそのものを微分しません。モデルが選んだ行動の対数確率の傾きに、その行動で生じる費用と基準の差を掛けます。これはスコア勾配と呼ばれます。将来の費用を見積もる別のネットワークも、学習に使います。

Qのほうは連続した値です。需要と各期に発注するかどうかを固定すれば、Qを少し変えたときに、届く量や未着注文、後の期の在庫と費用がどう変わるかを計算できます。著者らは、シミュレーターで計算したこの変化を、数量を出すモデルの学習に使いました。数量を変えた効果が、その期だけでなく、後の期の保有費用や未納費用に表れるからです。

### Labでは、1商品・2期の例で費用の傾きを確かめる

Labの例は1商品で、最初の在庫は1単位、各期の需要は順に3単位と2単位です。Y=1のときだけ発注し、発注した分はすぐに届きます。原論文のように納期を経て届く設定ではありません。1期目の期末在庫は `x₁ = 1 + YQ − 3`、2期目は `x₂ = x₁ − 2` です。値が負のとき、その絶対値は次の期にも残る未納分です。この例では未納分を売り逃しとして消しません。

費用は `KY + Σₜ[h max(xₜ,0) + b max(−xₜ,0)]` です。発注すると固定費K=3が1回かかります。期末に在庫があれば1単位当たりh=1、未納が残れば1単位当たりb=4を、その期の費用に足します。

たとえばY=1、Q=2.5では、1期目の期末在庫は0.5、2期目には1.5の未納が残ります。Qを少し増やすと、1期目の保有費用は1単位当たり1増え、2期目の未納費用は1単位当たり4減ります。合わせた費用の傾きは−3です。Y=0ならQを変えても発注しないので、在庫も費用も変わりません。

一次資料：[原論文v2、第2〜3節・付録B〜C](https://arxiv.org/html/2609.01933v2)。

### 著者らが学習で行ったこと

著者らは、共同発注するかどうかと商品ごとの候補数量を別々に出すモデルを作りました。発注するかは選んだ行動の確率を使って学習し、数量は、需要と発注の有無を固定し、数量を少し変えたときに後の在庫や費用がどう変わるかを計算して学習しました。

### 比較からは一つの工夫だけの効果を分けられない

Transformer-PPOは同じ種類のモデルで、数量の学び方が異なります。HPOは在庫の計算を通して数量の変化を学ぶ一方、商品間の関係は全結合のネットワークで扱います。費用の差だけでは、Transformerと数量の学び方がそれぞれどれだけ貢献したかは分かりません。

## 発注量を変えた効果を後の期まで追う

著者らのモデルでは、商品の並び順は判断材料になりません。商品を並べ替えると数量の出力も同じ順に変わり、発注する確率と将来費用の見積もりは変わりません。また、今の発注量が変われば、納期を経て届く量や、その後の未納と在庫も変わります。モデルは、変更の影響を後の期まで追って、数量をどう調整すれば総費用が下がるかを学びます。

## 論文が報告した費用と判断時間

### 1,024商品の50回の判断では、学習する比較手法の中でPPOが最も低コストだった

著者らは、互いに関連する商品の需要を人工的に作り、納期や保有・未納の費用を商品ごとに変えました。学習には使わなかった128本のシミュレーション経路で、50回の発注判断にかかった割引費用を比較しました。割引費用は、後の期の費用ほど重みを小さくして合計した値です。

1,024商品では、平均割引費用がOR-Transformerで約35万、学習する比較手法で最も低かったPPOで約139万でした。OR-TransformerはPPOより約75%低い結果でした。1商品と4商品ではHPOが最も低く、16商品以上ではOR-Transformerが最も低くなりました。1,024商品では各手法を学習したのは1回です。128本は学習の繰り返しではなく、評価に使った需要と在庫の経路の数です。

著者らは、同じ50回の比較で、GurobiとHiGHSにも、100通りの需要を想定して50期先まで計画する問題を解かせました。各発注判断の上限は10分です。1,024商品の場合、両方のソルバーが全6,400回の判断で時間切れになり、毎回発注量0を返しました。そのため、両方の費用は同じ約935万になりました。これは時間制限内に発注できなかった場合との比較です。両ソルバーが最適な発注案を求めたときの成績ではありません（表D.4・D.5）。

### 8回の判断では、Gurobiの計算上限を別に設定した

著者らは1,024商品の別の比較で、発注を8回判断し、Gurobiに1回につき最大6時間を認めました。割引費用は、千単位でOR-Transformerが126.61±4.23、Gurobiが156.58±4.93でした。±は標準誤差です。OR-Transformerが19.1%低い結果でした。

著者らは、8回の判断にかかった合計時間を、OR-Transformerが0.0432秒、Gurobiが48時間49分と報告しました。400万倍を超える差は、学習を終えたモデルが判断を出す時間と、その条件でソルバーを実行した時間の比較です。モデルの学習時間は含みません。[Gurobiの仕様書](https://docs.gurobi.com/projects/optimizer/en/current/reference/parameters.html#timelimit)によると、終了処理で設定した時間を超える場合があります。ただし、論文の48時間49分の内訳は確認できていません。論文のこの結果から、実店舗で同じ割合の費用が下がるとは分かりません。

一次資料：[原論文v2の第4節・図4.1・付録D](https://arxiv.org/html/2609.01933v2)。

## Labの人工例で確かめること

Labは学習していない自己注意を使い、3商品の並びを6通り変えて、出力が対応する順に並び替わるかを確かめます。さらに1商品・2期の人工例で、発注量Qを少し増やした場合と減らした場合の費用から傾きを計算し、式で求めた値と比べます。発注の有無については、0か1を確率で選ぶ小さな例を作り、スコア勾配と、期待費用を直接微分した値を照合します。

## 商品を並べ替え、発注量を変えた結果

商品を並べ替えると、各商品の出力は同じ順に並び替わり、全体を表す出力は変わりませんでした。ここで比べた出力は計算上の商品表現であり、学習した発注量ではありません。

1商品・2期の例で、発注量Qが0.5、2.5、4.5のとき、費用の傾きは順に−8、−3、2でした。Qが小さい範囲では、少し多く発注すると未納が減り、費用も下がります。Qが大きく両期で在庫が残る範囲では、多く発注するほど保有費用が上がります。

## Labが確認した範囲

**CONFIRMED（確認済み）。** Labの固定した自己注意では、商品の入力順と商品別の出力順が対応しました。在庫がゼロをまたがない範囲で、費用を式から微分した値は、数量を前後にずらして計算した中央差分と一致しました。発注の有無を選ぶスコア勾配も、期待費用を直接微分した値と一致しました。原論文の仕組みのうち、この小さな例が扱う範囲だけを確認しています（PARTIAL）。

## Labが確認していない範囲

**NOT TESTED（未検証）。** Labは原論文のTransformerを学習させていません。PPOやHPOとの性能比較、1,024商品の割引費用、Gurobiの判断時間も再現していません。在庫がゼロになる境目での微分、納期が長い場合の学習の安定性、実店舗での運用も確認していません。

## 実装と実行方法

`attention()` は、全体を表す入力と商品ごとの入力に同じ処理を行います。`cost()` は、1回分の固定費と2期分の保有費用・未納費用を足します。`derivative()` は、Qを少し動かしたときの費用の傾きを計算します。発注しないと実際の発注量は0です。そのとき候補量Qを変えても、在庫や費用は変わりません。

`uv run papers/or-transformer-joint-replenishment/run.py` を実行すると、同じフォルダの `results.json` を作り直せます。Pythonの標準ライブラリだけで動きます。
