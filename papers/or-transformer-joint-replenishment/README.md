# OR-Transformer: Scaling Real-Time Decision-Making to 1,000 Items

共同発注をするかどうかと、約千商品の発注量をどう分けて学ぶか

## 要点

OR-Transformerは発注するかどうかと、発注する場合の商品別の数量を分けて学ぶ。商品の並び順に左右されないTransformerを使い、数量を変えると在庫と費用がどう変わるかを計算して学習する。著者の合成環境では、1,024商品を扱うときの費用が、学習を使う比較手法の中で最も費用が低かったPPOより約75%低かった。実店舗で導入した結果ではない。

## 共同発注と欠品の扱い

どの商品を何個発注しても、まとめて1回発注すれば共通の固定費Kがかかる。発注する場合は商品ごとに数量を決める。在庫が足りなかった分は未納需要（backlog）として翌期に繰り越す。著者は、商品間で相関のある合成Poisson需要を使い、商品によって納期や費用が異なる条件で評価した。DingdongやJDの現場データを使った評価でも、棚割りのランダム化比較試験（RCT）でもない。

## 発注の有無と数量の学び方

著者は、固定費を払って発注するかどうかをY、商品別の連続的な発注量をQとし、別々に学習させる。Yは発注する・しないの2値なので、選ばれた行動の対数確率を微分し、費用と組み合わせて勾配を推定する（score gradient）。Qではサンプルした需要と発注の有無を固定し、数量を少し変えたときに各期の在庫と費用がどう変わるかを直接微分する（pathwise gradient）。

Labの解釈では、費用差をTransformerだけの効果とは読めない。Transformer-PPOとの差は数量の勾配の求め方を考える手がかりで、全結合ネットワーク（MLP）を使うHPOとの差は商品間の関係の表し方を考える手がかりになる。どちらも構成要素ごとの因果効果を切り分けた比較ではない。

## 商品の順序と将来の在庫費用

商品を一覧の中で並べ替えても発注の問題は変わらない。そこで、並び順を表す番号（位置ID）を入力せず、すべての商品を同じ方法で表現する。発注量を増減すると、後の期に残る在庫や未納分も変わる。この変化を直接微分すれば、発注量ごとの影響をサンプルの報酬だけから推定する負担を減らせると考えられる。

## 著者の評価結果

一次資料の[Table D.5・Figures 1.1, 4.1](https://arxiv.org/pdf/2609.01933v2)に著者の結果がある。評価には固定した128本の経路（episode）を使った。発注を50回判断する比較で、1,024商品の費用はOR-Transformerが0.35M、学習を使う比較手法の中で最も低かったPPOが1.39Mだった。1商品と4商品ではHPOの費用が最も低く、どの規模でもOR-Transformerが優位だったわけではない。

別の、発注を8回判断する評価では、数理最適化ソルバーのGurobiに1回あたり最長6時間を与えた。費用はOR-Transformerが126.61±4.23K、Gurobiが156.58±4.93Kで、前者が19.1%低かった。8回の判断に要した時間の合計は0.0432秒対48時間49分で、400万倍を超える差があった。この時間には学習を含めない。50回の判断に対して1回あたり10分に制限した表とは別の比較だ。

## Labの人工例を実行する

`uv run papers/or-transformer-joint-replenishment/run.py` を実行すると、同じフォルダーのresults.jsonを更新する。Python標準ライブラリだけで動く。

固定した重みでスカラーの自己注意（self-attention）を計算し、商品の並べ方を6通り試す。2期の未納費用を含む例では、Qに対する解析上の勾配と、Qをわずかに増減させて求める中央差分を比べる。発注するかどうかを表すBernoulli変数についても、score gradientと、期待費用を厳密に微分した値を照合する。

## 人工例の結果

商品の並び順を変えると、商品別の数量表現だけが同じ順に入れ替わる。全体の状態を表す出力（global出力）は変わらない。この例の表現は未学習で、発注量そのものではない。Qが0.5、2.5、4.5のとき、Qに対する費用の勾配は順に−8、−3、2となった。在庫が足りないときは発注量を増やすと費用が減り、在庫が十分なときは保有費用が増える。

## Labで確認した範囲

固定した自己注意で商品を並べ替えたときの振る舞い（順序同変性）、区分ごとに滑らかな在庫費用の微分、Bernoulli変数に対するscore gradientの恒等式を確認した（CONFIRMED）。仕組み全体の確認は一部に限る（Mechanism: PARTIAL）。

## Labで確認していない範囲

性能、規模を拡大したときの動作、実運用への適用は検証していない（Performance / Scaling / Production applicability: NOT TESTED）。Transformerの学習、PPO・HPOとの訓練比較、1,024商品での評価、Gurobiでの計算、実店舗での運用は行っていない。費用の傾きが切り替わる点での微分や、納期が長い条件でも学習が安定するかは調べていない。

## 実装

`attention()` は全体を表すトークン（global token）と各商品のトークンに同じ演算を適用する。`cost()` は2期分の保有費用と未納費用を計算し、`derivative()` はその費用をQで微分する。発注したらKは1回だけかかり、発注しなければQを変えても在庫は変わらない。
