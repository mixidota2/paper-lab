# OR-Transformer: Scaling Real-Time Decision-Making to 1,000 Items

まとめて発注すると固定費がかかるとき、どの商品をいつ、何個発注するか

OR-Transformerは複数の商品をまとめて発注するかどうかと、発注する場合の数量を別々に学びます。著者のシミュレーションでは、1,024商品の費用が、学習する比較手法の中で最も費用が低かったPPOより約75%低くなりました。実店舗での検証ではありません。

## 概要：共同発注するかと、商品を何個発注するか

商品をまとめて発注すると、品目や数量によらず1回分の固定費がかかります。著者は共同発注をするかどうかと、する場合に各商品を何個発注するかを別々に学ぶOR-Transformerを提案しました。商品を並べ替えても判断が変わらないようにしたうえで、発注量が将来の在庫と費用に与える影響を学習に使います。

1,024商品を対象に発注を50回判断するシミュレーションでは、学習する比較手法ではPPOの費用が最も低く、OR-Transformerの費用はそのPPOより約75%低くなりました。1商品と4商品では別の方法が最も低コストでした。結果は商品数によって違います。著者は実店舗では検証していません。

## 商品をまとめると発注の固定費を分け合える

企業は商品ごとに必要な数量を決めますが、発注するなら数量や品目数にかかわらず共通の固定費Kがかかります。在庫が足りないとき、満たせなかった需要は未納分として次の期に繰り越します。欠品ですぐに売上を失う設定ではありません。著者は商品間で相関するように作った人工のポアソン需要を使い、商品ごとに納期と費用が異なる条件を調べました。DingdongやJDの現場データ、店舗の棚割りを変更する実験は使っていません。

## 発注の有無と商品別の数量は別の方法で学ぶ

著者はまとめて発注するかどうかをY、各商品の候補数量をQで表します。発注の有無は0か1なので、著者は実際に選んだ行動の対数確率が学習パラメーターでどう変わるかを費用の情報と組み合わせて推定します（スコア勾配）。数量は連続量なので、需要と発注の有無を固定し、数量が各期の在庫と費用に与える影響をシミュレーションの式から直接求めます（経路ごとの勾配）。

## Labの解釈：比較は構成要素の効果を分離していない

Labでは費用差をTransformer単独の効果とはみなしません。Transformer-PPOは同じ種類のネットワークで数量の学び方を変えた比較です。HPOは同じようにシミュレーションから数量の勾配を求めますが、商品間の関係を全結合ネットワークで扱います。比較を読むとどの違いを調べるべきかが分かりますが、部品の効果を個別に測った結果ではありません。

## 商品の並び順を入力にせず、将来の費用で学ぶ

表の中で商品の順序を変えても、必要な発注は同じです。そこでモデルには商品の順番を示す番号を与えず、同じ処理で全商品の状態を読み込みます。また、発注量が変わると、次の期以降に残る在庫と未納分も変わります。著者はこのつながりを計算し、数量を少し動かしたときに費用がどちらへ動くかを学習に使いました。難しいのは、商品の数量を少し動かせても、発注するかどうかは少しだけ変えられない点です。

## 論文が報告した費用と判断時間

著者は一次資料の[原論文§4、図1.1・4.1、表D.5](https://arxiv.org/pdf/2609.01933v2)で、学習には使わなかった128本のシミュレーション経路を使っています。50回の発注判断では、1,024商品の割引費用はOR-Transformerが35万（0.35M）、最良の学習ベースラインのPPOが139万（1.39M）でした。一方、1商品と4商品ではHPOが最も低い費用でした。

発注を8回だけ判断する別の比較では、著者はGurobiに1回の最適化につき6時間の上限を設定しました。著者が報告した割引費用（千単位、±は標準誤差）は126.61±4.23対156.58±4.93で、OR-Transformerが19.1%低い結果でした。発注を判断する時間は0.0432秒対48時間49分で、400万倍を超える差があると著者は報告しています。学習時間は含みません。Gurobiの[仕様書](https://docs.gurobi.com/projects/optimizer/en/current/reference/parameters.html#timelimit)には終了処理で設定時間を超える場合があると書かれていますが、論文の実行時間の内訳は確認できていません。50回の比較で設定された1回10分の上限とは別の実験です。

## 小さな人工例で、学習の一部を確かめる

`uv run papers/or-transformer-joint-replenishment/run.py` を実行すると、同じフォルダーの `results.json` に計算結果が入ります。必要なのはPythonの標準ライブラリだけです。

Labは学習していない自己注意を使い、3商品の並びを6通り変えて出力を比べます。次に、2期だけの人工例で発注量Qを少し増やした場合と減らした場合の費用差を求め、式から求めた傾きと照合します。発注するかどうかは0か1の行動を確率で選ぶ例です。そのスコア勾配を、期待費用を直接微分した値と比べます。

## 並べ替えと発注量の変更で何が起きたか

商品を並べ替えると、商品ごとの出力も同じ順に入れ替わり、全体を表す出力は変わりませんでした。ここで比べた出力は計算上の商品表現であり、学習した発注量ではありません。発注量Qが0.5、2.5、4.5のとき、費用の傾きは順に−8、−3、2でした。例の中では、未納分を減らす間は発注量を増やすと費用が下がり、両期に在庫が残ると発注量を増やすほど保有費用が上がります。

## Labで確認した範囲

Labは、固定した自己注意の出力が商品の並べ替えに対応すること、各期の在庫がゼロをまたがない範囲で費用の微分が中央差分と合うこと、発注するかどうかのスコア勾配が期待費用の微分と合うことを確認しました（CONFIRMED）。いずれも小さな例で確かめたため、仕組みの評価は一部に限ります（Mechanism: PARTIAL）。

## Labで確認していない範囲

LabはTransformerを学習させておらず、PPO・HPOとの学習比較や、1,024商品の評価を再現していません。Gurobiの計算時間も測っていません。在庫がゼロになる境目での微分、長い納期でも学習が安定するか、実際の店舗で使えるかは未確認です。性能・規模・実運用への適用は未検証です（Performance / Scaling / Production applicability: NOT TESTED）。

## 実装は在庫と費用の式を確認するためのもの

`attention()` は全体を表す入力と各商品の入力に同じ計算を適用します。`cost()` は発注の固定費、2期分の在庫保有費、未納費用を足し、`derivative()` はQに対する費用の傾きを計算します。固定費Kは、発注した場合に1回だけかかる費用です。発注しない場合はQを変えても実際の発注量は0で、在庫も費用も変わりません。
