# SIDScope: A Diagnostic Resource for Semantic-ID Interfaces in Generative Recommendation

SIDScopeは、商品と識別子（SID）の対応表を点検する道具です。候補に正解のSIDが残っても、同じSIDを持つ別の商品と区別できるとは限りません。対応表を直したあとに旧モデルを使えるかも、別の検査で確かめます。

優先度: Watch。確認日: 2026-09-21。

## 実行

```sh
uv run papers/sidscope-diagnostics/run.py
uv run paper-lab build
```

## 概要

Dingらは、生成推薦で使う商品と識別子（SID）の対応表を点検する道具「SIDScope」を作りました。商品を一つずつ区別できるかと、利用履歴で一緒に現れやすい商品を先頭の符号でまとめて探せるかは、別の問題です。SIDScopeはその両方を調べ、対応表を更新したときに変わった符号や、生成した符号から実際にどの商品を取り出せるかも記録します。

著者は、利用履歴で一緒に現れた商品が先頭の符号を共有する度合い（D3）と、同じ先頭の符号で候補を探したときに正解商品が候補に入る割合を比べました。順位相関は8つの対応表で0.976、同じカタログをまとめた5群で0.900（p値0.083）でした。比べた二つの指標は同じ先頭の符号を使います。一方、学習済みの生成モデルで、上位20件の並びを評価する指標（NDCG@20）とD3の相関は、試した設定によって−0.564から0.205までばらつきました。

生成ログでも、正解の符号が候補に残ったことと、そこから正解の商品だけを取り出せたことは一致しませんでした。GRID/P5の一つの分割では6.4%と3.4%で、どちらも正解の商品を指定した探索記録が分母です。この診断は候補を取り出す仕組みの点検に使えますが、本番の推薦の質を測るものではありません。論文には本番でのA/Bテストはありません。

## どんな問題を調べるか

生成モデルが出したSIDが索引にあっても、同じSIDを持つ商品が複数あれば、そのSIDだけでは正解の商品を一つに絞れない。一方、全商品に異なるSIDを付けても、一緒に選ばれやすい商品が先頭の符号を共有していなければ、その符号は候補をまとめて探す手掛かりになりにくい。

対応表にない商品を足すと、以前からあった商品のSIDまで変わることがある。更新前に学習したモデルが、更新後の符号を正しく出せるとは限らない。

## 何が分かるか

著者は、出典をたどれる商品とSIDの対応表を共通の形式にそろえ、D1〜D7で検査する。対応表から分かるのは、商品を区別できるか、先頭の符号で関連する商品をまとめられるか、更新で何が変わったかなどである。生成ログがあれば、候補から商品へ戻る段階も調べられる。

[SIDInspector](../../papers/sidinspector-mapping-diagnostics.html)は、主に書き出した対応表の検査に使う。SIDScopeは、その対応表を使う生成モデルのログや、更新後に旧モデルを使えるかを確かめる手順まで扱う。[QuaSID](../../papers/quasid-collision-qualified-sid.html)のように重複を設計に含める場合も、共有されたSIDからどの商品を返すかは別に検査できる。[SnapLGR](../../papers/snaplgr-snapchat.html)のように一つのSIDから複数の動画を展開する設計にも、この区別が当てはまる。

## 手法

[手法の説明](method.md)に、図と計算式を載せています。

SIDの先頭の符号で候補を探す方式では、一緒に現れる商品対が同じ先頭の符号を持つ割合（D3）を見ると、正解が候補に入りやすいかを調べられる。先頭の符号を使わない採点器や、別の信号も学習する生成モデルの順位まで、D3だけで予測できるわけではない。

一つのSIDから複数の商品を返せる場合も、重複率だけで良し悪しは決まらない。候補に残った符号、その符号から取得できる商品、最後に選ばれた商品を分けて測ると、どの段階を調べ直すべきかを判断しやすい。

## 著者が測ったこと

[論文初版の表4〜7・§8](https://arxiv.org/html/2608.18779v1)は、実行条件を満たした8通りの取り込みと、確認できる記録を別途残した例を区別している。商品集合や符号列の長さが異なるため、表の行を符号化方式の順位としては読まない。

**先頭の符号で候補を探した結果。** 対応表を8つ個別に数えると、D3と正解が候補に入る割合の順位相関は0.976だった。同じ商品集合を共有する対応表を5群にまとめると0.900、正確検定のp値は0.083だった。学習済みのSID生成モデルで順位の質を表すNDCG@20との相関は−0.564〜0.205だった。この範囲は、試した設定ごとの値であり、信頼区間ではない。

**生成ログで数えた結果。** 索引で許された符号列だけを探索したとき、GRID/P5の分割0では正解の符号が候補に残った割合は6.4%、そこから正解の商品を一つに特定できた割合は3.4%だった。差は3.0ポイントだった。分割1では5.0%対3.0%、別の分割法を使ったDIGERでは6.6%対5.4%だった。どちらの率も正解を指定した探索記録で割る。差の1.2〜3.0はパーセントポイントで、相対変化率ではない。方式と評価データが違うため、差が出た原因をこの比較だけで分けることはできない。

**対応表の更新後に旧モデルを使った結果。** DACT 0.6から0.7への更新で、SIDがなかった275商品に符号が付いた。一方、前後に共通する9,610商品の23.6%は符号が変わった。対応表だけを更新し、旧モデルを使った場合、新商品のRecall@20は0のままだった。乱数の初期値を3通り変えて追加学習したモデルは、著者が事前に定めた引き継ぎの条件を満たした。既存商品では、対応表だけを変えたときの順位指標の差の区間が0をまたいだため、更新によって順位の質が下がったとは断定できない。

以上は著者が公開データや生成ログで測った結果である。本番の応答時間、クリックや購入の変化、A/Bテストはここでは評価していない。

## Labの人工例を動かす

Labの `run.py` は、商品とSIDの対応表をJSONで渡すと点検できる。段ごとの符号列の数や割り当ての偏り、同じSIDを共有する商品の割合、重複分の割合を求める。商品対とその重みを渡せば、先頭の符号が一致する度合いも計算する。更新前の表を渡した場合は、両方の表にある商品のうち符号が変わった割合を求める。

```sh
uv run papers/sidscope-diagnostics/run.py --mapping map.json --previous old.json --pairs pairs.json --out /tmp/my-diagnostics.json
```

`map.json` の例は `{"item-a":[0,1],"item-b":[0,2]}`。 `pairs.json` の例は `[["item-a","item-b",3]]`。Labは渡された商品対でD3を計算する。元の利用履歴から商品対を探す処理は含まない。人気の入力がないためD4は計算せず、対応表だけで生成モデルの品質も判定しない。

入力を指定しなければ、説明用の6商品と、公式パッケージがMITライセンスで公開した12商品の対応表を診断する。後者については、以前に公式の動作例も別に実行した。以前の公式実行で得た値と入力のハッシュは `official-check.json` にある。Labの計算結果は `results.json` に保存する。二つのファイルを見分けるには[配布ファイルの読み方](mapping.md#配布ファイルの読み方)を参照。入力例の利用条件は `NOTICE.txt` にある。

Labの人工例では、6商品のうち2商品が同じSIDを共有する。共有する商品を両方数えるD2は2/6だが、SIDの種類が1つ足りないことを数えるD5の重複率は1/6になる。重複を解消すると両方とも0になるが、この例で最初の符号が一致する度合い（D3）は変わらない。対応表の診断値が改善したことと、生成モデルを引き続き使えることは別である。

## 確認したこと

Labは符号列の長さがそろっているか、各符号が非負の整数かを点検する。実際のJSONを渡す使い方では、入力のハッシュを記録する。人工例では、有効なSIDが生成されても、複数の商品に対応すれば正解の商品を一つに絞れないことを確かめた。

過去の公式v1.0.1の動作例では、入力検査の通過とD1〜D5の出力を確認した。公開12商品では、異なる完全SIDの数11、D2の2/12、D5の重複率1/12、先頭から各段までの符号列の数3/6/11がLabの独立実装と一致した。これは本番の対応表ではなく、論文の仕組みは一部のみ確認した（PARTIAL）。

## 確認していないこと

公式の全条件、公開された125,000行の生成ログ、4,999回の再標本化、学習済みの生成モデルの引き継ぎは再現していない。D4、公式の手順で近い商品を選ぶ処理、出典を含めた全入力検査もLabでは実装していない。性能、規模を広げた場合の動作、本番での有用性は未検証（NOT TESTED）。本番のA/Bテストも実施していない。

## 実装と論文との対応

`validate()` は入力の形式を点検し、`diagnose()` は符号列の数や重複を集計する。`trace()` は生成されたSIDが商品に戻るか、複数の商品に戻って曖昧になるかを調べる。LabはPython標準ライブラリだけで動く。公式パッケージの読み込み名は、互換性のため `sidinspector` のままである。実装の対応と公開版のハッシュは `mapping.md` に記録した。
