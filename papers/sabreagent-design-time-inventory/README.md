# SabreAgent：言語モデルを設計時だけ使う発注方法

## 概要

著者は、欠品するとその需要を取り戻せない在庫管理で、言語モデルを発注のたびに使わず、ルールを設計する段階だけで使う方法を提案しました。SabreAgentは商品説明から季節ごとの需要の形を作り、発注量に上限を設けるルールを候補から選びます。運用時は、統計的な予測と在庫の計算だけで発注量を決めます。InventoryBenchの1,320事例では、在庫費用をもとにした評価点が0.6311で、公開されていた比較手法の最高値0.5380を上回りました。仕組みの一部を外して比べると、改善の大部分は、言語モデルが加えた機能ではなく、在庫費用に基づいて発注量を決める仕組みから来ていました。

## 問題設定と評価点

論文は、1商品を1拠点で補充する場合を扱います。欠品で売れなかった需要は翌週に持ち越しませんが、評価では欠品した週の需要も観測できます。販売数しか残らない状況とは異なります。著者は在庫ゼロから始め、評価前の需要5点を使い、人工データは50週、実データは47週を評価しました。仕入れ費用、1回の発注にかかる固定費、評価末の残存価値はいずれも0です。

担当する方策は、入荷を反映する前に手元と輸送中の在庫を見て発注量を決めます。その週の入荷を反映してから、需要に応じて販売します。納期は0週、4週、または1・2・3週と消失が混ざる条件です。納期0では今出した注文も同じ週に届きます。確率的な条件の納期∞は、注文が最後まで届かないことを指します。

正規化報酬（NR）は、売上から保管費を引いた報酬を「すべての需要を即時に満たした場合の売上」で割った点数です。各事例で負の点数は0に置き換え、1,320事例を同じ重みで平均します。1はすべて販売して保管費もかからない場合の基準で、どの納期でも達成できるという意味ではありません。

## 設計時と運用時の役割

言語モデルは商品説明から季節性の形を作り、確率的な納期に使う発注ルールの型を提案します。著者は検証データで型を選びます。運用中に言語モデルは呼びませんが、統計予測の更新と発注パラメータの探索は続けます。

言語モデルを発注判断の外に置く設計です。ただし、欠品時の需要も観測でき、仕入れ費用と発注固定費がゼロという評価条件があります。販売数しか分からない店舗や発注費用がかかる店舗へ、そのまま移せるとは限りません。

## 納期に応じた発注の決め方

運用中に注文を決めるのは、設計時に選んだ発注コードです。固定したコードの中で、予測の更新や方策パラメータの探索は続くため、毎回同じ数量を発注するわけではありません。統計モデルは新たに観測した需要を取り込み、元の予測を残しながら、設計時に作った季節性を組み合わせます。

### 即時に届く場合

仕入れが無料で、注文がその期に届くなら、将来に備えて今期から在庫を持つことで仕入れ費用は減りません。原論文の定理1では、需要が各期で独立し、その期ごとの需要分布が既知で、発注上限がなく、仕入れ費用・発注固定費・残存価値がすべてゼロだと仮定します。そのうえで、納期が0で需要の `p/(p+h)` 分位点が期を追って下がらなければ、その期の期待報酬だけで決める在庫水準が最適です。ここで `p` は販売単価、`h` は1個あたりの保管費です。需要分布が変わらなければ分位点も一定です。著者は、分位点が下がる場合まで近視眼最適とは主張していないので、条件を分けて読む必要があります。

### 到着までの期間が決まっている場合

納期が正なら、今回の注文が届くまでの確定済みの入荷を順番に加え、需要のうち実際に売れる分だけ在庫を減らします。売り逃した数量を翌期に繰り越さないため、在庫が負になることはありません。著者は、到着期の不足をもとに、式(3)で発注を増やしたときの売上と保管費の変化を近似します。係数κは余った在庫にかかる費用を調整するもので、正の納期における厳密な最適発注量を与える式ではありません。

### 到着までの期間が変わる場合

式(4)では、需要予測 `r` に `θ` を掛けた値を在庫の目標にし、手元と入荷予定の合計が目標に足りない分を発注します。ただし1回の発注量は `cr` を超えません。著者は設計時に発注ルールの型を探索し、需要予測に応じて在庫の目標を変える方法と、発注上限を加えました。運用時は型を変えず、将来の需要と入荷について共通の乱数経路を使い、この式の `θ` と `c` を探します。言語モデルは呼びません。発注上限は、注文が途中で消失したときに追加発注が急増するのを抑えますが、費用や報酬が常に改善するという保証ではありません。

## 在庫の計算を分ける理由

売り逃した分まで後から売る前提で在庫を計算すると、今回の補充で埋める必要のない不足まで足してしまいます。SabreAgentは納期が決まっている場合、各期に売れる量だけを引いて在庫を進めます。売り逃した分は翌期の不足に加えません。

注文が消失する条件では、1回の発注上限があると不足をまとめて埋めようとする注文が大きくなりすぎません。季節性の形は、需要の観測が少ない段階で統計予測を補います。発注上限や季節性を使えば、どの条件でも報酬が上がるという意味ではありません。

## 論文の評価結果と条件

一次資料は[原論文v2のTable 1・Fig. 4・Table 2](https://arxiv.org/pdf/2609.19760v2)です。以下は著者の報告で、Labが同じデータを使って得た値ではありません。

公式の1,320事例では、SabreAgentの正規化報酬は0.6311でした。これまで公開されていた比較手法の最高値は、Gemini 3 Flashを使って数理最適化の結果を言語モデルで補正する方式の0.5380です。モデルも数理最適化の構成も異なるため、この差を言語モデルの使いどころだけで説明することはできません。

著者は別に、複数事例をまとめて実行する条件で、機能を外して比較しました。固定した数理最適化だけでは0.6180で、季節性の形と、設計時の探索で選んだ発注ルールの型を加えると、3つの乱数の種で平均0.0138上がりました。探索では、まず在庫の目標を決めるときに直近の需要予測を基準にし、次に1回の発注に上限を加えました。運用中に係数θとcを探す計算とは別です。公式と同じように事例を一つずつ実行すると、追加後の点数は約0.0006下がります。そのため、二つの実行方法の値を引いて機能の効果を求めません。

同じ事例で比べると、季節性を加えた場合は実データの3条件で平均+0.0179、設計時に発注ルールの型を見直す探索を加えた場合は、納期が確率的な2条件で平均+0.0230でした。論文の+1.79%と+2.3%は、点数を100点満点に換算した差で、費用の相対的な削減率ではありません。

著者は、開発時にテスト側の集計を参照した判断を二つ開示しています。納期が決まった条件での事例群のずれを見てκを使う近似式の形を決め、係数そのものは検証データで当てはめました。また、確率的な納期に弱いことを示す4つの集計診断を、発注ルールの候補を提案する言語モデルに渡しました。候補ごとのテスト得点は渡していませんが、開発がテストから完全に独立していたわけではありません。

別の124事例では、同じDeepSeek-V4-Flashを運用中の補正に戻すと、納期が決まった4条件でいずれも点数の推定値が下がりました。低下が標準誤差の2倍を超えたのは、実データで納期4週の条件だけでした。特定のモデルと補正方法の比較であり、どの言語モデルを運用に使っても成績が下がるという結論ではありません。

## 図の操作

操作できる図では、初期在庫を0・2・8個から選びます。どの条件でも2期の入荷は0・4個、需要は5・2個です。2期を終えた時点で、次に備える目標の3個に対し、需要を全量引く計算と、売れた分だけ引く計算がそれぞれ何個不足と判断するかを比べます。次の期は実行しません。負の不足は在庫が目標を上回っているという意味で、負の数量を発注するわけではありません。

発注上限の図では、手元と輸送中の在庫を足した値を動かします。目標12個から足りない量を求め、上限がある場合は1回の注文を4個までに抑えます。この図は式(4)の係数を固定した例で、著者が運用時に使う係数の探索は行いません。

## Labの人工例

初期在庫が0個のとき、需要を全量引くと不足は6個、実際に売れた分を引くと不足は1個です。差の5個は、途中で売り逃した量と一致します。初期在庫が8個なら売り逃しは0個で、どちらも不足は−2個、発注量は0個です。式(8)の差は、負の値を残した不足量どうしで成り立ちます。

不足が負なら0にして発注する場合、発注量どうしの差は、売り逃した量を超えませんが、同じとは限りません。初期在庫0個の例で2期目の入荷だけを8個にすると、負の値を残した不足は2個と−3個になります。売り逃した量は5個のままですが、発注量は2個と0個で、差は2個です。この例は式の違いを示すための追加説明で、図の3条件には含めていません。

別の3期の例では、各期の期待報酬だけで決める方策と、3期全体の報酬を最大にする動的計画を比べました。確認した21状態では、両者の価値が一致し、初期在庫0個からの期待報酬はどちらも21でした。この人工例の結果であり、一般の需要や納期で一致するとは言えません。

## 確認したこと

CONFIRMED（確認済み）：Labは、負の値も残した不足の差が売り逃した量に等しく、発注量の差には同じ等式が成り立たないことを確認しました。固定した係数で発注上限を計算し、3期の人工例では、その期の期待報酬だけで発注量を決める方策と動的計画の価値を比べました。

PARTIAL（一部確認）：Labで実行したのは、在庫を進める式と発注量の一部です。SabreAgentの仕組み全体は確認していません。

## 確認していないこと

NOT TESTED（未検証）：LabはInventoryBenchを再実行していません。言語モデルでの季節性の生成、検証データでの発注ルールの選択、確率的な納期と需要を再現して発注パラメータを探す処理も検証していません。実際の店舗での性能、規模を広げたときの効果、本番で使えるかは、この人工例からは判断できません。

## 結果の再生成

リポジトリの直下で次を実行すると、Pythonの標準ライブラリだけで `results.json` を作り直せます。

```bash
uv run papers/sabreagent-design-time-inventory/run.py
```

`project()` は実際に売れた量を使って期末在庫を計算します。`capped()` は固定した係数で式(4)を計算し、`dp_check()` は3期の有限な選択肢を比較します。Labは式(3)のκを使った発注や、元の統計予測と季節性を混ぜる処理を実装していません。
