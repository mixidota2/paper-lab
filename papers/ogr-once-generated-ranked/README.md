# Once Generated, Ranked: End-to-End Generative Slate Recommendation with Unified Semantic-Collaborative IDs

Kuaishouなどの研究チームは、短い動画を1本ずつ採点して並べる代わりに、画面に出す動画の組とその順番を一緒に作る方法を提案しました。OGRは動画の内容に加え、視聴履歴の近い位置にどんな動画が現れやすいかを使って動画IDを作ります。モデルは表示位置どうしの関係を考えてから各位置の動画IDを生成し、動画の組全体に対する反応をもとに学習します。

Kuaishouの本番トラフィックの3%を使った1週間のA/Bテストでは、既存方式より有効視聴が1.120%増えたと著者は報告しています。また、論文の約2.2倍という値は、前の計算結果を待つ必要がある処理の長さを理論上で比べたものです。本番の応答時間が約2.2倍速くなったという測定結果ではありません。

## 推薦の仕組み

OGRは、動画の内容と視聴履歴での共起を使って動画ごとのコード（SID）を作る。推薦時にはまず、前までの表示位置を踏まえて、次の位置に合う動画の特徴を計画する。ある位置の計画ができれば、その位置のSIDを作り終える前に次の位置の計画に着手できる。

論文の調整実験で利用者の反応を報酬にできたのは、表示順も含めて学習ログに残っていた動画の組だけ。表示していない組に、見てくれたはずだと仮定して報酬を付けた実験ではない。

## 再実行

```bash
uv run papers/ogr-once-generated-ranked/run.py
uv run paper-lab build
```

計算にはPythonの標準ライブラリだけを使う。最初のコマンドが同じフォルダーの `results.json` を更新し、次のコマンドが `site/` にページを生成する。内容を直す場合は生成後のページではなく、`lab.yaml`、`method.md`、`mapping.md`、`run.py`、`results.json` を確認する。

## 検証範囲

仕組みの一部だけを検証した（Mechanism: PARTIAL）。依存関係に沿って計算が何段続くか、報酬の調整で主報酬の符号が変わらないかなどを、人工入力で確かめた。結果のCONFIRMEDは、その計算に限る。

論文のモデルや量子化器の学習、SPAによるモデル更新、表示ログの偏り、無効なSIDの処理、本番A/Bテスト、GPUで単位時間に処理できる組数は再現していない。CountSketchの衝突が、固定したハッシュで必ず相殺することも示していない。性能、規模を増したときの挙動、本番に適用できるかは未検証（NOT TESTED）。

論文は[一次PDF](https://arxiv.org/pdf/2608.17613v1)を参照。版、ハッシュ、図表とコードの対応は `mapping.md` に記載した。確認した資料では公式コードの案内は見つからず、公式コードは実行していない。
