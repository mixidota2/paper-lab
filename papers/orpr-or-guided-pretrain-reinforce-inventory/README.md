# ORPR：補充の目安を作り、発注を決めるモデルに教える

ORPRでは、数理最適化で選んだ補充量を使い、約93万パラメータのモデルを事前学習する段階と、ルールやシミュレーションを使って強化学習で調整する段階を分けます。著者はJD.comの過去データの再計算と、実際に発注を変えた現場比較を報告しました。

## 補充量は需要の何日分かで表す

たくさん補充すると、品切れで売り逃す数量を減らせる一方、商品を置いておく費用がかかります。商品によって売れる速さが違うため、著者は補充量を「需要の何日分か」にそろえ、カテゴリごとに候補となる整数の日数を一つ選びました。満たせなかった需要は翌日以降に繰り越さず、売り逃しとします。最適化で決める補充の目安はカテゴリ単位で、学習した補充方策を調整する単位は商品（SKU）です。

## 論文が報告したこと

### 過去データの再計算と、実際に発注を変えた結果を分ける

著者はまず、JD.comの菓子5,319商品について、過去のデータを使って補充量を計算し直しました。商品と配送センターの組み合わせは70,210件です。同じ需要予測の仕組みを使い、発注方法だけを変えて比較すると、表1の総費用はJDの現行方式が3,491、ORPRが3,153でした。現行方式からは約9.68%減りましたが、学習の手本にした数理最適化の方式は3,000でした。表に載っている費用は、実額が分からないように加工されています。

次に著者は、2025年9月の30日間、菓子3カテゴリの331商品でORPRの発注判断を実際に使いました。JDの担当者は、これまでモデルの発注判断をそのまま採用する割合が高かった商品を優先しました。比較対象は、同じカテゴリで需要と在庫回転日数が近い商品です。対象を無作為に割り当てたわけではありません。

この比較では、ORPRを使った商品の在庫回転日数が5.27日短く、在庫の保有費用は29.95%低くなりました（表3）。前年の同じ期間からの変化を比べた表4では、対照群の保有費用は22.05%増え、ORPRを使った群は3.70%増えました。差は18.35ポイントです。ORPRを使った群の費用が前年より下がったわけではありません。欠品しなければ何個売れたかは分からないため、著者は現場の評価に売り逃しの損失を含めませんでした。

在庫回転日数の差は表3が−5.27日、前年からの変化を比べた表4が−4.07日です。欠品しなかった日の割合は、表3がY+2.29%、表4がY+0.47%と記します。Yの値が開示されていないため、この二つの値は原表どおり記し、相対変化とポイント差のどちらかに読み替えません。在庫あり日率は欠品しなかった日の割合で、何個の需要を満たしたかとは別です。

著者は、2024年9月を介入前として、2025年9月との変化を比べました。この比較だけで、介入前に両群が同じように変化していたことや、観測されていない違いがないことは確かめられません。現場の評価は331商品と配送センターの3,899組が対象です。

一次資料：[原論文v2、表1・3・4と§4〜5](https://arxiv.org/pdf/2512.19001v2)。

## Labの二つの計算

Labは2カテゴリに、12日間で合計80個の架空の需要を置きます。カテゴリごとに需要の1〜10日分から一つ選ぶので、候補は100通りです。3日ごとに発注し、翌日に入荷する設定で、商品の単価は1です。図で売り逃しの上限を動かすと、同じ候補の中から、上限を守り、日ごとの期末在庫を足した量が最も小さい案を選びます。

別の計算では、4つの報酬について、それぞれから自分以外の報酬平均を引いた差を求めます。全報酬に同じ定数を足しても、この差は変わりません。ここで試すのはRLOOが使う差の計算までです。モデルの学習や補充判断の更新は行いません。

## 売り逃しの上限を変えると何が起きるか

売り逃しの上限が4個なら、条件を満たす20通りのうち、カテゴリAに需要7日分、Bに6日分を置く案の累計在庫が最も少なくなります。上限を1.6個にすると、初日の入荷が間に合わず4個を売り逃すため、どの案も条件を満たしません。候補がなければ、在庫が0という結果ではなく、条件を満たす案がないと表示します。

報酬の例では、ほかの候補との報酬差は計算しましたが、この差を使えば補充が改善するかは調べていません。

## どこまで確かめたか

**確認済み（CONFIRMED）**：日ごとの需要が販売と売り逃しに分かれ、在庫の収支が合うことを確かめました。100候補で上限を守るかを判定し、その候補の中で累計在庫が最も少ない案を見つけました。報酬は、全候補に同じ値を足しても差が変わりませんでした。

**部分的に確認（PARTIAL）**：論文の仕組みのうち、補充候補をシミュレーションで調べ、教師データの目安を選ぶ考え方を扱います。学習したモデルが実行時に必ず上限を守るとは言えません。

## 調べていないこと

**未検証（NOT TESTED）**：LabではTransformerとVAEを学習させず、RLOOで補充方策を更新していません。元の方策から大きく離れないための罰則や、販促で使う専門家の補充判断も実装していません。JDの費用、現場での効果、大規模な運用は再検証していません。菓子3カテゴリの30日間と、DeepStockで報告された、TmallでAlibaba自身が在庫を持つ全対象への展開は、対象の範囲が違います。
