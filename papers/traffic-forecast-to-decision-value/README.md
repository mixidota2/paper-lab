# When better traffic forecasts fail to improve signal control: a layered diagnostic study of forecast-to-decision value

## 予測の誤差は減ったが、車の列は安定して減らなかった

**Radar。** 著者は中国・宣城の交通需要を29日分再構成し、予測を使うと信号制御が改善するかをシミュレーションで調べました。過去の平均値で予測する方法と比べ、平均絶対誤差（MAE）は流入口で4.03%、進行方向別で3.92%減りました。ただし、車を通す方向の組み合わせを実際に選べたのは、対象の9交差点のうち2地点でした。

評価用の7日間では、将来の情報を使わない同じ制御方式に比べて、車が列で待った時間の合計が、予測を使うと6.09%、直後の実際の流入を先に知らせると3.39%増えました。直後の流入を知らせた場合には、列が上流にはみ出す指標が3.78%改善しました。3つの比較の95%区間はすべて0をまたぎました。この結果からは、渋滞が一貫して改善するとも悪化するとも言えません。これは信号制御の検証で、小売への効果は測っていません。

## 信号の選択肢と情報の時刻が効き目を左右する

右折車の流入を正確に予測できても、その地点で右折を通すタイミングを選べなければ、予測を使っても信号は変わらない。この評価の9交差点のうち、車を通す方向の組み合わせを複数から選べたのは2地点だけだった。

もう一つの落とし穴は情報の時刻だ。ある1分間の総交通量は、その分が終わるまで確定しない。分の途中の判断にその確定値を渡すと未来情報が漏れる。流入口や進行方向の細かさに加え、各数字をいつ使えるかも先に決める必要がある。

## 著者が試したこと

著者は、予測誤差、信号を選ぶ時点で使える情報、実際に選べる信号の組み合わせを順に点検した。次に、将来の流入を先に知る比較条件（oracle）で効果が出るかを試した。最後は設定を固定し、信号を切り替えた結果が次の判断に反映される評価を行った。人工交差点では将来情報が役立ったが、実記録から需要を再構成した最終評価では、待ち行列（queue）の安定した削減は観測されなかった（§5–7）。

## 小売へ持ち帰るなら、まず効果の余地を確かめる

小売でも、発注ロット・容量・納期や、価格を変更できる日と価格帯によって、実際に選べる手が限られる。予測の改善を在庫費用の改善とみなす前に、同じ制約と最適化器のまま将来需要を既知として渡し、費用が下がるかを試す。[Accuracy Is Not Service](accuracy-not-service-intermittent-demand.html)と[Zalandoの価格Lab](zalando-sales-event-pricing-forecast-optimize.html)も、予測を判断にどう使うかを扱う。この交通の結果が小売にも当てはまると確認したわけではない。

## 交通の何を予測したか

2023年4月の29日を、学習13日、検証4日、CQR校正5日、最終テスト7日に時系列で分けた。4月9日はファイルが重複していたため除いた。対象は9交差点、7流入口、20の進行方向。過去60分の観測を使い、先15分を予測する。

点予測では、直近値をそのまま使う方法（persistence）、曜日と分ごとの過去平均（historical mean）、ExtraTreesを比較した。進行方向別の予測には、まず流入口の総量を予測し、直近60分に観測した方向別の比率で割り振る方法（hierarchical rolling-share）を採った。

予測区間を作るときは、LightGBMで出した7分位点の順をそろえる。次に、学習とは別に確保したデータを使い、実績が区間に入るよう幅を調整する（CQR）。各校正例で `sᵢ=max(q低(xᵢ)−yᵢ, yᵢ−q高(xᵢ))` を計算し、その校正分位点だけ上下の端を広げる（Eq.3）。全件で実績が区間に入る割合（周辺被覆率）は、高需要の例だけでも同じ割合になるという保証ではない。

## 信号の選び方は同じにして、渡す情報だけを替えた

どの条件でも同じ目的関数で、各候補を選んだ後の60秒間を模擬計算（rollout）し、実際に選べる候補すべてを比較する。7交差点は各1候補、残る2地点は各8候補なので、1段階の組み合わせは8×8=64通り。

入力だけを、将来を使わない条件（no-future）、判断時点までの観測から作った予測、5秒刻みで将来を知る条件（event oracle）に替える。論文の「因果的予測」は判断時点で利用可能な情報だけを使う予測であり、施策の因果効果を推定する意味ではない。

## 分の途中で確定値を使わない

たとえば12:03:20に信号を選ぶなら、12:03の1分間の交通量はまだ分からない。12:02が終わった時点で分m（12:03）の予測を作り、12:03:20までに実際に流入した分を引いて、残りの未観測区間へ配る。これが分mの判断にm−1起点の予測を使う時刻修正である。

将来を知る条件でも、シミュレーションで先を計算する最初の時間区分（slot）には新しい流入を足さず、次の区分から、流入元を将来離れる車（source departure）を入れる。出発した時刻とネットワーク境界に着く時刻は別だ。また、内部計算は比例配分だが実行側は先着順（FIFO）なので、競合時には台数の絶対差の総和（L1）で2.5台のずれが残る。この制御器に将来の流入を渡しても、制御全体が最適になるわけではない。

## 検証2日で採用条件を満たさなかった理由

予測が外れたのか、予測を渡しても信号を選び直せないのかを分けるには、まず、将来情報が効くように作った人工交差点で手順を試す。そこで費用が下がっても、実記録から組み立てた需要で同じ効果が出るとは言えない。

時刻を修正した検証2日では、待ち行列の改善率は将来を知る条件で−1.38%、判断時点までの情報で作った予測で−2.56%だった。採用条件を満たさなかった（NO_GO）が、著者は改善が見られなかった程度を測るため、設定を変えず最終テストを1回実施した。その後、指標を上流への滞留（spillback）に替えて成功とは判定していない。

## 最終7日間で著者が測った結果

[一次資料：原論文 Table 2–3 / Fig.4 / §6](https://arxiv.org/pdf/2610.06992v1)の著者報告では、流入口のMAEは1.9805→1.9007（−4.03%）、進行方向別では0.8446→0.8115（−3.92%）だった。名目90%の予測区間に実績が入った割合は、全体で90.72%、実績を見て選んだ高需要群で75.66%だった。

人工交差点では、将来の流入を知ると制御器の内部計算での費用が3195.8→1230.0（−61.5%）に下がった。次は実記録から需要を再構成した最終7日間の結果。正の改善率は指標が減ったことを示す。

| 比較：将来を使わない条件が基準 | 改善率 | 95%信頼区間 | 改善した日 |
| --- | --- | --- | --- |
| 判断時点までの情報で作った予測：待ち行列 | −6.09% | [−12.94,1.15] | 3/7 |
| 将来の流入を知る条件：待ち行列 | −3.39% | [−7.24,3.08] | 4/7 |
| 将来の流入を知る条件：上流への滞留 | +3.78% | [−1.25,12.26] | 5/7 |

待ち行列の7日平均は、将来を使わない条件で851,022、予測ありで902,821、将来の流入を知る条件で879,866 vehicle-seconds（列にいた台数を時間方向に足した値）。信頼区間は同じ日どうしを組にした7日分を50,000回再標本化して求めた。すべてゼロを含み、安定した改善も一貫した悪化も示していない。再標本化を増やしても、独立した元の日数は増えない。

## 人工の補充例を操作する

交通を再実装する代わりに、補充量aと需要Dの絶対差|a−D|を費用とする1期間の例を動かす。人工データの同じ600件に対し、一定値の基準予測（historical）、誤差を減らした予測、需要を正確に知る比較条件（oracle）を試す。補充量の候補は{8}、{4,8,12}、{0,1,2}の3通り。

候補を替えても予測自体は同じなので、MAEの改善幅は変わらない。需要に応じて最適な補充量が変わる場合にだけ、予測を使って費用を減らせるかを確かめる。交通での先着順処理や、判断後の状態を次の判断へ戻す処理は含めない。

人工データのMAEは2.707→0.637。補充量が{8}だけなら、需要を知っても8しか選べず、費用は下がらない。{4,8,12}なら、改善した予測でも需要を知る条件でも費用はゼロになった。{0,1,2}では選択肢が3つあっても、需要に対してどれも小さく、常に2を選んだ。100%削減はこの人工例に限り、小売や交通での効果を予測した値ではない。

## 確認の範囲

CONFIRMED：同じMAE改善でも、選べる補充量によって費用が下がる場合と、変わらない場合があることを人工例で確認した。

NOT OBSERVED：原論文の最終評価では、待ち行列の安定した削減を観測しなかった。これは著者報告で、Labは元の交通データで再実行していない。仕組み全体の検証はPARTIAL。

NOT TESTED：元の交通記録、ExtraTrees・LightGBMの学習、CQRによる区間の校正、交通制御器、別の都市・季節、小売への適用。原論文の評価も1都市1カ月、テスト7日、再構成需要を用いた集約シミュレーションであり、現地の信号制御の導入試験でも、CityFlowの性能評価でもない。将来を知る条件が採用基準を満たさなかった後に、確率的MPCやCVaRによる制御を試したわけでもない。

## 実行する

次のコマンドをリポジトリの直下で実行する。実験にはPythonの標準ライブラリだけを使い、外部APIには接続しない。

```bash
uv run --no-project papers/traffic-forecast-to-decision-value/run.py
uv run paper-lab build
```

説明は `lab.yaml` と `README.md`、実験は `run.py` と `results.json`、原論文と実験の対応は `mapping.md` にある。HTMLはビルドで生成する。
