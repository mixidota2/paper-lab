# LIGE-GRは、先に選んだ動画を見ながらおすすめの並びを作る

MetaのLIGE-GRはすでに集めた動画候補から、おすすめに載せる順番を一つずつ決めます。既存のモデルが各動画に対する視聴や反応を個別に予測し、追加したモデルが先に選んだ動画を見て後続の候補の予測を更新する仕組みです。一覧全体を評価する際も、多様性などの既存のルールを使います。

著者が両サービスの従来方式と7日間比べたのは、各段階で最も評価の高い並びを一つだけ残す基本構成です。視聴面での滞在時間はInstagram Reelsで1.14%、Facebook Videoで0.72%増えましたが、Facebook Videoの再生数は0.52%減りました。Instagram Reelsで複数の並びを残す構成を試したのは別の比較です。

優先度：Must Read。Labは2026年9月21日に一次資料を確認した。

## 実行

リポジトリの最上位で次のコマンドを実行する。最初のコマンドで人工実験の結果を更新し、次のコマンドでLabのページを生成する。

```sh
uv run papers/lige-gr-meta-listwise/run.py
uv run paper-lab build
```

## 概要

著者は動画を個別に評価する既存のモデルを残し、次に出す動画の評価に、同じ一覧ですでに選んだ動画を使った。推薦する順番を決める部分から切り替えられる。従来方式との本番比較で使ったのは、追加の予測器を動かし、探索の各段階で並びを一つだけ残す基本構成だ。

## 課題

高得点の動画だけを並べても、同じような話題が続くと、後から出す動画の価値が変わる。既存の多様性のルールや業務上の禁止条件はこれを補うが、動画の反応を個別に予測するモデルは先に選んだ動画を見ない。LIGE-GRが扱うのは、すでに集めた数百件から約10件を選んで並べる処理だ。全カタログから動画を表すコード（SID）を生成する方法ではない。

## 中核アイデア

既存の予測器（CF）は、候補ごとの表現を一度だけ作る。追加の予測器（CA）は、先に選んだ動画を参照し、後続候補の予測を更新する。探索処理（Palette）は、その予測を使って一覧全体の評価値が高くなる順番を探す。従来の制約とCFは残るので、追加の経路を止めて元の順位付けに戻せる。

Labでは、[Sona](https://mixidota2.github.io/paper-lab/papers/sona-yandex-music.html)や[Gryphon-v2](https://mixidota2.github.io/paper-lab/papers/gryphon-v2-cascade.html)のように複数段を入れ替える研究と区別する。[OGR](https://mixidota2.github.io/paper-lab/papers/ogr-once-generated-ranked.html)や[GenPage](https://mixidota2.github.io/paper-lab/papers/genpage-netflix-homepage.html)と比較する場合も、候補をどこから得て、どこまで並びを生成するかを分ける。

## モデルと手法

[方法](method.md)に、CFとCAの分担、利用者が各位置に進む確率、Paletteの探索、従来方式に戻す手順を示す。人工候補で比較した5条件の図も収録した。

## 仕組みが働く理由

探索で次の位置を決めるたびに大きなCFを計算し直さず、追加した小さなCAが保存済みの表現から動画間の関係を予測する。後ろの位置は、その位置まで利用者が進む確率で重み付けする。届かない位置の価値を過大に見積もりにくい一方、次へ進む確率の誤差は後ろの位置ほど積み重なる。初めの候補一覧にない動画は選べない。

## 著者が報告した比較結果

一次資料：[原論文の§4–5、表1–4](https://arxiv.org/html/2609.18148v1)。従来方式と7日間比較したとき、Instagram Reelsは対照群と処置群が各1.5%、Facebook Videoは処置群が約2%で対照群が同程度だった。両サービスで視聴時間の差はp<0.001だった。

| 指標 | Instagram Reels | Facebook Video |
| --- | ---: | ---: |
| 視聴面での滞在時間 | +1.14% | +0.72% |
| 動画の再生数 | +2.28% | −0.52% |
| いいね・リアクション | +2.65% | +1.59% |
| セッション数 | +0.11% | +0.07% |

Facebook Videoでは視聴時間が増えたが、再生数は減った。Reelsの別の分析では、同じリクエストの候補から新旧方式で作った一覧を比べ、公開後72時間未満の動画の割合が0.66%下がった。

基本構成に追加した推論資源はCFの約10%に当たる。Reelsのリクエスト全体の応答時間は約7%、Facebook Videoの配信処理の平均レイテンシーは約2.2%増えた。測定範囲が異なるので比率は直接比べられない。候補を絞った場合に60–80%増えたのはCA経路の処理件数で、リクエスト当たりの時間がその割合だけ減ったわけではない。候補数とトラフィックをそろえると、6通り残す場合の追加資源は1通りの場合の約2.1倍で、CFの資源に対する約20%はその比較からの推定値だ。

Reelsの表3では、同じCAを使い、1通り残す基本構成と6通り残す2条件を別々に比較した。残す数だけを変えた条件の視聴時間は0.05%増えた。継続確率で重み付けし、動画の長さに応じて残りの枠の価値も見積もる条件では0.69%増えた。各値の対照は基本構成であり、従来方式に対する1.14%増に足し合わせることはできない。

## 人工実験

Labは、同じ7候補から3本を選び、個別採点、先に選んだ候補も使う幅1の探索、継続確率も使う幅6の探索、候補を上位3本に絞る探索、予算に達して従来方式へ戻る条件を比べる。同じ禁止ルールを適用し、可能な並びをすべて調べた場合の最大値も求める。予測値は固定した人工値で、予測モデルは学習しない。

## 結果

Labが同じ評価式で採点すると、個別採点と幅1の条件はどちらも14.732だった。この条件では、先に選んだ動画を考慮するだけで改善する様子は見られなかった。継続確率と残りの価値を使い6通り残すと21.754になったが、全列を調べた最大値22.512には届かなかった。候補を上位3本に絞っても幅6の結果は21.754のままで、評価回数は72回から12回に減った。候補4は外れるため、全候補を使った場合の最適な並びは作れない。この比較は評価回数を数えたもので、GPUの処理能力は測っていない。

## 確認した範囲

Labは仕組みの一部を確認した（Mechanism: PARTIAL）。重複と禁止された並びを除き、各位置に達する確率で評価を重み付けした。全列の最大値との比較、候補を絞ると作れる並びが減る例、探索の予算に達すると従来方式と同じ並びを返すことを確認した。

## 確認していない範囲

実運用での性能、規模を増やした場合の挙動、本番適用は未検証（NOT TESTED）。CAの学習、実ログでの正規化エントロピー、A/Bテスト、GPUの処理能力、実際の時間で探索を打ち切る動作、紹介する動画の鮮度や投稿者の多様性への効果は再現していない。残りの価値の見積もりが真の最大値以上になる保証や、幅を限った探索で最適解を得る保証はない。

## 実装

`score()` は位置ごとの到達確率を使って並びを採点する（式9）。`future()` は残りの位置の価値を見積もる（式12・14）。`decode()` は、制約を満たす並びを探索し、予算に達したら従来の手順へ戻る（Algorithm 1・2）。Labは同じグループの候補に減点する規則をCAの代わりに使う。Paletteの公式実装ではない。

Pythonの標準ライブラリだけを使う。候補を固定しているため乱数は使わない。結果はコードと同じフォルダーに保存する。
