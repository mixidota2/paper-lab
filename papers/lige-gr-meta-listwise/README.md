# LIGE-GR: A Smooth Leap from Ranking to Generative Recommendation in the LLM Era

MetaのLIGE-GRはすでに集めた動画候補から、おすすめに載せる順番を一つずつ決めます。既存のモデルが各動画に対する視聴や反応を個別に予測し、追加したモデルが先に選んだ動画を見て後続の候補の予測を更新する仕組みです。一覧全体を評価する際も、多様性などの既存のルールを使います。

著者が両サービスの従来方式と7日間比べたのは、各段階で最も評価の高い並びを一つだけ残す基本構成です。視聴面での滞在時間はInstagram Reelsで1.14%、Facebook Videoで0.72%増えましたが、Facebook Videoの再生数は0.52%減りました。Instagram Reelsで複数の並びを残す構成を試したのは別の比較です。

優先度: Must Read。確認日: 2026-09-21。

## Overview

動画を個別に評価する既存の順位付けモデルを残しつつ、すでに選んだ動画との関係を次の動画の選択に反映する。既存の予測や業務上の制約を引き継げるので、運用の責任分担を保ったまま段階的に切り替えられる。Instagram ReelsとFacebook Videoの7日間のA/Bテストでは、視聴時間（Time spent）がそれぞれ+1.14%と+0.72%だった。いずれも、選んだ動画の並びを考慮する予測器（CA）を使ったbeam 1の基本構成での結果である。

## Problem

各動画を独立に採点して高得点順に並べても、似た話題が続けば、後から出す動画の価値は変わる。従来も制約を扱う層（CL）が多様性の確保や禁止条件の適用を担っていたが、予測器自体はそれまでに選んだ動画を考慮しない。LIGE-GRが変えるのは、数百件ある既存の候補から約10件の並びを作る部分である。全カタログを対象にSIDを生成する方式ではない。

## Core Idea

既存の予測器（CF）が各候補について作った表現を、すでに選んだ動画の並びを読む予測器（CA）が更新する。Paletteはその予測を使い、並び全体の評価値（ListVM）が高くなるように候補を探索する。既存のCLとCFは残しているため、追加部分を止めて元の順位付けに戻せる。

解釈: [Sona](sona-yandex-music.html)・[Gryphon-v2](gryphon-v2-cascade.html)のcascade置換とは移行単位が違う。[OGR](ogr-once-generated-ranked.html)・[GenPage](genpage-netflix-homepage.html)のslate統合とも、候補空間と生成責任を分けて比較したい。

## Why It Might Work

次の動画を選ぶたびに重いCFを再計算するのではなく、小さいCAで並びの中の関係を見直す。たとえば同じ話題が続いて価値が下がる場合や、別の動画を組み合わせると価値が上がる場合を扱う。既存モデルの予測を使いながら探索を追加できるのはこのためである。後ろの動画ほど、視聴者がそこまで進む確率で重み付けすれば、届かない価値を過大に見積もりにくい。ただし、候補に入っていない動画は選べず、継続確率の推定誤差は後ろの位置ほど積み重なる。

## Evidence

[原典 §4–5・Tables 1–4](https://arxiv.org/html/2609.18148v1) の著者報告。Reelsはcontrol/treatment各1.5%、FBはtreatment約2%と同程度のcontrolで、両方7日間。Time spentの差は両面でp<0.001。

| 指標 | Reels | Facebook Video |
| --- | ---: | ---: |
| Time spent | +1.14% | +0.72% |
| Video views | +2.28% | −0.52% |
| Likes / reactions | +2.65% | +1.59% |
| Sessions | +0.11% | +0.07% |

Facebook Videoでは視聴時間が増えた一方、視聴回数は減った。体験全体の改善を、すべての指標が改善したという意味で受け取らない。Reelsで推薦した動画の内訳を調べると、公開後72時間未満の動画の割合も−0.66%だった。

基本構成で増えた推論資源は、CF部分が使う資源の約10%に相当する。サービス全体の計算量に対する割合ではない。Reelsではリクエスト全体の応答時間が約+7%、Facebook Videoでは配信処理の平均レイテンシーが約+2.2%だった。測定範囲が異なり、直接比較はできない。候補を絞るとCA経路が単位時間に処理できる量は60–80%増えたが、処理時間が60–80%減ったわけではない。beam 6が必要とする追加資源はbeam 1の約2.1倍で、CF比の約20%はこれらの数字から求めた値である。

Table 3では、どの構成もCAを使う。探索幅だけをbeam 6に広げると視聴時間は+0.05%で、評価関数をgoldenに替え、動画の長さを考慮した将来価値の推定も使うbeam 6では+0.69%だった。各行はbeam 1の基本構成と別々に比べた値なので、従来方式と比べた+1.14%にそのまま足すことはできない。

## Executable Understanding

同じ7候補、3枠、禁止条件のもとで、個別採点、CA beam 1、golden beam 6、上位だけを残す絞り込み（top-3 pool）、処理の予算を使い切った場合を比べる。全順列を列挙して最大値も求める。予測値は人工的に設定して固定したため、探索で高得点の並びを見つけても、CAの学習がうまくいく証拠にはならない。`uv run papers/lige-gr-meta-listwise/run.py`。

## Results

視聴が続く確率で重み付けした同じ評価値で比べると、動画を個別に評価した並びとCA beam 1の並びは、どちらも14.732だった。この条件ではCAだけによる順位の改善は観察できなかった（NOT OBSERVED）。golden beam 6では21.754になったが、全順列を調べたときの最大値22.512には届かなかった。候補を絞り込んだとき（top-3 pool）も、このbeam設定の評価値は21.754のままで、評価回数は72から12に減った。ただし候補4が外れるので、全候補を使ったときの最適な並びは作れない。この比較で数えたのは評価回数であり、GPUの処理能力は測っていない。

## What We Verified

仕組みを一部確認した（Mechanism PARTIAL）。有限個の候補から重複や禁止された並びを除き、各位置まで視聴が続く確率を掛けて、並び全体の評価値を求めた。処理の予算を使い切ったときの並びが、動画を個別に採点した基準方式（pointwise baseline）の結果と一致することをassertで確認した。全順列の最大値との比較に加え、候補を絞ると探索できる並びが減ることも記録した。

## What We Did NOT Verify

性能、規模拡大、本番への適用は未検証（Performance / Scaling / Production applicability: NOT TESTED）。CAの学習、実ログでのNE、A/Bテストの差、GPUの処理能力、実際の経過時間で打ち切った場合の動作、投稿の鮮度や投稿者の多様性への効果は再現していない。将来価値の見積もりが実際に得られる最大値以上になる保証はなく、有限幅のビーム探索で最適解が見つかる保証もない。
