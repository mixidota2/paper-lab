# Balancing Trial and Reorder: A Hybrid Sequential Transformer–GBDT Ranker for On-Demand Delivery

Woltは、購入履歴から作った店ごとのスコアを使い、配達可能な店の表示順を決めました。初期版のA/Bテストでは飲食店への初回注文の指標が5.5%、全体の注文転換率が0.16%上がりました。新規店をさらに重視したV2では、過去の注文で評価すると、6カ国中5カ国で再注文の店の順位が従来方式より悪くなりました。

選定: Worth Reading。原論文の確認日: 2026-09-21。

## 実行方法

配布された `run.py` を保存し、`python run.py` を実行すると、同じフォルダーに `results.json` ができます。リポジトリでは、プロジェクトのルートから次のコマンドで合成実験とサイトの生成を実行できます。

```sh
uv run papers/uvr-wolt-trial-reorder/run.py
uv run paper-lab build
```

## Overview

Woltの研究チームは、利用者が新しい店を試す機会を増やしつつ、いつもの店も見つけやすくする順位付けを調べました。Transformerで利用者の購入履歴を読み、次に選びそうな店のスコアを作ります。CatBoostはそのスコアをほかの特徴量と合わせて、店の表示順を決めます。

著者は主要10カ国で利用者を半分ずつ無作為に分け、初期版（V1）を従来方式と2週間比較しました。飲食店で初めて注文する割合は5.5%、全体の注文転換率は0.16%増えました（後者はp=0.017）。新しい店をさらに重視したV2では、購入履歴を使った別の評価で、再注文した店を上位に置く指標が6カ国中5カ国で従来方式を下回りました。実際の再注文が同じ割合で減ったという意味ではありません。

## 配達できる店から、初めての店と再注文の店を探す

フードデリバリーでは、利用者の好みに合う店でも、その時点で配達できなければ表示候補に入りません。受付時間、配達先との距離、配達員の空き、店の混み具合が変わるため、候補は画面を開くたびに変わります。

購入履歴がある利用者について、著者は、初めての店への注文を「新規店への注文（trial）」、以前に注文した店への注文を「再注文（reorder）」と分けました。利用者自身の初回注文は、履歴がないため別に扱います。再注文が多いデータでは、注文全体の順位だけを見ると、新規店を見つけにくいままでも評価が良く見えることがあります。

## 購入履歴のスコアと現在の配達条件を組み合わせる

WoltのUniversal Venue Ranker（UVR）は、購入履歴からTransformerが出した店ごとのスコアを、CatBoostに渡します。V2では、初めての店に注文したセッションを重く扱い、再注文の順位も確認しながら重みを選びます。V3では、飲食店と小売の履歴を同じTransformerで読み、従来の4つの順位付けモデルを一つの仕組みにまとめました。

共有するのは、同じ国の飲食店と小売の履歴です。国をまたいで学習する設計ではありません。この事例では、履歴から学ぶ情報と、店や配達条件から判断する情報を分けて考えると、二つのモデルを組み合わせる理由が分かります。

購入履歴だけでは、よく注文する店が今も選びやすいとは限りません。たとえば配達料が高い場合、距離や料金を受け取るCatBoostは履歴のスコアと合わせて順位を変えられます。Transformerには履歴を読み取らせ、CatBoostには配達可能な店を今の条件で並べ替えさせます。

OTTOのGBDT対DNNの記事は二つのモデルを比較します。UVRでは、一方のモデルが出したスコアをもう一方の入力にします。RESTの記事と比べるなら、購入履歴をどこで処理し、どのモデルが表示順を決めるかを見ると違いが分かります。

モデルの構成、学習の手順、重み別の図は [method.md](method.md) にあります。

## Woltが報告した本番とオフラインの評価

一次資料は[原論文の表3〜5と第5〜6節](https://arxiv.org/html/2609.16407v1)です。以下はWoltの著者が報告した結果です。

著者は3回のA/Bテストで、登録利用者を毎回、利用者単位で無作為に半分ずつ分けました。V1とV2は主要10カ国で各2週間、V3は全稼働国で3週間試しました。店への初回注文を捉える指標（Merchant Trial Rate）と、サービス全体の日次注文転換率（Global CVR）を測りました。表の値は、各行の比較相手に対する変化率です。

| 比べた方式 | 店への初回注文の指標 | 全体の注文転換率 |
| --- | ---: | ---: |
| V1と従来の飲食店向け方式（FPR+SPR/CSR） | 飲食店 +5.5% | +0.16%（p=0.017） |
| V2とV1 | 飲食店 +0.45% | −0.05%（p=0.398） |
| V3と飲食店向けV2・小売向けRR | 小売 +1.31% | +0.04%（p=0.457） |

初回注文の指標は表の3比較とも有意水準5%で改善しました。V2とV3では、全体の注文転換率に統計的な差を確認できませんでした。これは、転換率が変わらないと証明したわけでも、再注文への影響を単独で測ったわけでもありません。V3では広告売上が有意に0.43%減りました。

過去の注文を使った別の評価（表4）では、飲食店を並べるV2を、当時稼働していた順位付けと比較しました。実際に注文した店の順位の逆数を平均する指標（MRR）は、新規店への注文では6カ国すべてで12.5%〜30.3%上がりました。再注文ではフィンランドだけが6.7%上がり、残り5カ国では1.4%〜27.3%下がりました。V1の新規店のMRR改善は7.5%〜19.8%です。複数の乱数シードで学習した1カ国の検証では、改善率の標準偏差が平均改善率の約10〜30%に当たりました。

著者は、新規店のMRRを落とさず、再注文のMRR低下を従来比15%以内に抑える設定のうち、新規店のMRRが最も改善する設定を探しました。報告された探索では、ドイツでこの条件を満たす設定が見つかりませんでした。この設定選びの条件とは別に、配信前の検査では再注文MRRが悪化すると警告しますが、それだけで配信を止めるわけではありません（§4.5）。

WoltはFlyteとKubernetesで国別に毎日学び直します。学習時に見ていない店舗IDのスコアをTransformerは出せないため、新店を追加することも毎日更新する理由です。配信時はCPUでTransformerを動かします。特徴量の取得から応答データの整形まで含めると、著者が報告した応答時間の99パーセンタイルは約60 msです。

## Labは重みだけを変えて、注文区分ごとに順位を測る

Labは、以前に注文した店と初めて注文する店の2候補がある合成データを使います。各セッションには、2店のスコアと距離の差を表す合成の特徴量と、実際にどちらを選んだかを表す正解があります。学習には同じ400セッションを使い、正解店ともう一方の店を比べる線形モデルを4回学習します。再注文の重みは1のまま、新規店への注文の重みだけを1、2、3、5に変えます。

学習に使わなかった別の400セッションで、注文した店が1位なら1、2位なら0.5と数えます。新規店への注文と再注文を別々に集計し、それぞれのセッション内で得た逆順位を合計して、その区分のセッション数で割るとMRRになります。

重みの比較とは別に、正解ラベルの確率の合計が1になることと、最も高いスコアを持つ店でも配達できなければ候補から外れることを確かめます。TransformerやCatBoostは学習しません。

## 重みを変えると、合成データでは二つのMRRが逆に動く

設定を1から3へ変えると、この合成データでは、新規店への注文のMRRが0.5から1.0に上がり、再注文のMRRは1.0から0.5に下がりました。設定5でも、設定3と同じ値でした。この例で確かめたのは、二つの注文区分のどちらを学習で重く扱うかによって、モデルが付ける順位が変わることです。実際の注文を使っても新規店の順位が良くなるとは、この結果だけでは言えません。

## Labが確かめていないこと

Labは実際のTransformerやCatBoostを動かしていません。国別の購入履歴を使った精度、データ量が増えたときの処理、本番の応答時間約60 ms、A/Bテストの結果は再現していません。

論文のV3では、飲食店の履歴を小売にも使えるようにしただけでなく、小売にもTransformerとCatBoostの組み合わせを導入しました。著者は、履歴を領域ごとに分けた同じ構成との比較も、CatBoostの入力からTransformerのスコアだけを除いた比較も報告していません。小売で初回注文の指標が上がった理由を、領域間の履歴共有だけに絞ることはできません。

## 実行コードの読み方

`fit()`は、新規店への注文と再注文でセッションの重みを変え、2候補を並べる線形モデルを学習します。`metrics()`は、実際に注文した店の順位から、二つの区分のMRRを別々に計算します。`smooth_target()`は正解ラベルの確率を配分し、`eligible_scores()`は配達できる店のスコアだけを返します。

`run.py`はPython標準ライブラリだけで動きます。乱数シードは固定です。実行すると、同じフォルダーの`results.json`に結果を書き出します。
