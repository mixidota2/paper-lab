# RetailBench：個々の操作から180日の店舗運営へ

## Overview — 複数の業務を続けて動かす

RetailBenchは、価格・補充・棚・仕入先・資金繰りを180日間つなぐ店舗運営の評価環境である。

## Problem — 遅れた結果まで追えるか

Dominick’sのデータを基に96商品・20カテゴリを構成し、棚40商品、在庫容量15,000個、初期資金30,000、日額家賃600という条件で運営する。
需要やニュースの内部効果は隠される。

## Core Idea — 著者の主張と解釈

著者の主張：情報収集、仕入先選択、価格変更、補充を続ける過程で、不完全な情報収集、表面的な判断、継続する方策の欠如を診断する。

解釈：研究地図では運用中に店舗業務を操作するLLMの評価に当たり、InvEvolveの設計時の方策探索やSabreAgentの固定した在庫制御とは評価単位が異なる。

## Why It Might Work — 安い仕入れにも後の負担がある

解釈：安い仕入先を選んでも返品が増えれば収入は減り、棚へ載せなければ販売機会を失うため、ツール操作の正否だけでは長期の運営能力を測れない。

## 二つの局所会計を区別する

原論文の診断は[§5.2・§5.3](https://arxiv.org/html/2603.16453v3#S5.SS2)。付録A.1は返品を収入から差し引き、A.2.8のplace_orderは発注時に仕入費用を支払います。A.4のOracle停止条件は負の現金10日連続です。以下は公式シミュレータの再実装ではありません。

基本会計は単位粗利 `p*(1-r)-c`、日末現金 `C_t=C_(t-1)+q*粗利-R`。当日全額返金、返品物は廃棄、納期0、在庫持越0、期待値会計、借入無制限と仮定します。現金が負でも計算を続けるので、生存日数や純資産と呼びません。同点境界は `p*(r_A-r_B)=c_B-c_A`。価格0では返品率による境界を解けません。

手元資金モードは `q_t=min(需要,floor(max(日初現金,0)/原価))`。原価は正、需要は整数。仕入支払→即日納品と販売→同日期待返金→家賃の順です。欠品は失注し、翌日に持ち越しません。日末現金が負なら局所破綻として停止し、翌日以降は取引も家賃も0です。原論文の10日規則とは違います。販売0の返品比率は未定義、端数の返品数は期待値で実顧客数ではありません。

初期現金40・需要10・価格10・家賃35・2日では、A(原価4、返品15%)の現金は50→60、B(原価5、返品0%)は45→55。Bは単位粗利が高くても、仕入数量8→9に制約され逆転します。家賃80ではAは5→−70.5で2日目に停止します。両社の潜在需要を変えた結果ではありません。

## 再実行と保存

`uv run run.py` は保存済みresults.jsonを再生成します（このディレクトリで実行）。画面では任意の数値を直接変更し、JSONを書き出せます。JSONのinputsを再読込するとoutputは再計算されます。`uv run run.py --input comparison.json` でも入力を再計算して標準出力へ返せます。

Python標準ライブラリと小さなブラウザ計算だけを使います。数式・台帳の局所検証はCONFIRMED、論文全体の機構はPARTIAL。著者コード・学習・原論文性能・本番適用はNOT TESTED。実ブラウザの画面・キー操作・export/importもNOT TESTEDで、別環境での保護付き確認を残しています。

局所検査：リポジトリrootで `uv run --extra dev pytest tests/test_reference_comparisons.py`。Node.js 18以上がある場合、`uv run --extra dev python tests/check_reference_js.py` でJavaScriptの独立期待値とPythonとの120条件照合を実行できます。これはDOMや実ブラウザの検証ではありません。保護付きChromeが利用できる別環境では `uv run --with playwright tests/reference_browser.py` を実行し、360/1440pxの画面、任意値、キー入力、保存と再読込を確認します。CHROME_PATHと必要に応じREFERENCE_SITEを指定してください。検査内で127.0.0.1の一時HTTPサーバーを起動し、成功・失敗にかかわらず終了します。file://での確認とは区別します。

金額境界は入力数値の標準的な十進表記を厳密な有理数として扱います。PythonはFraction、ブラウザはBigIntの分子・分母で日々の会計を保持します。購入可否に許容差を加えず、セント等への丸めも行いません。現金0.3・原価0.1なら3個、0.29999999999999993なら2個です。内部の厳密値を表示・JSONへ出す段階だけ通常の数値へ変換します。数値入力として読んだ後の十進値が対象であり、入力欄で表せる精度を超えた桁の保存は保証しません。

保存形式schema 2には、教材仕様ID・版2.0.0、原典URL・版、指標や会計の規約を含めます。読込時はschema・教材ID・仕様版を照合し、inputsを再検証します。保存outputや説明メタデータは計算根拠にせず、現行の固定仕様で再計算・再出力します。旧schema 1や未知の仕様版を黙って読み替えません。署名付きの真正性証明ではありません。
