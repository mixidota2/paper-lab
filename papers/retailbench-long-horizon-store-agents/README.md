# RetailBench：言語モデルで180日間の店舗運営を評価する

## 概要

RetailBenchの著者は言語モデルにシミュレーター内の1店舗を任せ、何日間営業を続けられるかを調べました。エージェントは価格、補充する量、棚に並べる商品、仕入先を決めます。ある日の判断は後日の売上、返品、資金繰りに影響します。

著者は7つのモデルそれぞれで、営業を続けた日数を優先して試行を1つ選びました。上限の180日まで営業できたのはGPT-5.5とDeepSeek-V4-Proです。選ばれた試行で最も高かった純資産はGPT-5.5の24,350.98で、シミュレーターの内部情報を使えるルール方式の131,510.42の約19%でした。これらは選んだ試行の値で、各モデルの平均や実店舗の成績ではありません。

## 店舗の条件

著者はDominick’sの小売データをもとに、96商品を20カテゴリに分け、各商品に5社の仕入先がある1店舗を設定しました。棚に置けるのは40商品までで、在庫の上限は15,000個です。初期現金は30,000、家賃は1日600で、いずれもシミュレーター内の通貨単位です。

エージェントは需要やニュースの影響を直接知ることができません。在庫、価格、販売履歴、仕入先の条件などをツールで調べ、値付け、発注、棚の商品を決めます。入荷や販売、返品を経て変わった現金と在庫は、翌日の判断に影響します。安い仕入先でも返品が増えれば、購入時に節約した額をその後の返金が上回ることがあります。

## 著者が比べた試行

[一次資料の表1](https://arxiv.org/html/2603.16453v3)から、2つのLLM試行と比較用のルール方式を抜き出しました。

| 選ばれた試行 | 最終純資産 | 累積販売数量（個） | 営業日数 |
|---|---:|---:|---:|
| Oracle Policy | 131,510.42 | 267,998 | 180 |
| GPT-5.5（ReAct） | 24,350.98 | 136,405 | 180 |
| DeepSeek-V4-Pro（Plan-and-Act） | 10,120.90 | 164,417 | 180 |

著者はモデルごとの有効な試行を、営業日数、最終純資産、累積販売数量の順で比べ、1つずつ選びました。GPT-5.5は費用のためReActだけで実行しました。掲載結果は、実行方式や条件を揃えた全試行の平均ではありません。Kimi-K2.6は130日、残り4モデルは58〜73日で終了しました。DeepSeek-V4-ProのほうがGPT-5.5より多く売りましたが、ここで比べたのは個数であり、売上金額ではありません。

Oracle Policyは、LLMには見えない情報を使うルール方式です。LLMと同じ情報を与えた対照でも、あらゆる施策の中で最適な方式でもありません。本文§3.3と付録式(18)では未着の発注を純資産に含めるかの記述が揃っていないため、表では著者の値をそのまま使います。

## 著者が見つけた失敗のパターン

著者は、対象商品の選び方、判断前の情報収集、情報を使った判断、あとから結果を追う行動を調べました。そこから、情報が足りないまま決める、目に見えやすい条件に偏る、必要な商品を継続して見直さないという3つの傾向を報告しました。全LLM試行の発注明細では、同じ商品の中で品質が最高の仕入先を選んだ割合が21.5%、価格が最低の先を選んだ割合が55.6%でした。品質は直接見えないので、返品率などを手掛かりにする必要があります。2つの割合は別々の指標です。

著者は、1日に対象とした商品を、選ばれたLLM試行で0.95〜7.89種類、Oracle Policyで38.00種類と報告しました。本文5.3節は照会と操作の両方、付録A.5の式(20)は発注や値付けなど状態を変えた操作だけと説明しており、照会だけの商品の扱いは記述が揃っていません。どちらも売れた種類数や個数ではありません。著者は行動と成績を合わせて分析しましたが、個々の行動の因果効果を求めたわけではありません。運営中にLLMが複数の判断をする点で、設計段階に方策を探すInvEvolveやSabreAgentとは評価対象が異なります。

## Labで変えられる条件

Labは、販売価格、潜在需要、家賃、初期現金、日数をそろえて仕入先2社を比べます。これらの共通条件も、仕入先ごとの原価と返品率も変更できます。現金が足りなくても仕入れる基本会計と、手元にある現金の範囲で前払いする方式を切り替えられます。公式シミュレーターでLLMに運営させる実験ではありません。

旧固定例は価格10、扱う商品ごとの需要が1日10個、初期現金3,000、家賃600、30日間です。原価4・返品率30%の仕入先では、1個売ったときの返品込みの粗利は3です。原価5・返品率5%の仕入先では4.5です。1日8商品を扱うと30日後の現金はそれぞれ−7,800と−4,200、38商品では19,200と36,300です。現金が負になっても計算を続けるため、ここで得る数値は営業日数ではありません。

仕入先を入力して比べる図の初期条件では、30日後の現金はAが3,000、Bが12,000です。Bの返品率を20%に変えると同額になります。高い粗利が常に有利とは限りません。手元資金モードで初期現金40、需要10、価格10、日額家賃35とすると、Aは原価4・返品率15%で2日後に60、Bは原価5・返品率0%で55です。Bの粗利は高い一方、買える数量は初日に8個、2日目に9個に限られます。家賃を80にすると、Aは1日後に5、2日後に−70.5となって止まります。

## 計算と入力の範囲

基本会計は1個あたりの粗利を `p*(1-r)-c`、日末現金を `C_t=C_(t-1)+q*粗利-R` で計算します。pは販売価格、rは返品率、cは仕入原価、qは販売数、Rは日額家賃です。納期は0、在庫は翌日に持ち越さず、返品は同日に全額返金して商品は廃棄します。返品数に端数が出るのは期待値だからです。基本会計で販売数が正なら、AとBの最終現金が同額になる条件は `p*(r_A-r_B)=c_B-c_A` です。販売数が0なら、仕入先にかかわらず現金は同額になります。価格が0なら返金額は返品率によらないため、Bの返品率について解けません。

手元資金モードでは、日初の現金で買える整数個数と潜在需要の小さい方を仕入れます。発注時に支払い、即日納品・販売し、期待返金額と家賃を引きます。需要を満たせない分は翌日に持ち越しません。日末の現金が初めてマイナスになった日は取引と家賃を計上し、翌日以降は取引も家賃も0にします。論文のOracle Policyが負の現金を10日連続で記録した場合に止まる規則とは別です。販売数が0のとき、販売数に対する返品の割合は定義しません。

金額の比較は、入力を数値にしたあとの十進表記を、分子と分母が整数の数として扱います。PythonはFraction、JavaScriptはBigIntを使い、購入できるかを判定するときに許容差や通貨単位への丸めを入れません。現金0.3で原価0.1なら3個買えますが、現金0.29999999999999993なら2個です。表示やJSONの出力では通常の数値に戻します。入力欄で表現できない桁までは保存しません。手元資金モードの需要は0〜9,007,199,254,740,991の整数に限ります。

## 再実行と保存

配布された `run.py` を `python run.py` で実行すると、標準ライブラリだけで計算し、同じフォルダーの `results.json` を再生成します。既存の入力を計算するには `python run.py --input comparison.json` を実行します。初期の固定例、著者報告、仕入先比較の結果は、JSONの別々の項目に保存します。

図のJSONは保存形式schema 2で、教材仕様IDと版2.0.0、論文の版とURL、入力と結果を記録します。読み込み時は形式・仕様を照合し、保存した結果ではなく入力から現在のコードで再計算します。旧schema 1や未知の仕様版はそのまま読み替えません。

ビルドは配布する `model.js`・`interactive.js`・`run.py` のSHA-256を `implementation.json` と `implementation.js` に記録します。これら2つの生成ファイル自身はハッシュの対象外です。`sha256sum model.js interactive.js run.py` で配布ファイルと照合できます。Pythonの `pack()` は実行時の `run.py` のハッシュを記録します。ビルドせずにJSモデルを直接使った場合は `status: unavailable` です。ハッシュはコードの内容を識別するもので、署名や公開コミットを証明するものではありません。

## 確認した範囲

Labでは、固定例の240日分の収支と、仕入先の同点・逆転、手元資金で買える上限、停止後は取引しないこと、価格や販売数が0の場合を確かめました。公式環境でLLMに180日間運営させる試験は再実行していません。納期、賞味期限、ニュース、隠れた需要、棚で別の商品が代わりに売れる効果も対象外です。実店舗でのA/Bテストや棚割りの無作為比較ではありません。

リポジトリのルートで `uv run --extra dev pytest tests/test_reference_comparisons.py` を実行すると、会計の条件を確認できます。Node.js 18以上では `uv run --extra dev python tests/check_reference_js.py` でPythonとJavaScriptの120条件を比較できます。DOMや実ブラウザの確認とは別です。実ブラウザ向けの `uv run --with playwright tests/reference_browser.py` は `CHROME_PATH` と必要に応じ `REFERENCE_SITE` を指定し、一時HTTPサーバーを使ってキー操作、保存・再読込、画面幅360・1440pxでの表示を調べます。

対応表（`mapping.md`）に、確認した原論文の箇所と再現しなかった範囲を記録しました。
