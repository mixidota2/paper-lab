# HGenPush: A Heterogeneous Generative Recommendation Architecture for Industrial Push Notification Systems

KuaishouのHGenPushは通知で届ける動画の候補を二つの経路で探します。動画から探す経路は、動画の特徴を3段階で表したコード（SID）を生成します。投稿者から探す経路が生成するのは、利用者が好みそうな投稿者を表す2段階のコードと、動画の特徴を表す最初のコードの組み合わせです。この経路の目的も、投稿者を通知することではなく、その投稿者の動画を探すことです。

両方の経路から得た候補は、予備の順位付けを経ずに、最終的な順位を決めるモデルへ渡ります。著者が従来の通知システムと比較したA/Bテストでは、両経路を使う構成で1日あたりのアクティブ利用者数が0.181%増えました。同じ構成では、通知のクリック率とアプリ利用時間の差は5%水準で統計的に有意ではありませんでした。

## 手元で人工データの計算を実行する

配布された `run.py` はPython標準ライブラリだけで動きます。保存先で `python run.py` を実行すると、同じフォルダーに `results.json` を書き出します。リポジトリを取得した場合は、ルートから次を実行できます。

```bash
uv run papers/hgenpush-kuaishou-heterogeneous-push-gr/run.py
uv run paper-lab build
```

1行目で人工データの計算、2行目でサイトの生成を行います。

## Labは候補を集める処理と、次のコードの確率を確かめる

Labは、動画のコードと、投稿者のコードに動画の最初のコードを足した組み合わせを、別々の一覧で引きます。得られた動画を一つの集合にまとめ、重複を消して、すべてを同じ人工の最終スコアで並べます。

もう一つの計算では、利用者の関心を表す数値を固定し、前に選んだコードの埋め込みだけを変えます。次のコードの確率が変わることを確かめます。モデルを学習したり、推薦の精度を測ったりはしません。

人工データでは、動画の完全なコードで探すとv1が見つかり、投稿者のコードと動画の先頭コードで探すとv1とv2が見つかります。両経路をまとめて重複を消すと2件です。別の動画コードに属するv3は、同じ投稿者を表すコードでも入りません。人工の最終スコアではv2、v1の順になります。

前のコードを変える計算では、次に1番目のコードを選ぶ確率が約0.711から約0.250へ変わりました。同じ利用者の関心でも、前のコードで後の確率が変わることを示す人工例です。

## 確認した範囲と、読む資料

Labは、投稿者と動画の先頭コードの組み合わせで候補を絞れること、同じ動画が両方に出たときに一度だけ残すこと、すべての候補を同じスコアで並べることを確かめました。前のコードの埋め込みが次の確率に影響することも確認しました。重複を消す規則はLabで決めたもので、著者が本番で使った規則を再現したわけではありません。

Labは16層のデコーダー、投稿者のコードを作る量子化、クリックで利用者と投稿者の表現を近づける学習、GSISPOの更新を再現していません。論文のGPUでの最大QPSや本番のDAUも、独立には測っていません。表6の全構成の通知クリック率は、原論文の数値でも5%水準では有意ではありません。

仕組みの検証は一部（PARTIAL）です。精度や処理規模、本番への適用は検証していません（NOT TESTED）。モデルと図は [method.md](method.md)、論文と配布資料の対応は [mapping.md](mapping.md)、本番テストの報告は [lab.yaml](lab.yaml) にあります。
