ICLRはエージェントが直前のステップで書いた推論を空行で区切り、次のトークンを予測しやすい箇所から置き換える。採点モデル（scorer）は、そのトークンより前の履歴だけを読んで次のトークンの確率分布を出す。Fig. 2 と Eq. 1–9 では、分布全体の不確かさをエントロピーで測り、ブロックごとに平均する。

```text
Sₜ = (Rₜ, Aₜ, Oₜ₊₁)                  推論・行動・観測
hₜ = −Σᵥ pθ(v | cₜ) log₂ pθ(v | cₜ)    予測分布の不確かさ
H(Bᵢ) = Σₜ∈Bᵢ hₜ / |Bᵢ|               ブロック内平均
D = BottomK⌊0.8N⌋ {H(Bᵢ)}               低い順に[SKIP]へ置換
```

実際に出たトークン一つの意外さ（surprisal）を測る方法ではない。N=1なら置き換えず、採点モデルの入力が42Kトークンの上限を超える場合も、そのステップは置き換えを見送る。行動と観測は残し、書き換えた履歴を次の要求から使う。Random対照はトークン単位、ICLRはブロック単位なので、両者の削除率はそのまま比較できない。

Appendix B.3 の情報量の上界は、各ブロックの内容を見る前から削除する位置が決まっている場合に限る。採点結果を見て削除箇所を決める ICLR に、そのまま適用できる安全保証ではない。Corollary B.4 が示すのは、到達可能な各履歴で、残した状態 Z だけから元の履歴を使った場合と同じ行動分布を得られれば、やり取り全体の分布は変わらないという十分条件だ。

```text
πₜ(a | Zₜ,Wₜ) = qₜ(a | Zₜ) = π̃ₜ(a | Zₜ)
TV(Pπ,Pπ̃) ≤ 1 − ∏ₜ(1−εₜ) ≤ min(1,Σₜ εₜ)
```

Wは消す推論。εは、元のエージェントと推論を削ったエージェントが同じ履歴に到達したときの、次の行動の確率分布の差の上限だ。同じ環境と初期状態で、次の行動の分布が毎回一致するなら、やり取り全体の分布も一致する。状態をファイルに書いただけでε=0になるわけではない。
