# エージェントは、前の推論をどこまで消せるか

## Overview

著者は、長い作業を進めるエージェントが、以前の推論をすべて読み直す必要があるかを調べた。提案手法の ICLR は、エージェントが次に行動する前に、直前の推論を段落に分ける。別のモデルが、これまでの履歴から予測しやすいと判定した段落を削り、実際の行動とツールが返した情報は残す。

WorkBuddyBench の 260 課題では、同じ実行モデルの平均報酬が 0.699 から 0.718 に上がった。入力トークンは 25.5%、出力は 14.4%、キャッシュからの読み出しは 33.3% 減った。ただし、コード、オフィス、Web の3領域では報酬が下がった。別の80課題では、ICLR の平均報酬は 0.7376、推論をすべて消した場合は 0.7178 だった。

著者は、次に使う情報が推論にしか残っていない場面と、コードやファイル、ツール結果などに残っている場面も比べた。モデルが後で同じ制約を考え直したり、計画を立て直したりした割合は、前者の 52 場面で 67.31%、後者の 213 場面で 36.15% だった。この比較は、記録の保存先と後続の行動に関係があることを示す。保存すればいつでも推論を消せるという意味ではない。

## Problem

長い作業では、モデルが行動を決めるたびに、それまでの履歴を入力する。すでにコードに反映した判断も毎回読ませると、同じ説明の処理に費用がかかる。一方、その判断にしか残っていない制約を消すと、モデルは前の作業をやり直したり、別の結果にたどり着いたりする。

完成済みの回答を後から短くする場合と違い、この論文では作業の途中で履歴を変える。そのため、削った文章の量だけを測っても、作業全体の費用や結果は分からない。

## Core Idea

著者は、行動モデルを再学習せずに、直前の推論を履歴から削る手法を提案した。何を消すかは、別の固定モデルがそれまでの履歴から予測した結果で決める。

Labでは、消す文章の量よりも、後で必要になる情報を別の記録から読めるかに注目した。ファイルに書いただけでは、後続のモデルが読めることも、その費用が減ることも保証されない。

## Method

### ICLR が削るのは、直前の推論だけ

エージェントの 1 ステップには、モデルが書いた推論、実際に選んだ行動、環境から返った観測がある。著者は、DeepSeek-V4-Flash が行動を終えるたびに、そのステップの推論だけを短くした。行動、ツールの引数、観測、最終回答は元のまま残した。最初の要求には、まだ直前の推論がないため、この処理をしない。

ICLR は推論を空行で区切り、各段落を次の手順で採点する（図 2、式 1〜9）。

1. 固定した Qwen3.5-9B が、システム指示、ツールの定義、これまでの履歴を順番に読む。各位置で次に出るトークンの確率分布を求める。
2. ICLR はその分布のエントロピーをトークンごとに求め、段落内で平均する。ここで測るのは候補全体の予測のばらつきで、実際に出たトークン 1 個の意外さではない。
3. ICLR は平均エントロピーが低い方から、段落数の 80%（端数は切り捨て）を `[SKIP]` に置き換える。段落が 1 つしかないときや、採点用の入力が 42,000 トークンを超えるときは、その回は削らない。
4. エージェントは置き換えた履歴で次の行動を選ぶ。後の呼び出しでも、削った段落は元に戻さない。

80% は段落を数えた割合で、削ったトークンの割合ではない。著者のランダム削除はトークンを単位にするため、2 つの割合は同じものを表さない。

### 途中で削ると、その先の作業も変わる

以前の推論を消したことで、モデルが別のツールを呼ぶとする。そのツールは別の結果を返し、次のモデル呼び出しで読む履歴も変わる。作業全体の費用を測るなら、削った量だけでなく、その後の入力と出力、呼び出しの回数まで数える。入力に含まれるキャッシュ読み出しは、合計へもう一度足さない（付録 B.6、D.2）。

付録 B.3 の情報量の上界には、段落の中身とは無関係に削除位置を定めるという前提がある。段落を採点してから決める ICLR に、そのまま当てはめることはできない。一方、系 B.4 では、残した履歴だけで元と同じ次の行動分布が得られるなら、同じ初期条件と環境で作業全体の分布も変わらないと示した。

```text
πₜ(a | Zₜ,Wₜ) = qₜ(a | Zₜ) = π̃ₜ(a | Zₜ)
TV(Pπ,Pπ̃) ≤ 1 − ∏ₜ(1−εₜ) ≤ min(1,Σₜ εₜ)
```

Z は残した情報、W は消した推論。ε は、同じ履歴に到達した 2 つのエージェントが次の行動を選ぶ確率分布の差の上限だ。定理 B.3 は、この差が積み重なる範囲を示す。コードへ情報を書いたという事実だけでは、モデルがそれを読んで同じ行動を選ぶことも、ε が 0 になることも保証しない。

## Why It Might Work

過去の推論に「入力に欠損があれば処理を止める」とだけ書いてある場合、推論を消すと、エージェントはその制約を失う。コードに実際の検査が残り、エージェントがコードを読み直せる場合は、同じ制約を推論以外から確認できる。

著者が途中のコードをディスクに保存した後で推論を消した比較では、採点結果は 0.7587 のままだった。一方、モデルが後で書いた推論は 1,289 から 3,222 トークンに増えた。別の記録から判断をやり直せる場合でも、その確認に使う処理は残る。

著者は別に、31 課題の 265 場面を使い、Qwen の内部表現から後の推論再利用を予測した。課題単位で分割を入れ子にして評価した AUROC は 0.8444 だった。内部表現の一部を元に戻す実験は 8 課題の 47 場面を使っており、対象は実行モデルの DeepSeek ではなく、固定した Qwen だった。元と同じ最終層の値を入れると回復指標が 1 になるのは、この計測の対照条件だ。

主評価には、乱数を変えた実行の反復や平均報酬の信頼区間が示されていない。トークンの表は判定役を含む運用費用や応答時間を示すものでもない。

## Executable Understanding

Lab の作例では、決められた 4 つの制約を同じ順序で計 6 回使う。推論を残す条件、推論だけを消す条件、ファイルに保存してから消す条件、保存はするが読めない条件を比べる。削除は要求列の開始前だけに行う。論文のように、次の呼び出しのたびに履歴を削る実験ではない。

作例では推論の参照に 1、ファイルからの読出しに 2、制約を求め直す作業に 10 を割り当てた。いずれも作例内の仮の単位で、トークン数ではない。

## Results

推論を残す条件では、制約を求め直す回数は 0 回だった。推論を消してもファイルを読める場合は 0 回で、最初に必要になった 4 つの制約をファイルから読んだ。推論しかない場合と、ファイルを読めない場合は、ともに 4 回求め直した。4 つの条件で、6 回の要求に返した値はすべて一致した。

## What We Verified

Lab は、同じ入力と順序なら、保存した制約を読める条件だけが、推論を消しても再計算を避けることを確認した。この確認の対象は、決められた規則で情報を探す作例に限る。論文で使った段落の採点や、モデルが後で選ぶ行動は再現していない。

## What We Did Not Verify

Lab は DeepSeek-V4-Flash も Qwen3.5-9B も実行していない。WorkBuddyBench の報酬、実トークン数、判定役の費用、作業時間、本番での挙動は未検証だ。著者の 67.31% と 36.15% を作例で測り直したわけでもない。

## Implementation

リポジトリ直下で次を実行すると、作例が結果を出力し、Lab のページを生成する。

```bash
uv run --no-project papers/agent-reasoning-forgetting-externalized-state/run.py
uv run paper-lab build
```

`run.py` の `replay()` は、まず残した推論を探し、なければ読めるファイルを探す。どちらにも制約がなければ、決められた式で値を求め直す。この作例に外部 API や追加ライブラリは不要だ。
