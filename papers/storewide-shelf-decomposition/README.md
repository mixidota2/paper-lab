# 棚を配る前に、各幅で何を売れるかを計算する

店全体で使える棚幅から、カテゴリごとの幅、置く商品、商品ごとのフェイス数を決める教材である。フェイス数は商品の正面を横に何列見せるかを表す。先に各カテゴリで幅ごとの最大利益を求め、その結果を使って店全体の棚幅を配る。どの通路や棚に置くかは、この計算では決めない。

Tüzün Aksuほか（2025、DOI 10.17341/gazimmfd.1600434）の既刊論文を、合成した6 SKUの例で理解する。利益は単位粗利に需要を掛け、補充費と商品採用費を引いたモデル上の値であり、実店舗で観測した額ではない。

## 手元で実験を再実行する

リポジトリのルートで実行する。Pythonは標準ライブラリだけを使う。

```bash
uv run --locked papers/storewide-shelf-decomposition/run.py
uv run --locked --extra dev pytest tests/test_shelf_decomposition.py
uv run --locked python -m paper_lab.build --out /tmp/paper-lab-shelf-preview
```

全教材のビルド先を一時ディレクトリに分け、既存のsite/は上書きしない。

`run.py`は同じディレクトリのresults.jsonを更新する。乱数は使わない。ブラウザーで試す場合は、interactive.html、interactive.js、model.jsを同じディレクトリに保存し、ローカルHTTPサーバーから開く。

```bash
uv run --locked python -m http.server 8000 --directory papers/storewide-shelf-decomposition
```

http://localhost:8000/interactive.html を開く。全店容量、代替率、弾力性、補充費、SKU固定費、需要保持率、最低ブランド数を変更できる。価値表のボタンを押すと、採用SKUと費用の内訳が表示される。「現在の入力と結果を保存」を押すと、合成入力と計算結果がJSONに保存される。本改稿では、実ブラウザーでの画面操作とスマホ・PCでの表示は未確認である。公開前に確認が必要である。

## 初期値の答えを独立した全列挙で固定した

初期値ではカテゴリAとBに割り当てる幅がA:B=3:2となる。選ばれたフェイス数はA1=1、A2=2、A3=0、B1=2、B2=B3=0。利益は150.78059291689343で、同じ利益を出す別のフェイス構成はなく、解は1通りである。基礎粗利に比例させる基準案も初期値では3:2になるが、この一致から方式の優劣は判断できない。

Pythonは6商品の729通りを一括で調べる。JavaScriptはカテゴリごとの27通りを調べ、幅ごとの最大利益を表にする。同点を判定する浮動小数点数の許容誤差は1e−9。表示する解は、フェイス列の辞書順を優先し、同じフェイス列なら不要な割当容量を最小にする。results.jsonには、一括列挙で求めた最適なフェイス構成の件数も保存する。割当容量が異なっても、フェイス構成が同じなら別解に数えない。

## 確認範囲を分ける

- CONFIRMED：合成条件で需要を直接計算し、有限の候補内で最適値が一致することを確かめた。検査条件はtests/test_shelf_decomposition.pyに記載。
- PARTIAL：論文の仕組みを小規模な例で確かめた。線形化したソルバと原論文と同じ規模の計算は再現していない。
- NOT OBSERVED：著者の実装コードと、継続して商用運用していることを示す独立した証拠は確認していない。
- NOT TESTED：実店舗での売上・利益の改善、性能と規模を広げたときの動作、実ブラウザーでの画面は検証していない。

図、データ、実装、日本語の説明はこのLabで作成した。原典の全文や図版は複製していない。原典と実装との対応、印字上の不整合はmapping.md、数式と制約はmethod.mdを参照。

図や操作文言の分岐は `uv run --locked --extra dev pytest tests/test_shelf_ui.py -q` で確認できる。この検査にはDOMの代替を使う。実ブラウザーでの描画、画面幅、操作、ダウンロードは、この検査の対象に含まれない。
