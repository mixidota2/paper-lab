# 店全体の棚幅と、カテゴリごとの品ぞろえを決める

Tüzün Aksuらは、限られた棚幅をカテゴリに配り、各カテゴリで置く商品と陳列面数を決める方法を提案した。研究の前半ではカテゴリごとに棚幅の候補を調べ、後半では店全体の幅が上限を超えないように組み合わせる。陳列面数（フェイス数）は、商品正面を横に何列見せるかを表す。[原論文（2025年）](https://doi.org/10.17341/gazimmfd.1600434)は、棚の高さや店内の位置を決める研究ではない。

Labは6商品の架空の例を作った。教材では、商品が売れると見込む数に単位粗利を掛けて足し、補充費と採用費を引く。この計算値は店舗で記録した利益ではない。

## 初期条件の結果

Labの計算では、Aに幅3、Bに幅2を配る案の利益が最大になる。A1を1面、A2とB1を各2面置き、A3、B2、B3は置かない。利益は150.78059291689343で、同じ利益になる別のフェイス構成はない。この初期条件では、基礎粗利の比で幅を配った案も同じ3対2になる。初期条件だけで、どの方式が一般に優れているかは判断できない。

Pythonでは全店を一括で729構成調べ、JavaScriptでは各カテゴリで27構成を調べる。利益が同じかは絶対許容誤差1e−9で判定する。表示する案はフェイス数の列を先頭から比べ、それも同じなら、余分に割り当てる幅が少ない案を選ぶ。`results.json` は同じ利益になるフェイス構成を数える。割当幅だけ異なる案は別構成にしない。

## 教材を再実行する

リポジトリの最上位で、次のコマンドを実行する。Pythonの計算は乱数を使わず、標準ライブラリだけで `results.json` を作り直す。

```bash
uv run --locked papers/storewide-shelf-decomposition/run.py
uv run --locked --extra dev pytest tests/test_shelf_decomposition.py
uv run --locked python -m paper_lab.build --out /tmp/paper-lab-shelf-preview
```

サイトを確認するときは、既存の `site/` ではなく、新しい一時ディレクトリに出力する。画面だけを試すなら、`interactive.html`、`interactive.js`、`model.js` を同じディレクトリに置き、ローカルHTTPサーバーを使う。

```bash
uv run --locked python -m http.server 8000 --directory papers/storewide-shelf-decomposition
```

http://localhost:8000/interactive.html を開く。店全体の棚幅、代替率、面数で増える需要、補充費、採用費、保つ基礎需要の割合、最低ブランド数を変えられる。カテゴリの幅を押すと、その幅で置ける商品と費用が表示される。「現在の入力と結果を保存」を押すと、入力と計算結果をJSONで保存する。

## Labが確かめた範囲

- **CONFIRMED（教材で確認）**：直接計算で需要を求めた。同じ候補幅と独立したカテゴリを使うと、一括計算とカテゴリ別の計算で最大利益が一致した。
- **PARTIAL（原論文との対応を部分確認）**：教材は論文の手順の一部を小規模に試している。著者の線形化ソルバーや、原論文規模の実験は再現していない。
- **NOT OBSERVED（確認できる資料なし）**：著者コードと、継続した商用運用を裏付ける独立資料は確認していない。
- **NOT TESTED（未検証）**：実店舗の売上・利益、規模を広げた性能、改稿後の画面を実ブラウザーで操作した結果は、この教材のテスト対象ではない。

図や操作文は `uv run --locked --extra dev pytest tests/test_shelf_ui.py -q` で確認できる。このテストはDOMを代用する。実ブラウザーでの描画、幅、操作とダウンロードの確認にはならない。

`method.md` はモデルの仮定、`experiment.md` は操作と手計算の例、`validation.md` は確かめた範囲、`implementation.md` は実装を説明する。式の印字をどう読んだかは `mapping.md` にある。図とデータはLabが作り、著者の図版や全文は転載していない。
